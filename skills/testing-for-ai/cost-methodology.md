# 周期成本的诊断与优化模式

> **本文件与 `SKILL.md` 的分工**：本文件是**周期成本的诊断与优化手册** —— 五段模型、三个定义陷阱、五个症状、七项优化模式、反模式、真实案例、两小时自检清单、AI 自诊失误类型、盲区；自足，可单独读。
> `SKILL.md` 是**体系决策层与落地顺序** —— 目标与度量（A）、门禁与真值（B）、确定性（C）、文档与规则（D）、静默与画面证据（E）、落地顺序（F）；机制细节见 `REFERENCE.md`。
> 两处重合时的口径：**判定标准**以 `SKILL.md` A1（"必须是周期成本类"）为准；**瓶颈在哪一段、该选哪个模式**以本文件的诊断流程为准。本文件**不重复** `SKILL.md` 的规则与门禁设计。

> **触发与不适用**（合并自原 `iteration-cost` skill，原文保留）：降低「单次迭代周期」成本：把迭代看成「①定位→②理解→③改→④验证→⑤记录」五段，先量瓶颈在哪段，再只打那段。触发：项目越做越慢 / 改动前要读的越来越多 / 验证越来越重 / 历史越来越难追溯；AI 改完要跑很久才敢说没改坏；验证是一条跑不完的 && 长链；要给长期 AI 迭代项目做优化排期或加门禁；有人把「省 token / 降 API 账单」当优化目标；诊断时验证跑不起来（先分清环境还是能力问题）；要给超大 CHANGELOG 做可追溯改造；复盘「做了很多但没变快」。不适用：一次性脚本、寿命短于一个月的项目、验证无法自动化的主观质量项目。

> 只优化「**迭代这个动作本身**」的成本；**不**解决"AI 更聪明 / 代码更快 / 功能更多"。
> 出处：一次对真实长期工程（AI 生成、由 AI 持续迭代）的完整研究；本文自足。

## 0. 什么时候用 / 不用

| 场景 | 用不用 |
|------|-------|
| 越做越慢：改动前要读一大坨、验证越来越重、说不清上轮改了什么 | ✅ 核心 |
| AI 生成并由 AI 持续迭代、长期演进、有验证链、文档即契约 | ✅ 越符合越适用 |
| 有人把"省 token / 降 API 账单 / 回答质量更高"当目标 | ✅ 先用 §1 掰回 |
| 一次性脚本、寿命 < 1 个月；好坏无法机械判定 | ❌ 不在射程 |

前置：① 一条命令跑完的验证入口；② 变更记录机制；③ 一个"唯一真源"约定。

> ⚠️ 全文出现的**具体阈值、倍数、价格比**都只是**参考量级**（来自一次真实工程），**不是判定标准**。
> 用它们**排序**（哪段最值得打），不要用它们**卡线**（"没到 30 s 就不用优化"）。

## 1. 先定义目标（最容易做错的一步）

**周期 = 五段**：`① 定位→② 理解→③ 改→④ 验证→⑤ 记录`（③ 通常不是瓶颈）。目标：**降低单次迭代周期的总成本**。

| 定义陷阱 | 后果 |
|---------|------|
| 把**手段**当目标（"省 token / 上下文效率"） | 整套方案只优化 ①，而**瓶颈在 ④** |
| 把**成本**当目标（"减少 API 费用"） | 有缓存定价时小到无法测量 |
| 把**输出**当目标（"回答质量更高"） | 产品能力，与迭代速度不同轴 |

判定只用**周期成本类**指标：验证链可用性 / 验证耗时 / 可增量断言占比 / 追溯成本 / 回滚能力 —— **不用** token 消耗、上下文占比、模型评分。
**换算原则**：任何优化都要能回答「**它让哪一段变快了多少**」。

## 2. 诊断：先量再优化

**铁律：先测出瓶颈在五段中的哪一段，再选药。**

1. **计时 + 逐段耗时表**：逐段跑验证链记秒数，算 `单段耗时 ÷ 断言数`，先打**占比最高**的段（> 50%）。
2. **五个症状**：**S1 慢**（单次验证 > 30 s；"慢"≠"坏"）；**S1b 跑不起来**（先分清环境/能力）；**S2 全或无**（`&&` 长链）；**S3 追溯贵**（首个文件 > 100 KB）；**S4 多副本**（同一事实 ≥2 份且不一致）；**S5 承诺≠能力**（文档里的通道不存在）。做法见 §7。
3. **预算写进 runner 而非文档**（让"悄悄涨回去"变红），并输出**归因表**（段位 / 耗时或可用性 / 是否瓶颈 / 对应模式）—— **只有瓶颈段才值得投入**。

**判断 A：先分清「跑不了」是能力还是环境问题。** 失败时不要立刻说"对象有缺陷"，先做**环境对照**（换沙箱 / 换机器 / 最小复现，同命令再跑）：**能跑 ⇒ 环境问题**（改测量或去耦合）；**仍跑不了 ⇒ 能力问题**（**排在所有优化之前**）。

> 教训：受限环境的假失败被我当成"验证链坏了"，最高优先级定为"修可用性"；换环境后同批命令全绿。**能力问题修对象，环境问题修测量**。

**判断 B：瓶颈通常不在"读"而在"验"**：读取一次性，验证每次迭代都付。

## 3. 七项通用优化模式

**1 验证进程内调用★**｜把"起子进程 + 捕获输出"改为进程内调用，免付每条断言的冷启动。｜`耗时÷断言数` 达数百毫秒/条 ⇒ 是启动开销。｜入口导出纯函数。｜退出码/输出是**对外契约** ⇒ 先写契约快照。

**2 消除「为统计而重跑」**｜派生数据走机器可读通道，别为拿数字重跑整套测试。｜存在"为统计而重跑"的脚本。｜reporter 落盘 → 脚本读文件。｜落盘有读旧值的竞态；**失败必须 fail loud**。

**3 拆「快链 / 全链」**｜`&&` 长链 ⇒ 改一行也跑全量，真正的杀手是**人们因此跳过验证**。｜能否按改动面选子集。｜快链秒级（单测 + 数据校验）/ 全链分钟级（+ E2E / 冒烟）。｜防"只跑快链就宣称完成" ⇒ **交付清单强制全链**。
｜**进阶：当快链自己长到分钟级时**（工程变大后必然发生），两级不够用 —— 需要**档位阶梯 + 机选**：
① **先把「收口检查」从快链里拆出去**：只对交付证据有意义的贵检查（覆盖率收集 / 性能趋势 / 发布一致性等）归全链、快链跳过（实测：某工程一段占全链约 46% 的检查塞在快链里白付 ~10 分钟，快链因此名存实亡——快链全程 14 min 15 s ≈ 全链 20.7 min 的 69%）；② **改动面 → 档位映射机械化**：档位阶梯（如 文档档 / 域档 / 快链 / 全链），由**只读建议器**从 `git diff` 推导 + 输出「被跳过的面 + 兜底说明」；三条纪律 —— **保守升级**（判据面 / 构建面 / 未识别路径一律升全链）、**映射表本身是判据**（放入判据冻结集；改它走判据变更通道；保守方向配门禁 + 判别力证明）、**工具只给建议不做判定**；③ **收口分两步开放**：先只放「物理上不参与构建/测试输入」的那一档（如纯文档批次——其全部相关门禁可被枚举实跑），其余档在**观察期**（零事故 + 映射表有判别力证明）后再放开。有工程按此落地过（实例见 `cases/`）。

**4 窄通道替代读全量**｜高频窄问题给一个只回答它的极小接口。｜答窄问题却要读整份数据。｜一条 CLI 命令 + 一个极小状态文件。｜状态**必须明确失效方向**，**绝不因残留状态永久阻塞使用者**。

**5 为「理解成本」建持久层**｜定位有 grep、验证有测试，唯独"为什么"没有机制承载。｜新会话都要重新推导"当初为什么这么写"。｜决策记录 ＞ 变更索引 ＞ 跨会话记忆。｜⚠️ 最大风险是**引入第二个真源** ⇒ 自动生成的知识只取任务清单，**禁止**写架构与决策。

**6 让追溯成本与项目年龄解耦**｜append-only 的变更日志读取成本随年龄线性增长，而它服务的动作**每轮都发生**。｜答"上轮改了什么"要打开的文件 > 100 KB 且单调增长。｜① 生成"每版本一行 + 标题"目录 ② 分层读取 ③ 超 N 版归档留指针 ④ 发版清空未发布段。｜归档损失 grep 便利 ⇒ **必须留在同仓库**。

**7 补齐全量与单条之间的粒度**｜只有"一个对象"或"整棵树"两档，会逼人为取 3 个对象读全部。｜有无子树 / 按 id 批量 / 仅骨架 / 压缩输出。｜补中间档；去美化输出（破坏序列化确定性 ⇒ 缓存前缀不稳）。｜只加档位、不改规则侧。

## 4. 加门禁的三条硬规矩

1. **只加在"每次迭代都付"的地方，别给最频繁的动作加成本。** 给最高频动作新增强制步骤 = 反向加码。排序：**每次迭代都付 > 每轮付一次 > 一次性**。
2. **采不到真值 = 红；跳过不得伪装成一致。** 取不到真值时静默 skip 的门禁等于不存在；宁可红，也不要假守护。
3. **判定自身要有判别力，且不能过窄、不能自我判红。** 上线前注入一次违规确认它变红；判定过窄（排除最常用写法）会近乎失效；引用缺陷原文会被判定自己判红 ⇒ **改措辞，别弱化判定**。

## 5. 反模式

| 反模式 | 为什么不该做 |
|--------|-------------|
| 1 把"省 token"当目标 | 有前缀缓存定价时，**命中价远低于未命中**（量级随供应商与时期变化，故不写倍数）⇒ 省的是分位数，不是成本 |
| 2 为省 token 改写前缀 | 前缀缓存要求从第 0 个 token 起完全相同，改一处即作废 ⇒ **"稳定"优先于"更短"** |
| 3 加原生向量库 | Windows 构建被官方称 "complex"，与"零依赖/单包分发"不相容 |
| 4 直接改默认值而非让成本可见 | 破坏既有习惯、常用路径可能多一步 ⇒ **总成本反而上升**；更稳：保留默认 + 自述成本 |
| 5 直接改发行版自带模板 | 升级会覆盖 ⇒ **要改就复制一份再改** |
| 6 用"兼容层"实现核心能力 | 只覆盖上游部分事件，**且往往恰好缺掉你需要的那几个** |
| 7 盲装生态插件 | 它解决的是**它自己的**问题。**先问"它让哪一段变快"，答不上就不装** |

## 6. 案例：某次真实工程的数字

> ⚠️ **某一次真实工程改造的实测值**，只用来看量级与方向，**不是通用目标、更不是 KPI**。

| 项 | 前 | 后 |
|---|---|---|
| 集成断言段 | 102.1 s | **4.2 s**（本以为要改 188 个调用点，实测**一处未改**） |
| 全量读取 | 211,820 B | **28,841 B**（−86.4%） |
| 答"上轮改了什么" | 213 KB 变更日志 | **10.4 KB** 索引（22.6×，不漂移） |
| 单次验证总耗时 | ≈154 s（后更正 176.3 s） | 67.8 s（**未达标**：52.6 s 是"真启动 GUI"的固有成本） |

**最该学的三件事**：① 真瓶颈常不在计划以为的地方；② 慢步与断言可能**天然不可拆、不可增量**，别设绝对值目标；③ 新门禁上线即红是它在工作，不是它坏了。

> ⚠️ **时代锚（必读）**：上表是**某一次改造（2026-09）**的实测值。同一工程的链耗时此后**又降到数十秒**
> （量级不变），说明这类数字是**随被测对象一起漂移的** —— 拿它们**排序**可以，拿它们**卡线**不行
> （见 §0 的免责声明与 `SKILL.md` A1：判定标准必须是周期成本类，不是某个具体秒数）。

## 7. 两小时自检清单

> 可直接照做（假设你有一个由 AI 迭代的项目）。

**第 0 步（10 min）明确目标**：□ 目标**必须是周期成本类**（非 token/成本/质量） □ 写明**不在范围**的三件事
**第 1 步（30 min）测症状**：□ **S1** 逐段跑、记每段秒数、算"耗时÷断言数" □ **S1b** 有步骤不过先做**环境对照**（换沙箱 / 换机器 / 最小复现）：能跑 ⇒ 环境问题；仍跑不了 ⇒ 能力问题 □ **S2** 能否按改动面选子集 □ **S3** 首个要打开的文件多大 □ **S4** grep 规则/版本号，数副本查一致 □ **S5** 文档声称的通道是否存在
**第 2 步（20 min）归因**：□ 症状映射到五段，输出"哪一段是瓶颈"（**可能不止一段**） □ "仍跑不了" ⇒ **能力问题排最前**；"环境问题" ⇒ 按普通优化项处理 □ S1 几乎总命中 ⇒ 按占比排序
**第 3 步（30 min）选模式**：□ 从 §3 只选 **2–3 个**（**不要全选**） □ 每个写出：现状值 → 目标值 → 验收方式 □ 对照 §5 没踩坑
**第 4 步（30 min）排期与风控**：□ 按"每次迭代都付 > 每轮付一次 > 一次性"排序 □ 每个改动写出**回滚方式** □ 标注哪些是**推算**、哪些已**实测**

## 8. AI 自诊的失误类型（同类诊断里复发率很高）

| 失误 | 可识别特征 | 怎么避免 |
|---|---|---|
| **1 把手段当目标**：动作**无一让验证更快** | **全部**动作都指向同一段 | 先写目标再写动作，每个动作要能回答"它让哪段变快" |
| **2 断言的「方向」搞反**：阈值方向被一手数据推翻 | 结论建立在"经验值 / 社区说法"而非**权威数据**上 | "倍数/比例"类论断先拿一手数据；拿不到就标"未验证"，不要推算 |
| **3 用「泛论」代替「逐条评估」**（最隐蔽）：替代路径其实没在用 | 否决理由**换个对象也成立** | 逐条对着硬约束列不相容点，并确认**替代路径真的在工作** |
| **4 把「测量环境的限制」当成「被测对象的缺陷」**（后果最严重）：换环境后同批命令全绿 | 证据全来自**某一种环境**；报错是**权限 / 沙箱 / 管道 / EPERM** 这类**环境词** | 下"对象有缺陷"结论前**强制插入环境对照**：能跑 ⇒ 修测量/去耦合；仍跑不了 ⇒ 修对象，排最前 |

**共同结构**：`用一个"听起来对"的判断，替代了对本项目的具体测量。`（手段换目标 / 经验泛论换一手数据 / 局部证据换全称结论）。
**两条硬规则**：① **"缺陷"类结论前必须有环境对照**；② **"能力/边界"类结论必须来自一手装配材料**（不看挂载清单，不许说"它做不到"）。
**对策**：结论标注"实测 / 官方数据 / 我的推断"；危险的错误**不会进"未验证清单"**，因为它当时看起来像已证实。

## 9. 盲区

| 盲区 | 说明 |
|------|------|
| 不解决"验证本身不够强" | 更快、不再因环境假失败，但**不保证测得对** |
| 不解决零测试项目 | 无自动化验证 ⇒ 模式 1–3 无对象 |
| 理解层轻量做法有上限 | 决策记录靠自觉、**无门禁可强制** ⇒ 会腐坏 |
| 不适用于主观质量主导的项目 | 好坏无法机械判定时，瓶颈不在验证吞吐 |
| 外部阻塞无解 | 如企业禁用版本控制：只能给**弱等价**，且**不应假装等价** |
