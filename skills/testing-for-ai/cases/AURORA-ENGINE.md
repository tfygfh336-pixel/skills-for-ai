# 可验证工程在 AuroraEngine（原生 C++ 引擎）的落地

> 与 [`VISION-LOOP.md`](VISION-LOOP.md)（Electron 笔记应用）互补：那份是**带界面的应用**，
> 这份是**原生 C++ / 游戏引擎**。两份共享同一套方法论（`SKILL.md` 的 A–F），
> 差异集中在"离屏、输入、判定"三件事的实现方式上。
> **时代锚**：本案例初版写于 2026-10（v0.60.0）；**2026-10-14 已刷新至 v0.240.0**
> （C++20 / MinGW-w64 / Ninja / Vulkan + OpenGL 双后端）。数字随被测对象漂移，只用于排序，
> **不可当目标值**（SKILL A1）；下文未特别标注的量化数据均为 **v0.240.0（2026-10-14）** 现场实测。
> §9 记录了初版之后该工程继续演进出的机制（v0.66 → v0.240）。

## 0. 闭环全景（本工程视角）

| 六件套 | 本工程的实现 |
|---|---|
| ① 离屏 | `--headless` + 引擎自带 `beginOffscreen(w,h)` / `endOffscreen(path)`；**不用系统截屏**（游戏帧的抓取引擎自己最稳） |
| ② 输入 | 引擎自己的按键状态注入 `window.debugSetKey(code, down)` + 鼠标增量；**不是合成系统事件** |
| ③ 截图 | PPM（无第三方依赖，可逐字节比对）；转 PNG 只为给人/AI 看 |
| ④ 驱动 | **声明式脚本**（JSON）逐帧喂输入，见 §4；外加 CLI 与 MCP 两个等价入口 |
| ⑤ 判定 | 五层（§2）：ctest 分组 / 隔离套件 / 通关脚本 / 视觉 / 文档门禁 |
| ⑥ 留痕 | `tools/verify/run_verify.py` 每次打印逐段耗时表（含**链后段**）+ 落 `verify_last.json`（含 postchain 摘要）；证据包绑帧 sha256 |

**一个入口**：`python tools/verify/run_verify.py`（全链）／`--quick`（快链，跳过链后三段）。
它做四件事：跑完 ctest、按桶打印耗时并**强制预算**、跑前后对工作树逐字比对（G5）、
跑**链后检查三段**（coverage / perf-trend / tag-version，各自计时 + 预算）。
**实测（v0.240.0）**：全链端到端 ≈ **21 分钟**（ctest 段 655 s + coverage 段 583 s + 杂项 ~5 s）；
快链修复后 ≈ **3.6–4 分钟**（修复前实测 14 min 15 s —— 链后三段当时无条件跑，其中一段就占 ~10 分钟）。

## 1. 栈的差异：相对 Electron 那份，哪些前提变了

| 维度 | Electron | 原生 C++ 引擎（本工程） |
|---|---|---|
| "不弹窗" | 要专门关 `show`/`backgroundThrottling` | **天然没有窗口**（headless 无 Win32 窗口） |
| 输入注入 | 合成 DOM/系统事件 | **引擎内函数直调**（`debugSetKey`）—— 更快，但"真实事件链"的保证弱一档：它绕过了 OS 层，只保证"从输入状态到行为"这一段 |
| 判定粒度 | 像素统计为主 | **进程退出码 + 结构化输出**为主，像素只是其中一层 |
| 冷启动成本 | 秒级 | **进程启动 ~1.9 s**（含载入引擎、建资产、建渲染设备）⇒ 决定"一条用例一个进程"不可行，必须**分组**（见 §3） |
| 并行 | 可以并发 | **必须串行**：同进程反复建/毁 Vulkan 设备会在 loader 层崩且**无任何报错**（真实验过：第二次 `vkCreateSwapchainKHR` 静默退出） |

## 2. 分层（本工程实际在用的五层）

层名**刻意不编号** —— 本领域的 `L0–L4` 已被"视觉判定阶梯"占用（产物存在→有效帧→ROI→基线差率→读图），同名会读错。

| 层 | 答什么问题 | 入口 | 抓不住 |
|---|---|---|---|
| 单元 | 某个函数/类对不对 | ctest 的 16 个**分组**（每组一个进程）+ `aurora self-test` | 跨模块接线 |
| 集成 | 模块之间接得对不对 | ctest 的 **isolated 条目**（17 个设备套件，会建 Vulkan 设备，必须一条一进程）+ `aurora test run --suite smoke\|regression` | 真实内容上的行为 |
| 端到端（数据驱动） | 一个**真实关卡**玩不玩得通 | `aurora test run --suite playtest --project <p>` | 画面；碰撞（本工程未接，见 §7） |
| 视觉 | 这一帧画得对不对 | `--capture-level-out` → `aurora inspect`（+ 由调用方 AI 读图） | 语义/美感 —— **只出证据，不做门禁** |
| 文档/规则 | 文档与真值一致吗 | `aurora doc-facts --check`（门禁 G1/G6/G7/G11/G12/G16–G22） | 语义正确性（只判"一致"，不判"说对了"） |

## 3. 一个入口 + 预算：为什么"分组"是必须的

**实测（2026-09-30）**：445 条 gtest 用例，逐条一个进程 = **533 s**；整个二进制一次跑完 = **57–80 s**。
⇒ **约 90% 的墙钟花在进程冷启动上**，而不是被测对象。

改法：把用例按**区域**合成分组条目（每组合成一个进程），只把"会建 Vulkan 设备"的套件
逐条隔离。**现状（v0.240.0）**：**1112 条 gtest 用例 / 222 个套件**收敛成 **99 条 ctest 条目**
（16 个分组 + 40 条守卫 + 43 条 isolated，口径为 2026-10-14 全链现场输出）；ctest 段实测 **655 s** ——
其中「起进程」的桶占 ~77%（**进程模型没变，是用例与条目在长**：这是「正当变慢」而不是结构性退化，
预算据此逐桶重校准，超线时先分流再调参、并写明理由）。

**代价与必须补的守卫**：分组用的是**模式**（`Gen*` 这类），模式写漏一个套件 ⇒ 那些用例
**永远不会被跑到**，而"没跑"与"通过"在报告里长得一模一样。
⇒ 必须有一条**覆盖守卫**（本工程 `guard-test-coverage`）：拿 `--gtest_list_tests` 的**运行时**输出
（不用源码正则）与 CMake 注册的过滤器清单求差集，**任一条用例不被覆盖即红**。

**预算写进 runner 而不是文档**（SKILL A2）：`tools/verify/budgets.json` 逐桶记 `budget / max_observed /
factor`，超了 exit 1。它是**止涨线**，不是性能目标。
⚠️ 但它**会随用例数增加而合法上涨**：本工程实测一次「用例 16→17 条、44.5→59.8 s」，
按文件自身的方法论 `ceil(max × 1.5)` 上调到 90，并**在 JSON 里写明为什么涨**；
区分「正当变慢」与「结构性退化」是每次调整时必须回答的问题。

## 4. 端到端层：脚本化通关测试（本工程最有价值的一块）

**问题**（真实现象）：每个模块各有单测，但"这条链路走得通"没人验 ——
移动只在**空演示世界**里按过键；对话在真实关卡里测过却靠**瞬移 + 直接调 API**
（`pos = npc.pos + 1; talk()`）。于是「**走过去**并按 E 交谈」这条跨四模块的真实链路
**从来没有被验证过**。

**做法**：一份 JSON 脚本，由测试入口**逐帧喂真实输入**、在**真实加载的数据**上执行：

```json
{ "steps": [
  { "frames": 30 },
  { "mark": true },
  { "walkTo": { "npc": "elder", "range": 1.8, "timeout": 1800 } },
  { "assert": { "talkableId": "elder" } },
  { "talk": true },
  { "assert": { "inDialogue": true } },
  { "choose": 0 },
  { "assert": { "questState": { "id": "q_main", "state": "active" } } },
  { "assert": { "questProgress": { "id": "q_main", "objective": "firewood", "count": 0 } } },
  { "walkTo": { "interactable": "well_water", "range": 1.5 } },
  { "assert": { "interacted": { "id": "well_water", "expect": false } } },
  { "interact": true },
  { "assert": { "interacted": { "id": "well_water" } } },
  { "assert": { "questProgress": { "id": "q_main", "objective": "firewood", "count": 1 } } }
] }
```

要点（每条都由一次真实事故换来）：
1. **每帧两步都做**：先喂控制器（输入→位移），再把结果喂关卡（位移→判定）。
   只做一步就只测到半边 —— 这是"端到端"与"两个单测"的分界线。
2. **脚本拿一份独立的会话**，并把被驱动的对象**显式置回初始态**
   （否则上一段检查把角色走掉了，"从出生点出发"是假的）。
3. **判据成对**：`expect:false`（改变前）+ 默认 true（改变后）。只看后一半，
   在"本来就已 true"时假绿。
4. **样本不要落在对称轴上**（见 §5 第 4 条）。
5. **失败要说得出原因**：把"没到达"拆成 **卡住**（连续 N 帧无推进 ⇒ 报卡点坐标）与
   **超时**（在推进但不够快）—— 两者的修法不同（改路径 vs 放宽预算）。
6. **脚本字段/键名写错要明确报错**，不静默忽略 —— 否则你会以为自己按了键。

**接入标准入口**（否则它不是"体系"的一部分，只是"某人手敲过一条命令"）：
`aurora test run --suite playtest --project <工程>` 跑该工程的全部脚本，
判据与 ctest 侧一致：**任一份非 0 ⇒ 失败**；**一份都没有也失败**
（"没写测试"与"测试通过"必须在报告里长得不一样）。

## 5. 判据口径：6 条，每条都有事故

| # | 口径 | 事故（真实发生） |
|---|---|---|
| 1 | **采不到真值即红**（解析不出/文件缺失/空集合 ⇒ 判红并打印"无法取得真值"；`skip` 不得伪装 `pass`） | 覆盖守卫拿不到用例列表时必须红，否则"没跑"会读成"通过" |
| 2 | **跨副本逐字相等**（同事实多处表达时用逐字比对；禁用"能解析成合法 X"这类弱判据） | 引擎版本已 0.58.0，而 `CMakeLists` 与 `vcpkg.json` 仍写 **0.56.0**，**漂 2–3 版而没有任何门禁会红**（运行期自检只看得到运行期来源）⇒ 建 G22 |
| 3 | **判别力证明的锚点不写字面量**（从单一真源现场拼出） | 写死 `VERSION 0.59.0` 的证明会**随每次升版腐烂**：下次升版后它报"锚点不存在"，而不再是"门禁有牙" ⇒ 判别力**悄悄消失** |
| 4 | **样本不要落在对称轴上** | 朝向公式符号错（`atan2(dx,-dz)` 应为 `atan2(-dx,-dz)`），而它在目标位于**正前/正后**（`dx==0`）时与正确式**完全一致** ⇒ 第一份脚本（NPC 恰在 -Z 轴）一直绿；把 NPC 挪到 `(6,0,0)` 才暴露：**人朝反方向走出 30 m** |
| 5 | **状态改变要成对断言** | 交互物断言查"id 还在不在列表里"，而被消费对象**从不移除**（只置 `consumed`）⇒ **恒判红**；且它**从未被任何脚本用过**，缺陷潜伏。修好后又发现：只看"改变后为 true"在"本来就已 true"时假绿 |
| 6 | **隔离的实例** | 脚本真的把玩家走遍关卡、惊动 NPC ⇒ 与内建检查**共用同一个会话**时，那些检查的前提不再成立，**因其无关的原因变红**；得到的是**互相污染**，不是"更省" |

**后记（2026-10-14 追记 · 两条同族新形态，均由真实事故驱动）**：

| # | 口径 | 事故（真实发生） |
|---|---|---|
| 7 | **临时物命名必须含进程唯一标识** | ★实测：测试套件的临时沙箱用**固定名** + 构造/析构 `remove_all` ⇒ **单进程** `--gtest_repeat=300` 全绿（4200 次执行 0 红），而**双进程**同条件并跑 ⇒ 各在 ~1200 次执行时出现 ~200 红、且两边报文互相印证（"第二次写入被拒（应当成功）"/ `CreateFileW failed, err=32` / 共享冲突）。⇒ 修法 = 临时根按进程唯一（`<名>_<pid>`）；**证明**修复要用**同条件的双进程复跑**（单进程跑不出来） |
| 8 | **自动化产物必须被自动化消费** | ★实测：某"可执行 walkthrough"脚本自称"跑不通即失败"，却**没有任何自动化在跑它** ⇒ 从 v0.68 到 v0.214 连红 **146 个版本无人发现**。⇒ 判据：任何"自验脚本"必须被主链**真的消费**（建成 ctest 条目），否则它只是文档——**没人跑的判据，红了也等于没红** |

## 6. 门禁的家：注册表渲染 + 生成区新鲜度

本工程的门禁清单**不是手写表格**：唯一真源是一个 C++ 注册表（编号/短名/实现命令/守卫名/挂载点），
文档里的表格由渲染器生成，写进"生成区"标记之间；检查时**重算并与磁盘逐字比对**（G7）。

好处：**"忘了把新门禁写进表"不可能发生**（表格自动跟随）。
代价：渲染器本身成了**唯一的破坏点** —— 实测发现它**不转义 `|`**，
于是 `--suite smoke|regression` 里的分隔符把那一行**渲染成 5 列**（列标题与内容整体错位）。
而这类破损**不会让任何机器判定变红**（G7 只比对"渲染 == 磁盘"，两边一起错也绿）
⇒ 属于**只有人读才发现**的坏。
修法：**转义放进渲染器**（不是"要求作者别写 `|`"——要求人记住迟早会忘），
并加一条守卫：数每行**未转义**的 `|` 应为 5、行数不足即红。
**这条守卫加上后第一次运行就报 `未转义 | 数 = 7（应为 5）` 并点名那一行** ——
判别力由**缺陷本身**提供，比人造注入更有说服力。

## 7. 环境与本机边界（诚实标注）

- **必须串行**：同进程反复建/毁 Vulkan 设备会在 loader/ICD 层崩且**无报错**。
  ctest 的 `-j N`、以及"边构建边跑 ctest"都会造出假失败（后者还因负载敏感：
  构建中 39.6 fps 判红 / 空闲 630 fps 通过）。**门禁前让机器空闲**。
- **MinGW 运行时**：跑"调独立 CLI 子进程"的用例需要 `mingw64/bin` 在 PATH，
  否则子进程起不来给 `rc=0xC0000135`，而断言只打印 "CLI failed" ⇒ **极易误读成逻辑失败**。
- **产物路径**：`endOffscreen` 这类接口**自己不建父目录**，且**默认别落 cwd** ——
  实测"从仓库根跑一次"就污染仓库根，被"根目录白名单"守卫判红；**`.gitignore` 救不了它**
  （那条守卫看的是**目录内容**、不看 git）。修法是给"产物目录"一个统一出口 + 环境变量可覆盖。
- **别养"跑前移走 / 跑后还原"的绕法**：同一个坑一度在 3 个文件里各写了一遍 ——
  那是"该修源头"的信号，不是"每处都小心"。
- **临时目录要含进程唯一标识**（2026-10 补）：见 §5 后记第 7 条 —— 固定名沙箱在多进程
  并跑时互删，症状分散且"单进程复现不出来"。

## 9. 初版之后继续长出的机制（v0.66 → v0.240，供"要更硬"的读者参考）

上文 §1–§8 写于 v0.60.0；此后该工程被真实迭代推着又走了半年，长出了五件**SKILL 正文未展开**
的机制 —— 每件都由一次真实事故驱动（细节见该工程 `docs/IN-FLIGHT.md`，此处只给形状与触发条件）：

  1. **验证窗口**（SKILL C4 的"机制化"①）：验证开始时申请**全局单例租约**（append-only 记录 +
     stale 五态接管，不留死锁；旁路必须**响亮声明**"本次无保护"）；并发写盘命令在窗口期被**拒**
     （命令级），验证自身的子进程经环境变量免拦。
  2. **判据冻结**（②）：跑链开始对"**验证装置**"（门禁实现 + 报告工具 + 链驱动 + 证明脚本 +
     阈值文件）算内容哈希，结束复算；漂移 ⇒ 本次证据**作废**（不是重跑能解决）。
  3. **判据变更串行通道**（③）：改判据前要求"所有并行 agent 停下"（不满足则 rc≠0 并**逐个点名**
     谁在跑/哪个键/何时到期），改完重钉基线才放行 —— 多 agent 常态化并行后，"改判据"成为
     唯一的串行点。
  4. **证明库保鲜守卫**（见 SKILL B4 后半）：一条守卫扫全部证明脚本的"锚点是否仍出现在其声明
     的靶文件里"，防"跑起来只报锚点不存在"的腐烂（实测一次扫出 6 份）；另配"**门禁脚本 ↔ 链条目**
     双向对账"守卫（孤儿脚本 / 死引用各自必红）。
  5. **预算逐桶化 + 先分流后调参**（见 SKILL A2/A4）：预算不是一条总账，而是**逐桶**
     （"起进程"的桶单独记账，防止把别的桶的余量一起放松）；超线时不直接放宽，而是先**分流**
     （用例数正当增加 vs 结构性退化），按 `max(3 次采样) × 系数` 重校准并写明理由；
     **表外的步骤也要进表**（曾有一段占全链 ~46% 的检查不在表、也无预算，涨了 1.7× 无人变红）。

> 这五件的共同形状：**先把纪律变成"可机检的机制"，再让机制自己被守卫**（保鲜守卫、接线守卫、
