## 1. 它解决什么：AI 迭代的三个失败模式

| 失败模式 | 表现 | 对策 |
|---------|------|------|
| **打扰** | 每次验证都弹窗、抢焦点、把测试数据写进用户真实目录 | §2.2 静默三层（不弹窗 / 不抢焦点 / 不碰真实数据） |
| **无据** | "跑过了" = exit 0，但**没人看过画面**；取景漂移、黑屏、白屏都不会让门禁变红 | §2.3 判定阶梯 L1–L4 + 读图 |
| **失忆** | 上一轮"界面看起来对不对"的结论没留下，下一轮重新看图、无法对比 | 读图产物落盘 + PNG 哈希绑定 |
| **假守护** | 门禁看着在跑，其实**永不生效**（正则匹配不到、逻辑没单测、跳过冒充一致） | §7 判别力证明 + §8 门禁可单测化 + 采不到真值 = 红 |
| **漂移** | 同一个数字有多份手写副本，静默互相矛盾 | §6 单源与真值口径 |

> "假守护"与"漂移"这两条是旧版 `silent-verify-loop` **没有**的，来自后续轮次的真实事故。

## 2. 核心模型

### 2.1 闭环六件套

```
AI 改动 ──► ① 离屏运行 ──► ② 虚拟输入 ──► ③ 自动截图 ──► ④ AI 读图 ──┐
             ▲                                                        │
             │                                                        ▼
             └── ⑥ 失败回流 ◄── ⑤ 机器断言判定（exit 0/1 + 断言清单）
```

缺哪件，闭环就断在哪一环。**双支撑判定**的含义：⑤ 绿只证明"行为级可用"；
④ 才能发现"实现变了、呈现已不是设计意图"。两者缺一，就回到"测试全绿但东西已经不对"的老路。

### 2.2 静默三层（三层都要，少一层就不算静默）

| 层 | 硬要求 | 常见错误 |
|----|-------|---------|
| 不弹窗 | 窗口/进程**创建期**即隐藏 | 用"事后隐藏" API —— 🟡 对**从未显示过**的窗口，Windows 上事后设置不进任务栏**不生效**；隐藏也必须在构造期给 |
| 不抢焦点 | 全程无 `focus()` / `show()` / 激活窗口 | 为了"让渲染更真"而 `showInactive()` —— 一样会闪现在桌面 |
| 不碰真实数据 | 数据根 → 临时副本；**子进程/CLI 同样遵守** | 只在主进程改了路径，子进程仍写真实数据（用户数据被污染，且不可逆） |

> 判据（见 SKILL E2）：**"人按原有习惯操作，得到的是否还是设计意图"** —— 不是"测试是否还绿"。

### 2.3 ★判定阶梯 L0–L4（视觉那半边要分层，别一步跳到"像素级全等"）

> **编号对齐**：L0（产物存在/尺寸）是最低一档，**有的工程把它并进 L1 而不单独编号**（本 skill 的案例即从 L1 起）。
> 与别的文档对齐时**按"判什么"对齐，不要按编号对齐**。

| 级 | 判什么 | 抓得住 | 抓不住 |
|----|-------|-------|-------|
| **L0** | 产物存在、尺寸符合预期、哈希可记录 | 截图没生成 / 尺寸漂移 | 内容错 |
| **L1** | **有效帧**：非空、非纯色（`unique` / `range` / `variance` 过阈） | 黑屏、白屏、旧帧、空白页 | **画面错位 / 取景漂移** |
| **L2** | **ROI**：关键区域独立统计（工具栏 / 对话框 / 面板矩形） | "整图有效但关键区空白" | 局部内容错、**被浮层遮挡造成的假绿**（见 §5.3） |
| **L3** | **基线差率**：与基线帧逐像素差率 ≤ 阈值（或直接比哈希） | 取景漂移、布局回归 | 基线本身错（**基线必须由人确认过的一次运行产生**） |
| **L4** | **读图结论**：AI 逐项 checklist + 哈希绑定 | 语义级异常（"这个按钮怎么没了"） | **无法自动判定** ⇒ 只能产出证据，**不许做门禁**（SKILL B7） |

- **顺序落地**：先 L1（几乎零成本、判别力立竿见影）→ L2 → L3 → L4。
- L1 的**已知边界**必须写进文档：只做 L1 时"取景漂移"抓不到 —— 别因为"有视觉断言了"就以为画面被守住了。
- L2 与 L1 是**叠加**关系，不是替代：L1 抓"黑屏/白屏/空白页"，L2 抓"整图有效但某关键区空白"。
- L3 的基线更新**必须写明理由**，否则就是把 bug 记成"新常态"。

### 2.4 三个"确定性"层级（别混为一谈）

| 层级 | 含义 | 判据 |
|------|------|------|
| 产物可复现 | 同一状态两次运行产出**同字节**产物 | sha256 一致（最强，先试着做到） |
| 产物等价 | 尺寸 + 统计量落在同一容差带内 | 尺寸相等（**不写死数字**）+ L1 统计量容差 |
| 行为等价 | 同一输入得到同一行为结论 | 断言全绿 + 对外契约（exit code / 输出）逐字不变 |

> 实测教训（🟡）：**别急着把判据弱化**。"哈希一致"曾被判定"按字面不可达"（当时 4 次运行哈希全不同），
> 但**消除非确定性来源**（清掉落在截图范围内的本地时间串）之后**两次运行逐字节相同、字节差 0**。
> ⇒ 顺序是：**先尝试"消除来源"，再考虑"放宽判据"**。

## 3. 分栈配方

### 3.1 Electron（样板实现已实测跑通）

```js
/* ① 离屏窗口：headless 判定要显式传参，不能靠默认值 */
const headless = !!(opts && opts.show === false);
const win = new BrowserWindow({
  width: (opts && opts.width) || 1680,      // ② 固定尺寸 = 取景确定性的前提（别把默认值当固定值）
  height: (opts && opts.height) || 1050,
  show: (opts && opts.show) !== false,      //    headless 时 false（构造期）
  skipTaskbar: headless,                    // 🟡 必须构造期给；事后再设对未显示窗口无效
  webPreferences: {
    backgroundThrottling: !headless,        // 🟡 隐藏窗口若被节流：定时器降频、rAF 暂停 → 旧帧/黑屏
    paintWhenInitiallyHidden: true          // 🟡 未显示也绘制 → capturePage 才读得到真实帧
  }
});
```

  换不受限环境跑，并在文档里显式标注该边界（否则会被误读成"测试挂了"）。

### 3.2 浏览器 / Web（Playwright、Puppeteer 等）

```js
const browser = await chromium.launch({ headless: true });          // ① 天然静默
const ctx = await browser.newContext({
  viewport: { width: 1680, height: 1050 },                          // ② 固定取景
  deviceScaleFactor: 1,                                             //    设备像素比固定，防尺寸漂移
  reducedMotion: 'reduce'                                           //    关动画：减少非确定性
});
const page = await ctx.newPage();
await page.goto(url, { waitUntil: 'networkidle' });
await page.evaluate(() => document.fonts.ready);                    //    字体就绪再截
await page.screenshot({ path: 'smoke-shot.png' });
```

- ② 虚拟输入用框架自带 API（`page.mouse` / `page.keyboard`）——它走的是真实输入管线，比在页面里
  `dispatchEvent` 更"真"；在 Electron 里没有这层时，才退回 `new MouseEvent(...) + dispatchEvent`。
- ③ 数据隔离：给测试起独立的存储目录 / 临时实例，别连用户正在用的库。

### 3.3 其它 GUI（原生窗口 / 游戏引擎 / 自绘）

通用映射（只要满足六件套即可）：
- ① 离屏：引擎的"隐藏窗口 / 后台渲染 / 无头模式"开关；无此能力时退到"虚拟显示器"。
- ② 输入：注入系统级或引擎级输入事件（合成事件即可，只要是**真实事件链**）。
- ③ 截图：引擎自带的帧抓取（比系统截屏稳定、可复现）。
- ⑤ 判定：先做 L1（帧统计）；引擎通常能直接给到像素缓冲，实现比 Electron 更简单。

#### 3.3.1 原生 C++ / 游戏引擎的实测配方

> 完整案例：`cases/AURORA-ENGINE.md`（C++20 / MinGW / Ninja / Vulkan+OpenGL 双后端，引擎 v0.60.0）。
> 下面是可直接照搬的部分。

**① 离屏与产物路径（两个坑，都踩过）**
- 无头模式通常要**同时**关窗口与关设备无关的检查；本工程的 `--headless` 走引擎自带
  `beginOffscreen(w,h)` / `endOffscreen(path)`，比系统截屏可复现得多。
- ⚠️ **`endOffscreen` 类接口一般不建父目录** ⇒ 调用方必须先 `create_directories`。
- ⚠️⚠️ **默认产物路径绝不能是 cwd**：引擎的 cwd 往往被"按仓库相对路径载入内置资产"钉死在仓库根，
  于是"从仓库根跑一次"就把仓库根弄脏，被**根目录白名单守卫**判红 ——
  而且 **`.gitignore` 救不了它**（那条守卫看的是**目录内容**，不看 git）。
  修法是给"产物目录"一个统一出口（默认 `build/artifacts`，环境变量可覆盖）。
  **同一个坑一度在 3 个文件里各写了一遍"跑前移走 / 跑后还原"的绕法** —— 那是"该修源头"的信号。

**② 输入：引擎内注入，但要保证"每帧两步都做"**
- 用引擎自己的按键状态注入（如 `debugSetKey(code, down)`）而非合成系统事件：更快、更确定。
  ⚠️ **能力边界要写明**：它绕过了 OS 事件层，只保证"输入状态 → 行为"这一段。
- **端到端的分界线就在这里**：每帧**先喂控制器**（输入→位移）、**再把结果喂关卡**（位移→判定/触发）。
  只做一步，测到的就是两个单测而不是一条链路。
- 高层动作（"走到 X 旁边"）要**用真实输入实现**（每帧朝向目标 + 按住前进键），
  不许"设个坐标瞬移过去" —— 后者绕开的正是最易断的那一段。

**③ 判定：退出码优先，像素是其中一层**
- 进程退出码 + 结构化 stdout（JSON）是最便宜也最早断言的信号；
  脚本化通关（SKILL B9）比截图**更早**抓到接线断裂。
- 别把"每用例一个进程"当默认：本工程实测进程冷启动 ≈1.9 s，
  445 条逐条跑 **533 s** vs 整包一次跑 **57–80 s** ⇒ 必须**分组**，
  并且**补一条覆盖守卫**（模式写漏 = 静默少跑，与"通过"无法区分）。
- 视觉层照旧只出证据（B7/E4），语义判定不做门禁。

**④ 并发与环境（会造出假失败的两件事）**
- **必须串行**：同进程反复建/毁图形设备可在 loader 层崩且**无任何报错**（本工程实测：
  第二次 `vkCreateSwapchainKHR` 静默退出，而逐条单跑都通过）。
- **别边构建边跑**：负载敏感用例（帧率类）在构建中会红、空闲时绿 ⇒ 门禁前让机器空闲。
- 子进程类断言要**把解释性信息打全**：本工程实测"缺运行时 DLL"给出 `rc=0xC0000135`，
  而断言只打印 "CLI failed" ⇒ 极易被误读成逻辑失败。

## 4. ★取景确定性清单（同一状态必须截出同一画面）

> ⚠️ **顺序要求（实测结论）**：**先禁过渡/动画，再做任何会改变视图的动作。**
> 顺序反了（先复位视图、再禁过渡），复位本身触发的 CSS 过渡会被截图**捕捉到动画中间帧**
> ⇒ 两次运行的哈希**不再一致**（实测 `unique` 462 vs 468）。这条不是"更优雅"，是**正确性**要求。

```markdown
[ ] 0) 【第一步】关闭动画与过渡（禁用 CSS transition / 用 reducedMotion: 'reduce'）
[ ] 1) 窗口/视口尺寸固定 —— 不要把"默认尺寸"当固定尺寸（默认值会随版本变）
[ ] 2) 设备像素比固定（deviceScaleFactor=1；注意系统缩放）
[ ] 3) 显式复位视图（resetView / 还原缩放与平移 / 展开全部树）—— 必须在 0) 之后
[ ] 4) 等待渲染稳定：did-finish-load + ≥2 帧 rAF/布局稳定 + 字体就绪
[ ] 5) 清除非确定性来源：时间戳、随机数、光标/焦点态、网络状态、地理位置、动画帧计数
      ★最隐蔽的一类：**状态栏/角标里的本地时间串**，且它**落在截图范围内**（实测根因）
[ ] 6) 产物路径与命名固定；同时记录分辨率与 sha256
[ ] 7) 验收：同输入**连续**两次运行 → PNG 哈希一致（或 L3 差率断言给一个极小阈值）
```

**别写死数字**：判据优先写成"**两次运行尺寸相等**"而不是"尺寸 == 1424×835" ⇒ 机器无关、零易腐数字
（写死分辨率会随缩放/版本变，且它本身就是一份手写易腐数字）。

**关于"预热效应"**（见 SKILL C3）：改文件后的**第一次**运行可能给出旧值，从第 2 次起才一致；
**机制未查明 [未验证]**。⇒ 判"确定性"时看**连续**结果（例如"连续 N 次哈希一致"），
不要用"改动后的第一次"当判据，也不要据此下"不确定"的结论。

## 5. 视觉断言：阈值单源 + 判别力证明

### 5.1 阈值单源（SKILL B1）

```js
/* thresholds.js —— 唯一阈值来源，禁止各断言各写一套 */
module.exports = Object.freeze({
  validFrame: { minUnique: 8, minRange: 40, minVariance: 4 },  // L1
  roi:        { minUnique: 4, minRange: 24, minVariance: 2 },  // L2
  baseline:   { maxDiffRatio: 0.02, channelTolerance: 8 },     // L3
  sampleCap:  20000                                            // 采样上限，控制耗时
});
```

> 🔴 这些**具体数值是参考实现的选择**，不是定律。用它们**起步**，用实测分布调它们。

### 5.2 判别力证明（SKILL B4）—— 完整做法

**新加任何门禁/断言时，注入一次违规并确认它变红；不红就是没接上或口径太窄。**

| 步骤 | 做什么 | 通过判据 |
|------|--------|---------|
| 1 注入 | 造一个"必须被抓"的坏输入：全黑帧 / 全白帧 / 位移帧 / 关键区涂白 / 真值写错一个数 | — |
| 2 必红 | 跑门禁，**期望 exit 非 0** | 变红了，并**记下报文**（报文能定位到具体条目才算有效） |
| 3 撤销 | 移除注入 | — |
| 4 还原 | **逐字节还原**注入前的文件/数据 | sha256 与注入前**完全一致**（别用"看起来一样"） |
| 5 复绿 | 再跑一次 | exit 0，且输出与注入前相同 |
| 6 留痕 | 把注入方式、期望、实际报文写进交付说明 | 下次改动有据可查 |

**注入 × 期望对照表**：

| 注入 | 期望 | 若没变红说明 |
|------|------|-------------|
| 全黑帧（`unique=1, range=0`） | L1 红 | 阈值太松 / 断言没接到这一级 |
| 全白帧 | L1 红 | 同上 |
| 错位帧（内容平移 N px 后当基线比对） | L3 红 | 差率阈值太宽 / 没做基线比对 |
| 关键区涂白（整图仍有效） | L2 红 | ROI 没独立判定 |
| 把文档里的真值改错一个数 | 真值门禁红 | **正则/归属逻辑没覆盖那种写法**（★真实事故见 §7.1） |

**★真实事故复盘（这是"假守护"的母样本）**：
- 现象：注入"共 99 条视觉断言"（真值 2）后，门禁 **exit 0，没变红**。
- 第一版诊断：以为"归属逻辑缺一个分类分支"。
- **真根因**：断言正则要求**数字紧邻「断言」**，而中文的自然写法是「**2 条视觉断言**」
  —— 类别词夹在数字与「断言」之间 ⇒ **压根匹配不到** ⇒ 把这个数写进任何文档都**不进判定**。
- 修法：放宽正则允许内联类别词，并优先用它归类；重做判别力证明 ⇒ **exit 1**，报文定位到具体文件行。
- **可迁移教训**：① **"结论对、根因错"是常态**，修法必须对着真根因；
  ② 跳过一次判别力证明，就会把一个**永不生效的门禁**当成守护。

### 5.3 L2 的两个真实缝隙（写下来，别假装覆盖了）

1. **矩形取不到 vs 内容空白是两条分支**：真机注入 `#main *{visibility:hidden}`（连容器自身一起隐藏）走的是
   "**取不到可见矩形**"分支；而"**区域存在但内容空白**"是另一条分支，只有单测覆盖。
   ⇒ 要真机覆盖第二条，用**覆盖式遮挡**（在容器上盖一层不透明 `::after`，容器自身仍在、矩形照旧可测）。
2. **被浮层遮挡会造成假绿**：导图未渲染、同时有可见浮层占住该区域时，ROI 统计量仍然"有效" ⇒ L2 仍绿。
   修它要按 z 序或"排除区"把图层与浮层分开测 —— 属 L3 范畴。
3. **刻意清空的元素不要放进 ROI**：为取景确定性清掉的状态栏，若又被 ROI 测，则**永远判红**。
   ⇒ 被清空的区域要从 ROI 清单里显式排除，并写明理由。

## 6. 真值口径与单源（SKILL B1–B3）

### 6.1 运行时计数 vs 源码正则

| 口径 | 怎么取 | 准确度 | 适用 |
|------|--------|--------|------|
| **运行时**（首选） | `require(模块).长度` / 运行器回报"实际跑了多少条" | **精确**（就是实际执行数） | 断言清单是**纯数据模块**，或运行器能显式回报条数时 |
| 源码正则 | 正则扫源码数"字面量" | **近似**（结构上会失真） | 断言是**脚本**（require 会执行它）时的兜底 |

**静态口径已知失真形态**（说清才有资格用它）：
- 断言写进**循环**：源码 1 个 vs 运行时 N 条；
- 写进**数组再 `forEach`**：源码 0 个；
- 一张表里多行、模板拼接、条件分支生成 …… 都会让"源码数字"与"实际条数"脱钩。
- 类别词位置也会让正则**扫不到**：`45 冒烟断言`（类别词在数字**之后**）与 `2 条视觉断言`（夹在中间）
  都是中文自然写法，**要求"数字紧邻『断言』"的正则一个都匹配不到**。

### 6.2 真值必须可派生、可逐字比对

- 真值（分辨率、条数、哈希、比例）**全部从产物里读**，由脚本生成基线文件，其它文档只引用。
- 「采不到真值 = 红」在代码里的形状：`if (truth == null) { 打印原因; exit 1 }`，
  **不允许**落到"跳过这条比对，然后打印一致"的分支上。
- **单源判据**：grep 一个易腐数字，若命中 ≥ 2 份**手写**副本 ⇒ 已经在漂移路上。

### 6.3 ★手写数字漂移的真实事故

- 一处文档写着"…45 冒烟断言全通过）"——类别词在数字**之后**，旧正则扫不到 ⇒
  这个数字**从 45 漂到 115 而从未被门禁管过**。
- 它是**被"放宽正则"顺带抓出来的**，不是被专门检查发现的 ⇒ 见 SKILL B5：
  **放宽匹配口径 = 扩大覆盖范围 ⇒ 必须重跑全量**（否则不会发现它顺手抓出的既存缺陷）。
- 连带规矩：解释"某个易腐数字曾经是错的"时，**不要把那一串数字抄进文档** ——
  解释性注释本身会被正则匹配 ⇒ 又变红。**改措辞，别弱化判定。**

### 6.4 通道序：不要假设像素缓冲的通道顺序

🟢 Electron 的 `toBitmap()` 类型声明写明：`The specific format is platform-dependent.`
⇒ **没有可依赖的答案，而"依赖通道身份"本身就是缺陷**。
**修法**：让统计量与通道序**无关** ——
- `unique` 只用**去重计数**（任何通道排列都是双射，计数不变）；
- `mean` / `variance` / `range` 改用**三通道均值**，不要用加权亮度（`0.299R+0.587G+0.114B`
  对 R/B 互换**敏感**：实测旧公式 `126.090 → 133.490`，新口径**完全相同**）。

## 7. 门禁接入（阶段 5）

1. **断言计数进真值**：脚本从断言源数出真值并**生成**基线文档；其它文档只引用，不手写。
2. **采不到真值 = 红**：受限环境导致子进程起不来时，脚本必须 `exit 1` 并打印
   "无法取得真值，门禁不能自称已校验"，**绝不能跳过该条比对然后打印"一致"**。
3. **挂进主验证链**：视觉断言步排在冒烟**之后**（先行为、后画面），失败即整链红。
   - 更省的做法：**让视觉断言跑在同一次冒烟引导内、截图之后**（复用同一帧）
     ⇒ 天然满足顺序语义，且**零额外启动、零额外墙钟**（真启动 GUI 常占全链 80%，再加一次不可接受）。
4. **门禁自身要有判别力证明**（§5.2）：故意让声明数与真值不符一次，确认门禁抓到差异行，再撤销。
5. **门禁的能力边界写清楚**：它抓的是**损坏的结果**，不是**违规的动作**；也只抓"可机械判定"的部分。
6. **新增/修改门禁的连带清单**（SKILL D3）：
   新产物要同批处理 —— 白名单 / `.gitignore` / 真值 / 生成物 / 登记表 / 索引；
   改门禁的**分类/归属逻辑**时，别忘"新数字是否真的被扫到"（否则就是又加了一个手写易腐数字）。

### 7.1 门禁正则的"假守护"模式（见到就要怀疑）

| 模式 | 症状 | 怎么查 |
|------|------|--------|
| 要求过窄 | 中文自然写法匹配不到（类别词夹在中间 / 在数字之后 / 全角数字 / 带千分位 / **markdown 强调**） | 用**人真会写的 5 种写法**各写一遍，看是否都被扫到；**并把"合法写法必须被识别"写成断言**（否则改个排版就静默停用守卫） |
| 分类缺支 | 新类别数字没有归属分支 ⇒ 不进判定 | 打印"被扫到的条目清单"，肉眼确认新条目**在清单里** |
| **适用条件自证** | 判定的**适用条件由被检查方自己决定**：例"只在行内有数字时才跑这条比对" ⇒ 把那处内容删掉或改写成不被识别的形式，守卫就被**静默关掉**，而它照样打印"全部通过" | 问一句"**这条判定凭什么决定要不要跑？**"；若答案取自被检查对象的内容 ⇒ 改设计：与声明无关的检查**无条件跑**，且守卫自己要**在受检范围内**（"谁守守门人"要有答案） |
| 判定被绕过 | 早退、`continue`、`if (!x) return ok` 之类把"采不到"当"通过" | 注入"采不到"场景，看是否红 |
| 永久红 | 绑定了每次都变的东西（哈希、时间戳） | 连跑两次，若必红 ⇒ 是**假红**，不是守护 |

> **"要求过窄"会静默停用守卫**（🟡 实测，来自一次真实事故）：把声明的条数写成 `（**N 条判定**）`（加粗），
> 而匹配口径要求 `（` 后紧跟数字 ⇒ **匹配不上 ⇒ 整条比对被悄悄绕过，门禁照样全绿**。
> ⇒ 两条互补对策：① 匹配口径要容忍**人真会写的写法**（强调、空格、全角）；② **把"合法写法必须被识别"写成断言**。
> **标记重复**是同族第三种形态（实测踩过三次：两个 `①` 数出偏大的数 · `⑥` 与 `⑥b` 撞计数 ·
> "解释这条判定的注释"里又枚举了一遍标记）⇒ 计数类判定的标记必须唯一，**续写/举例要用不计入的写法**。

## 8. ★门禁可单测化（`require.main` 守卫 + 抽纯函数）

**问题形状**：门禁脚本在文件末尾**无条件执行** `main()`。
⇒ `require('该门禁')` 会**直接跑主流程** ⇒ 它**无法被单测引入** ⇒ **判定逻辑长期没有单测**
⇒ §5.2 那个空转的门禁因此**活了下来**（只靠一次手动的判别力证明才发现）。

**修法（三步，可操作）**：

1. **抽纯函数**：把判定逻辑抽成**无 IO 的纯函数**，例如把"一行文本里的事实声明解析"抽成
   `parseClaims(line)` —— 它只吃字符串、只返回结构；`scan()` 改为调用它。
   ⚠️ 抽的时候**四类计数的匹配顺序与归类规则要逐字保留**（否则改变行为）。
2. **加守卫**：末尾 `main();` 改成 `if (require.main === module) main();`。
3. **导出**：`module.exports = { parseClaims, scan, ... }`，供单测直接引用。

**实测收益**（🟡，单机）：`require` 耗时 **7189 ms → 12 ms**，而直接以 CLI 方式运行该门禁脚本
的行为**逐字不变**（exit 0、输出相同）。⇒ 判据：**`require` 该门禁应当零副作用、耗时≈0**。

**改动安全**：这种改动值得**先断言再改** —— 例如脚本先校验"文件结尾恰好是一处裸露的 `main();`"
（`main();` 出现次数 == 1），不满足就**拒绝改动**。比 `node -e "..."` 更好的做法是**写成文件**
（见 §10.5：本轮反复栽在 shell 引号转义上；写成文件则内容**逐字**就是你要的样子，没有转义层）。

## 9. ★恢复手段：从 Agent 运行时的会话日志恢复被覆盖的文件

**适用**：一个**有逐次工具调用日志**的 Agent 运行时；只维护一份副本、且没有版本控制 / 没有提交时，文件被人覆盖了。
**这不是备份**，是**事故恢复**；但实测能逐字重建。

> ⚠️ **本节 = 机制 + 一个 harness 的实例，不是通用格式规范。**
> 下文的具体路径与 zstd 帧结构是**某一个 harness 当时的布局**（它的 home 形如 `~/.<harness>`），仅作**形状示例**；
> 换 harness **必须重新摸**。你要找的是同一类东西：**"每次工具调用 + 完整载荷"的逐次记录**（`write` 带全文、`edit` 带前后串）。


### 9.1 找对文件（别找错地方）

> ⚠️ 下表路径是**某一个 harness 的布局**（它的 home 形如 `~/.<harness>`），只作形状示例；换 harness 请找等价物。
> **这里刻意不写那个 harness 的真名与真路径** —— 对读者无用，且会让"可迁移的机制层"绑上一个具体工具。

| 路径（形状示例） | 是什么 | 能不能当恢复源 |
|------|--------|---------------|
| `~/.<harness>/sessions/<工作区slug>/<会话id>/session.*.jsonl.zstd` | **会话日志本体**，含每次工具调用的完整载荷 | ✅ **是恢复源** |
| `~/.<harness>/storages/*/sessions/*.json` | **派生投影**：标题 / 时间线 / 统计 / 待办 | ❌ **不是** —— 它**不含任何工具调用的路径与内容**；搜关键词会命中**对话文本**，极易被误判成"里面有载荷" |

### 9.2 格式与解码（关键坑）

- 日志是**一串互相独立的 zstd frame 首尾相接**，**每帧恰好一条 JSON 行**。
- ⚠️ **Node 内置 `zlib.zstdDecompressSync` 只解第一帧就结束** ⇒ 必须自己走帧头逐帧解：

```
Magic(0xFD2FB528)
 → Frame_Header_Descriptor
 → (可选) Window_Descriptor
 → (可选) Dictionary_ID
 → (可选) Frame_Content_Size
 → 3 字节 block header 循环
 → (可选) 4 字节 checksum   （是否存在的位在 Frame_Header_Descriptor 里）
```

### 9.3 字段路径

- `tool/call` → `data.name` + `data.arguments`（**JSON 字符串**，需再 `JSON.parse` 一层）
  - `write` = `{ file_path, content }` —— **完整原文**
  - `edit`  = `{ file_path, old_string, new_string }`
- `tool/result` → `data.message.content[0].text` —— `read` 的结果**内嵌整份文件文本**（可作交叉验证）
- 重放策略：按时间序把 `write` 直接落盘、把 `edit` 的 `old_string → new_string` 逐个套用，
  得到"会话视角下该文件应有的内容"，再与磁盘现状比。

### 9.4 无损性佐证与边界

- 🟡 把日志里对工作区副本的 `write.content` 与磁盘现文件逐字节比对，**20 个精确命中**；
  肇事会话 1816 条记录里 `compaction/summary` = **0**（未被摘要裁剪）。
- ⚠️ **边界**：一旦发生**压缩/摘要**（`compaction/summary` 记录非 0），早期 `write` 载荷可能已被裁掉 ⇒
  恢复只能覆盖**摘要之后**的部分。**先数 `compaction/summary` 的条数再承诺能恢复多少。**
- ⚠️ **顺序**：`edit` 的重放**必须按时间序**，且 `old_string` 要能匹配上（匹配不上说明中间还有别的写入）。
- ⚠️ 会话日志是**工作区相关**的（按工作区 slug 分目录）；跨工作区的同名文件不要混用。

### 9.5 更根本的对策

- **只维护一份副本**（SKILL C5）：两份副本 + 反复单向同步会**必然**丢工作；
  🟡 实测镜像同步丢过**两次**，根因是**设置**（同步会回退"直接写在主副本上"的改动），不是某一次操作。
- 备份要**只读**、不参与回归；同步脚本会保留源时间戳 ⇒ **mtime 本身就是可读的覆盖指纹**。

## 10. ★编码与落盘卫生（SKILL E5 的展开）

### 10.1 临时产物区也可能被编码门禁扫

⇒ **临时物也不能带 BOM**。真实工程里 **`.review/`（工作产物区）不豁免编码扫描**，
只有部分门禁（真值/登记）豁免 ⇒ 往那儿写带 BOM 的文件，验证**第 1 步就红**。

### 10.2 同一个约束的四面（一轮里踩了 4 次）

| # | 形状 | 后果 |
|---|------|------|
| 1 | **多**一个 BOM：`Set-Content -Encoding utf8` / `Out-File` 默认会写 BOM | 编码门禁判红 |
| 2 | **少**一个 BOM：`.ps1` 无 BOM ⇒ 旧版 PowerShell 按 **ANSI/GBK** 读 | 含中文的脚本**乱码 + 语法错**，一次都没跑起来 |
| 3 | 在**模板字符串里**放反引号 | 提前终止模板串 ⇒ 语法错 |
| 4 | 把**字符数当字节数**（PowerShell 的 `.Length` 是字符数；中文 1 字 ≈ 3 字节） | 体积记成 1/3、百分比结论全错（曾把 `211,820 B` 记成 `149,422`、把 `−63.9%` 记成 `−51.4%`，并据此得出"比例在 51%–64% 浮动"的**错误结论**） |

### 10.3 怎么做

- **不要用 PowerShell 写 UTF-8 文档/脚本**；用 **node**：
  `fs.writeFileSync(p, s, 'utf8')` —— UTF-8 无 BOM 是 JS 的正确编码，无歧义。
- 交付前**逐文件验 BOM**：`fs.readFileSync(p)[0] === 0xEF` 或看前三字节是否 `EF BB BF`。
- 体积口径写清**"字节 / 字符"**；用 `Buffer.byteLength(s, 'utf8')`。
- 改门禁/做脚本改动：**写成文件**而不是 `node -e "..."` / 一行 PowerShell
  （少一层 shell 引号 + 编码转换，内容逐字可控）。
- 发现方式（值得学）：与**更早的独立实测**交叉比对 —— 新记录与旧记录几乎逐字节吻合时，
  说明**新测量错了、旧记录是对的**。

| `vision-record.example.json` | 读图产物样例（checklist + verdict + sha256 绑定） | ⚠️ 其中 `smokeCount` / `resolution` 等字段**是手写数字样例**，正是 SKILL B3 要消灭的东西 ⇒ 真实产物里这些字段必须**从产物读**（本项目做法：从取景记录 JSON 机械取，并校验与当前 PNG 的 sha256 一致，不一致就**拒绝写入**） |

**L4 记录的正确语义**（真实工程裁决，值得照抄）：
- 语义是"**本次迭代的读图证据**"，**不是跨迭代比对键**：哈希绑的是**本次截图**，图一换记录即过期。
  ⇒ **不能**把它当"与上次一致"的判据。
- **不进门禁**：阶梯自己写着 L4"无法自动判定 → 靠纪律 + 人复核"，给这样的层级加门禁是自相矛盾的。
- 但它**必须能拦住"记了异常还报全绿"**：`verdict != ok` 时至少要**显式在交付说明里点名**。
- 落点是**工作产物区**（不进产品文档体系）；⚠️ 该区仍受**编码门禁**约束（§10.1）。

## 13. 失败回流 runbook（现象 → 定位 → 处置）

| 现象 | 定位路径 | 处置 |
|------|---------|------|
| L1 红（有效帧判定失败） | 先看 PNG：黑屏 → 绘制/GPU 开关；白屏 → 页面未渲染完；旧帧 → 后台节流/时序 | 修完重跑；把根因补成断言 |
| L2 红（ROI 空白） | 在图上量该区域矩形，核对是"矩形取不到"还是"区域空白" | 修布局或改 ROI 定义；ROI 定义也要单源；被清空的区域要排除 |
| L3 红（差率超限） | 看差异区域 → 布局漂移还是内容变化 | 内容变化 → 修；取景变化 → 补 §4 的确定性；**基线更新必须写明理由** |
| 截图生成失败 | `capturePage` 抛错 → 窗口是否已销毁/尺寸非法 | **报告失败，不静默跳过**（采不到真值 = 红） |
| 同输入两次哈希不同 | 先按 §4 逐项查（第一步查**是否先禁了过渡**，再查时间戳类来源） | 顺序错 → 调顺序；有来源 → 清来源；都没有 → 用 L1 容差并**写明理由** |
| 门禁报"真值缺失" | 采集真值的子进程在受限环境起不来（管道 stdio / 命名管道被拒） | 那不是通过：按"采不到 = 红"处理，或换不受限环境跑，并在文档里标注边界 |
| 门禁该红没红 | 按 §7.1 四种"假守护"逐一查；**先查正则口径，再查分类分支** | 放宽口径 → **重跑全量**；补分类分支；去掉"把采不到当通过"的早退 |
| 门禁该绿却红 | 是不是绑定了每次都变的东西（哈希/时间戳） | 那是**假红**：改语义（证据而非判据）或改绑定对象 |
| 窗口仍弹在桌面 | 隐藏参数没走构造期 / 有 `show()` 兜底 | 改成构造期参数；删掉兜底 |
| 真实数据被改动 | 只隔离了主进程 | 数据根走环境变量、子进程继承；补一条"隔离生效"断言 |
| 验证之间结果飘 | ① 是否**并发写工程**（§12 实测）；② 是否**改动后第一次跑**（预热效应） | 串行化；判据改成"**连续** N 次一致"；不要用单次结果下结论 |
| 脚本/文档乱码、门禁判红 | 按 §10 四个面查：BOM 多/少、反引号、字节/字符口径 | 改用 node 写；口径写清；交付前验 BOM |
| 文件被覆盖 | 先确认有无版本控制；无则按 §9 从会话日志恢复 | 恢复后**建立只读备份**并停止同步脚本 |

## 14. 反模式清单（见到就改）

- ❌ **把"跑过了"当结论**：没有画面/数据证据的"改好了"。
- ❌ **只做 L1 就宣布"有视觉断言了"**：取景漂移照旧无人守。
- ❌ **第一版就拿基线全等比对**：噪声导致的假红会让人很快把断言关掉；先 L1/L2，再 L3。
- ❌ **阈值散落各处**：迟早互相矛盾。
- ❌ **跳过采集失败**：把"没校验"打印成"一致"。
- ❌ **让门禁自己证明自己**：新门禁必须做一次**注入式**判别力验证。
- ❌ **门禁只靠手测**：判定逻辑没有单测 ⇒ 空转的门禁会活下来（§8）。
- ❌ **读图不落盘**：下一轮重复劳动，且无法对比回归。
- ❌ **把 L4/主观层做成门禁**：它自己声明"不可自动判定"，加门禁自相矛盾且制造必然假红。
- ❌ **绑哈希当跨迭代键**：图一换必红，只能手工消红 ⇒ 等于给验证链加一个永远红的步骤。
- ❌ **把方法论抄进每个工程**：方法论只有一份（本 skill）；工程里只留**应用记录与偏离说明**。
- ❌ **两处维护同一份事实**：多副本必然静默漂移；解释历史错误时抄数字 ⇒ 又撞门禁。
- ❌ **放宽口径后只跑一个用例**：扩大覆盖却不重跑全量 = 白改。
- ❌ **用 PowerShell 写 UTF-8 文档/脚本**：BOM/GBK/反引号/字节-字符四个坑等着。
- ❌ **用同步脚本维护第二份副本**：必然丢工作；要备份就备份，别双向"保持一致"。
- ❌ **验证期间并发改工程**：假失败，且症状分散到不同步骤，极难归因。
- ❌ **拿"改动后第一次跑"当判据**：预热效应会让它给出旧值（机制未查明）。
- ❌ **凭感觉优化验证链**：先量、先归因，再动手；预算只当"止涨线"。
- ❌ **把环境限制当工程缺陷**（或反之）：换环境再跑一遍再下结论。

## 15. 边界与未验证项（诚实标注）

**本方法能保证的**：AI 迭代时**不打扰用户**、结论**有可复现证据**、门禁**真的会红**、
易腐事实**不会静默漂移**、被覆盖的工作**有恢复路径**。
**它不能保证的**：
- **"改对了"** —— "实现变了、呈现还与设计意图一致吗"仍需人判定，机械化不了。
- **语义正确性** —— 视觉断言能抓取景漂移/黑屏白屏/关键区空白，**抓不到语义错误**（文案写反、按钮点错功能）。
- **没有验证链的项目** —— 无自动断言可分层、可加速。

**明确标为未验证 / 未查明的**：
1. **[未验证] 预热效应的机制**：现象是"改文件后第一次跑给出旧值、第 2 次起一致"，
   **根因未查明**。本 skill **不提供解释**（SKILL C3、§4）。对策只是"看连续结果"。
2. **[未验证] 抗锯齿/字体栈是否会造成 ±1 抖动**：清掉时间戳后实测逐字节相同，
   但换机/换字体/换缩放后**是否仍能逐字节复现**未验证 ⇒ 判据仍应保留"差率容差"这条退路。
3. **[未验证] 某些环境变量/路径因素对 GUI 启动的影响**：真实工程里"Electron 只能从某个盘符路径启动"
   的现象根因未分辨（盘符 / 路径长度 / 沙箱三者未定）。**诊断不解除阻塞时主动放弃，比硬猜更好。**
4. **[未验证] L2 的"区域存在但内容空白"只在单测层覆盖**（真机注入只走了另一条分支）；见 §5.3。
