# 可验证工程（AI 迭代版）

> **定位（先读）**：本 skill 是**跨工程、跨技术栈的通用方法论**，用于指导 AI 开发/迭代**任意**项目，**不绑定特定工程**。
> 文中出现的工程名、数字、路径与命令都是**案例与证据**（供理解与排序），不是判据、不是要求 ——
> 换栈、换场景时按你的现场重新判断（标 🔴 / [未验证] 者尤其如此）；`cases/`、`checklists/`、`templates/`
> 只是参考实现，把某个工程的具体选择当成「用本方法就得这么做」是最常见的误读。

> 判定标准用**周期成本类**指标；每条「改好了」都由可复现证据支撑；每个门禁先证明它会红。
> **证据强度（怎么读本文）**：★ = 由**真实事故**驱动的条目；标 **[未验证]** 的是"现象已实测、机制未查明"；
> 完整的强度表（🟢 源码级 / 🟡 单机实测 / 🔴 参考实现的选择）与"未验证项"清单见 `REFERENCE.md` §12 与 §15。
> 本文是**决策层**（读完再动手）：机制与实测证据见 `REFERENCE.md`，真实工程（Electron 笔记应用）的案例见
> `cases/VISION-LOOP.md`，可拷走的模板见 `templates/`；原 `silent-verify-loop` 已被吸收（见 `README.md`）。
> 周期成本的**判定与优化模式**（五段模型、三个定义陷阱、五个症状、七项优化模式、反模式、两小时自检清单、AI 自诊失误类型、盲区）见同目录 `cost-methodology.md`。

**用**：AI 生成且由 AI 长期迭代、有验证链的工程；给新项目接入自动验证/回归闭环；结论只有 exit code、没人看过画面；
验证越跑越慢；带界面的工程验证时会弹到用户桌面；工程按模块/包组织，要建 per-module 测试入口与并行可跑性。
**不用**：好坏无法机械判定的主观质量；纯人肉验收且不改 headless；
一次性脚本或寿命 < 1 个月；目标只是"省 token / 降费"（那不是本 skill 的目标，见 A1）。

> **如果只来得及做 5 件事，做这 5 件**（本文 A–F 有几十条，全做等于不做；下面这 5 条能拿到大部分收益）：
> ① **一个入口、一条命令、exit code 说话**（A4）—— 没有它，其余全部不可度量；
> ② **失败必须非 0 退出**；「跳过」必须与「通过」可区分（A5/B2）—— 否则得到的是假绿；
> ③ **采不到真值 = 红**，不许静默降级（A5）；
> ④ **每次运行打印逐段耗时**，否则某一步悄悄变慢没人知道（A4）；
> ⑤ **新门禁先注入一次违规、确认它变红、再撤销**（B4）—— 没红过的门禁不算门禁。
> 这 5 条做完，再按 **F 表的阶段 −1 → 0 → 1** 往下走；其余条目按现场问题逐条取用。


## A. 目标与度量

**A1 判定标准必须是周期成本类**｜用验证耗时与可用性、可增量断言占比、追溯成本、回滚能力；**不用** token、费用、模型评分。
每个动作要能回答「**它让哪一段变快了多少**」（定位/理解/改/验证/记录）。｜反例：把**手段**（省 token）或**输出**
（回答质量）当目标 ⇒ 只优化了"读"而瓶颈在"验"（实测，2026-09：写路径一次只回 156 字节级，验证每次迭代却要重付
~154 s；该链此后已降到数十秒 ⇒ **数字只看量级，不看绝对值**）。

**A2 先量再优化：计时 + 逐段耗时表 + 预算**｜逐段记秒、算 `单段耗时÷断言数`，先打占比最高那段（>50%）；
预算写进 **runner 而非文档**（让"悄悄涨回去"变红），语义是**止涨线**不是性能目标（"慢"≠"坏"）。
"跑不了"先分环境还是能力：换环境再跑，能跑 ⇒ 修测量；仍跑不了 ⇒ 修对象、排最前。｜反例：凭感觉优化；
把受限环境的**假失败**当成"验证链坏了"去修工程。

**A3 分层 + 写明「何时必跑」**｜单测/集成/冒烟/数据/文档/规则各答一个问题；定义"改动面 → 必跑哪几层"，交付清单强制全链。
｜**当快链自己长到分钟级时**，两级会不够用 —— 需要「**档位阶梯 + 机选**」（形态与三条纪律：保守升级 / 映射表即判据 / 工具只建议，见 `cost-methodology.md` §3 模式 3 的进阶段）。
｜反例：`&&` 长链的真正杀手是**人们因此跳过验证**；只有"单对象/整棵树"两档粒度 ⇒ 为取 3 个对象跑全量。

**A6 per-module 验证最小集：一条命令构建并测试一个模块**｜模块级迭代不该付全链成本：每个模块有**独立的测试可执行**
+ 统一 label（`ctest -L <m>` 秒回）+ **自己的预算桶**；全链不变，模块迭代只跑自己那一桶。
｜落地：测试按模块归类（归类规则要可机械复现 —— 按测试文件 include 的第一方模块定；跨模块/端到端进 integration 桶）；
模块级预算单独设桶，"某模块悄悄变慢"才有人红（A2/A4 的模块级延伸）。｜反例：N 个测试文件挤一个二进制
⇒ 改一个模块要链全部测试文件、跑全部用例，模块级迭代成本 = 全链成本 ⇒ 并行开发时两个改造者互相等待。
｜**粒度判据**（什么算一个模块、边界怎么切）见 `architecture-for-ai` I1/I3；本条只给"每个模块都要有秒回的验证入口"。

**A4 一个入口跑完整链，并打印逐段耗时**｜一条命令 exit 0/1，**每次运行都打印逐段耗时表**。
｜**否则没人发现某一步悄悄变慢**（实测，2026-09 两个时点：冒烟段 40.5→52.6 s，占全链 78–81%；没有任何门禁会为"变慢"变红）。
｜**表必须覆盖整链的全部步骤**：任何重要步骤（量级 ≥ 全链 10%）漏出表外 = 该步**无人守**——实测（单机，2026-10）：某工程最大的一段（占全链约 46%）**不在表里、也没有预算**，从 374 s 涨到 633 s（≈1.7×）**没有任何机制变红**。⇒ 新增一个重要步骤必须**同时进表 + 进预算**；「表外存在大段」本身就是缺陷（与 B8「守卫自己要受检」同族）。
｜**输出的最后一行必须是机器可读的单行结论**（从与结果文件**同一个真值**生成，例：`结论: FAIL — 失败分组: a, b`）——「只看输出尾部 N 行」是已实测的误判源：全链 102 条里 3 个分组失败被 tail 截断、只剩逐桶耗时表与「合计 OK」，差点把红当绿引用（2026-10，AuroraEngine）。

**A5 采不到真值 = 红**｜取不到真值必须 `exit 1` 并打印"无法取得真值，门禁不能自称已校验"；代码里把"采不到"与
"采到了但一致"分成两个分支。｜反例：静默 `skip` 再打印"一致"——**跳过伪装成一致的门禁等于不存在**。

## B. 门禁与真值

**B1 单源：阈值 / 计数 / 真值各只一份**｜易腐数字（阈值、尺寸、用例数、断言数）**由脚本从真值生成**到一份基线文件，
其它文档只引用。｜反例：多副本会**静默**漂移。判据：grep 一个数字命中 ≥2 份手写副本 ⇒ 已在漂移路上。
｜**权威副本**（生成 + 逐字校验 + 副本上限的完整做法）在 `docs-for-ai` C2；本条只给验证侧的真值口径。

**B2 计数口径：运行时 > 静态正则**｜能 `require().length` 或由运行器**回报条数**就别数源码。
｜正则数的是"源码里的**字面量**"而非"跑了多少条"：写进循环即 1 vs N、写进数组再 `forEach` 即 0。｜反例：拿静态近似当真值。
｜★**更糟的用法：拿正则去判断「行为」，而不是判断「数量」。** 实测（QQ 桥接，2026-10）：运行器用
`/process\.exit\(1\)|process\.exitCode\s*=\s*[1-9]/` 判断「这个测试失败时会不会以非 0 退出」，据此把脚本分成
"门禁 / 探针"。结果漏判两类：`node:test` 脚本（失败时 runner 自己置 `exitCode=1`，源码里没有字面量）与
`process.exitCode = failed > 0 ? 1 : 0`（等号右边不是字面量）。于是**一半"探针"其实本来就会正常报错**，
它们跑红了只标 WARN，整链照样打印 PASS —— **判据错比没有判据更坏**。
⇒ 规则：**某个脚本失败时响不响，是它作者的责任，运行器不猜**。默认一律当门禁（红就是红），
只把**显式声明为诊断工具**的排除（前缀或清单），且排除项必须每次开跑打印、写进结论行。

**B3 数字不手写：可派生的生成 + 逐字比对**｜分辨率/条数/哈希一律从产物读。｜★事故：手写的冒烟断言数
**从 45 漂到 115 无人察觉**，因为它落在门禁正则扫不到的写法里（类别词在数字**之后**）。｜反例：把"当时的数字"抄进文档当契约。

**B4 ★判别力证明：新门禁先注入一次违规、确认变红，再撤销**｜没红过的不算门禁。做法：注入坏数据/坏帧 → **必红**
（记报文）→ 撤销 → **逐字节还原**（比哈希）→ 复绿，结果写进交付说明。★事故：注入后 **exit 0 没变红** —— 查明断言正则
要求**数字紧邻「断言」**，而中文自然写法是「**2 条视觉断言**」（类别词夹在中间）⇒ **门禁一直在空转**。
⚠️ **结论对、根因错是常态**：诊断说"缺分类分支"、真根因是"正则太窄"，**修法必须对着真根因**。
｜**证明库会腐烂**（证明脚本通常**不进验证链**）：生产代码一演进，注入锚点就悄悄对不上——此时证明**不是红而是"跑不起来"**，而"跑不起来"和"没跑"在盘上长得一样 ⇒ 判别力**悄悄消失**。对策：① 锚点从单一真源**现场拼出**（见 B13）；② 给证明库配一条**保鲜守卫**：扫全部证明脚本的锚点是否仍出现在其声明的靶文件里，找不到即红（有工程实测一次扫出 **6 份**腐烂证明——锚点随生产代码演进失效、此前无人察觉）；③ 「跑起来报锚点不存在」的证明视为**损坏**，同批修复。

⚠️ **「永远不可能变红」的三种形态**（都只有靠注入才会暴露，实测同一天各踩中一次）：
① **判据口径比被测对象窄** —— 上面的静态正则；或断言要求"退出码恰好是字面量 1"，而脚本返回别的非 0 值。
② **断言跑在异步副作用落地之前** —— `void (async () => …)()` 这类 fire-and-forget，测试在它完成前就断言
"没有发生"，于是**恒真**。实测：一条"退役时不许归档同伴会话"的断言，因为没等一拍，`calls.archived`
永远是空数组 —— 这条测试**原本永远不可能失败**，直到注入回归才现形。对策：断言前显式等待，或让被测行为返回可 await 的 promise。
③ **跨 realm 的对象比较** —— 被测对象来自 `vm.createContext` / 子进程 / worker 时，其 Array/Object 原型与
主 realm 不同，`assert.deepEqual`（strict）连原型一起比 ⇒ `['a']` 与 `['a']` **假红**。实测踩中一次。
对策：按值比（`JSON.stringify`）或逐元素比，不要用严格深比。
⇒ 所以**判别力证明不是"补一道手续"**：②③ 的表现都是"跑起来是绿的"，不做注入就永远不知道它没测。

**B4 的分级：别把几十条门禁都注入一遍**｜门禁从几条长到几十条后，"每条都注入一次"会直接劝退所有人，
规则随之失效。按**损害可逆性**分层：
· **必须证明**：锁住不可逆损害的（数据丢失、越权发送、协议破裂、记忆丢失）—— 这类应当很少；
· **可以标 `unproven`**：其余允许只声明、不证明，但必须进**债务清单**（记录条数与理由），
  且清单设上限——超了就不许再加新门禁，先把债还掉。
｜反例：不分级 ⇒ 要么"全部证明"（不可行），要么"全部不证明"（规则形同虚设），实际总会滑到后者。

**B5 ★放宽匹配口径后必须重跑全量**｜放宽正则会**扩大覆盖**并暴露既存缺陷（上一条放宽后**顺带抓出**"45 已漂到 115"
那处从未被管的数字）。｜反例：改完只跑一个用例。｜连带：解释"某易腐数字曾经是错的"时**不要把那串数字抄进文档**
（解释性注释本身会被匹配 ⇒ 又红）——**改措辞，别弱化判定**。

**B6 ★门禁本身必须可单测：`require.main` 守卫 + 抽纯函数**｜★事故：某门禁**末尾无条件执行 `main()`** ⇒ `require` 它会
跑主流程 ⇒ **无法被单测引入** ⇒ **判定逻辑长期没有单测**，B4 那个空转的门禁因此**活了下来**。修法：纯逻辑抽成
`parseClaims(line)` 这类**无 IO 纯函数**，末尾改 `if (require.main === module) main();`，再 `module.exports`。
**实测**：`require` **7189 ms → 12 ms**，CLI 行为**逐字不变**。判据：`require` 该门禁应**零副作用、耗时≈0**。

**B7 明说"不可自动判定"的那一级不要做成门禁**｜阶梯里自己标注"抓不住/靠人复核"的层级（如"呈现是否还是设计意图"）
只产出**证据**。｜反例：给它加门禁 ⇒ 自相矛盾且制造**必然假红**（实测：读图结论绑每次都会变的截图哈希 ⇒ 下轮必红）。
｜**权威副本**（"什么只配做人工清单"的一般原则）在 `architecture-for-ai` F3；本条只是它在视觉阶梯上的落点。

**B8 边界写进文档**｜门禁抓的是**损坏的结果**而非**违规的动作**，只抓可机械判定的部分；已知边界要写明
（例：只做"有效帧"判定时**取景漂移抓不到**）。
｜并且**适用条件不得由被检查方自己决定**：若"这条判定要不要跑"取决于被检查对象的内容（例："行内有数字才比对"），
那么把那处内容删掉或改写一下，就能把守卫**静默关掉** —— 与声明无关的检查必须**无条件跑**，且守卫自己要**在受检范围内**。

**B9 ★跨模块链路必须"真跑一遍"：脚本化通关测试**｜"每个模块各有单测"与"这条链路走得通"是两件事：
后者跨了输入→控制→判定→状态→产出，任一处接线断了，**每个模块自己的单测都是绿的**。
做法：写一份**声明式脚本**（`frames/key/mouse/walkTo/talk/interact/choose/assert`），由测试入口**逐帧喂真实输入**、
在**真实加载的数据**上执行，断言结局；任一条断言不成立 ⇒ 进程 rc≠0 ⇒ 可当门禁用。
｜反例（本项目的真实缺口）：移动只在**空演示世界**里按过键；对话在真实关卡里测过却靠**瞬移 + 直接调 API**
（`pos = npc.pos + 1; talk()`）——于是"**走过去**并按 E"这条真实链路**从来没有被验证过**。

**B10 ★端到端判据的样本不要落在对称轴上**｜★实测：朝向公式写错符号（`atan2(dx,-dz)` 应为 `atan2(-dx,-dz)`），
而它在目标位于**正前/正后**（`dx==0`）时与正确式**完全一致** ⇒ 第一份脚本（NPC 恰在 -Z 轴）**一直是绿的**，
错误被"目标刚好在轴上"这个抽样掩盖；把 NPC 放到 `(6,0,0)` 才暴露（人朝反方向一路走出 30 m）。
｜**判据**：测运动/朝向/映射时，样本要**斜着放**、要覆盖**各象限**；同理"只在原点上成立"的判据等于没判。

**B11 ★断言写成对的（前 false → 后 true）**｜★实测：`interacted: {id}` 断言查"该物还在不在列表里"，
而被消费的对象**从不从列表移除**（只置 `consumed`）⇒ 该断言**恒判红**；且它从未被任何脚本用过，缺陷潜伏。
修正后仍不够：只看"交互后为 true"在"**它本来就已 true**"时假绿 ⇒ 判据要能表达 **`expect:false`（交互前）**，
两步都断。｜**判据**：任何"状态被本步改变"的断言，都要能写**改变前**那一半。

**B12 ★脚本化测试要给被测世界一份独立实例，并显式置位初始态**｜★实测：脚本真的把玩家走遍关卡、惊动了 NPC
（追逐/巡逻真的发生）⇒ 世界状态变了；与内建检查**共用同一个会话**时，那些检查的前提（"第一个 NPC 在数据原位"
"最近的说话对象就是它"）不再成立，于是它们**因与被测脚本无关的原因**变红 —— 得到的是**互相污染**，不是"更省"。
同理：被驱动的控制器在前面的检查里**已经被走过**，它的位置是**残留值**；不显式 `setPosition(出生点)`，
脚本第一句"从出生点出发"就是假的。｜**判据**：任何"共享可变世界"的测试都要问一句"**它改了别人赖以成立的前提吗**"。

**B13 ★多处表达的事实要有"跨副本逐字相等"的门禁；且证明的锚点别写字面量**｜同一事实在多处表达时（版本号：
`Version.h` / `CMakeLists.txt` / `vcpkg.json`；命令数：CLI / MCP / 文档；阈值：代码 / 文档），
运行期自检**只看得到运行期来源** ⇒ 构建/清单侧的副本可以**静默落后**。
★实测：引擎版本已到 0.58.0，而根 `CMakeLists.txt` 与 `vcpkg.json` 仍写 **0.56.0**，**漂了 2–3 版而没有任何门禁会红**。
门禁判据用**逐字相等**（别用"能解析成合法 SemVer"这种弱判据 —— 它抓不住"旧版本号"，而旧版本号正是缺陷的形状）。
⚠️ **连带**：为它写判别力证明时，**注入锚点不要写字面量**（写死 `VERSION 0.59.0` 的证明会**随每次升版腐烂**：
下次升版后它报的是"锚点不存在"而不再是"门禁有牙"，判别力**悄悄消失**）⇒ 锚点**从单一真源现场拼出**
（读 `kEngineVersion` 再拼 `"VERSION " + v`）。
｜**跨副本清单还要包含面向人的「当前版本 vX」声明句**（README 首屏那类）——它在文档层、运行期自检看不到，但文档门禁会核对；升版动作清单必须显式列出它。实测：升版只同步了 5 处、漏改 README 一句 ⇒ 文档门禁红 ⇒ **连带三个分组一起红**（2026-10，AuroraEngine）。

**B14 ★同一缺陷在 N 处各写一遍绕法 = 该修源头**｜★实测：某引擎的自检产物**默认落在 cwd**，
而它的 cwd 被"按仓库相对路径载入内置资产"钉死在仓库根 ⇒ 跑一次就污染仓库根、被根目录守卫判红。
于是**3 个文件各写了一遍"跑前移走 / 跑后按情况还原"的沙箱手法**（第 3 处还换了种写法）。
每处都"小心处理"看起来是尽责，实际是把一个缺陷**复制成了三份**（而且第四处仍会踩）。
｜**判据**：同一段"绕开某个行为"的代码出现**第二次**，就停下来问"能不能让它**不再发生**"。
修法 = 给那个行为一个统一出口（产物目录 + 环境变量可覆盖），改完三处绕法**全删** ——
这才是减债；"每处都记得小心"只是把债分散了，而且**没有任何守卫会提醒第四个人**。

**B15 ★真起进程的门禁/验证链必须前置「产物新鲜度」检查**｜凡门禁或 runner 会**真起 exe/进程**，
跑之前必须机械核对「受检源文件的 mtime ≤ 产物 mtime」，任一源文件比二进制新 ⇒ **响亮红**并列出
清单（A5 同族：拿旧产物跑出的红绿，在盘上与真跑长得一样 ⇒ 静默）。⚠️ 连**全链 runner** 也要查
——「链很全」不等于「链跑在新代码上」。｜★事故：收口期直接跑门禁报「NPC avatar 位移 0.000」
假红，重编后 **5.243 m**、代码零改动（2026-10，AuroraEngine）；同一工程的全链 runner 全文
没有一条构建命令。｜**边界（如实）**：mtime 口径抓的是「改了源没重编」；checkout 会刷新 mtime
⇒ 语义必须写成「**工作树比二进制新**」且报文可行动（提示重编命令）；「内容没变只动了 mtime」
不是缺陷，不算误报。
**B16 ★「事件 → 消费」型链路的判据必须写成对计数相等**｜正向判据（"播放/调用次数 > 0"）抓不住
**「补一条看起来对的调用」型缺陷**：往已接好的链路里再补一次发布/调用，消费计数**翻倍**，
而正向判据**只会更绿**。判据 = **事件数 == 消费数**（漏发与重复发两头都咬），并用注入
（重复发一次）证明它真的会红。｜★事故：在动画回调里补一次 `publish`（上游 emit 才是唯一真源、
早已发布）⇒ 同一次运行 **13 个事件播了 26 次**（脚步声重叠加倍），"次数 > 0"毫无反应
（2026-10，AuroraEngine）。

**B17 ★发现式收集必须配计数对账**｜按 glob / 目录收集测试文件时，"少了文件"是**静默**失效：
目录里删一个文件、或文件没进 glob 模式，测试照样全绿 —— 与"没跑"在盘上长得一样（A5 同族）。
｜落地：测试入口启动时**回报实际条数**（运行期统计，别数源码 —— B2），注册表/基线记录期望值，
门禁逐单元对账，**不等即红**；期望值入注册表而非文档（B1 单源）。｜同类事故：手写的冒烟断言数
**从 45 漂到 115 无人察觉**（B3）—— 计数对账就是把"写死的数字"从文档搬进门禁的两侧。
｜反例：只收集不计数 ⇒ 漏文件无声无息；计数写在文档里 ⇒ 又一份会漂移的副本。

**B18 判别力证明与模块同生命周期**｜证明脚本按模块归档（`proofs/<模块>/`），模块迁移时证明**随模块走** ——
否则模块挪了目录、证明的锚点还指向旧路径，"跑不起来"与"没跑"再次无法区分（B4 已实测证明库会腐烂）。
｜落地：证明目录结构与源码模块结构同构；把"证明存在且锚点仍可解析"纳入模块登记面的对账（与 B4 的保鲜守卫同思路）。
｜反例：所有证明平铺一个目录 ⇒ 模块挪走后 proof 留在原地、锚点腐烂，下一个人按文档找不到证明。

## C. 确定性

**C1 ★先禁过渡/动画，再做任何改变视图的动作**｜实测：顺序反了（先复位视图、后禁过渡），复位本身触发的 CSS 过渡
会被截图**捕捉到动画中间帧** ⇒ 两次运行**哈希不再一致**。｜反例：把"复位"当第一步，再奇怪哈希为何不稳。

**C2 清掉非确定性来源，再谈"哈希一致"**｜固定尺寸（**别把默认值当固定值**）·设备像素比·复位视图·**清时间戳/随机数/
焦点态**·等稳定（≥2 帧 rAF + 字体就绪）·禁过渡·产物路径固定。★事故：状态栏写了本地时间串且**落在截图范围内** ⇒
每次都不同；**清掉后两次运行逐字节相同**（字节差 0）⇒ **"消除非确定性来源"的收益常大于"放宽判据"**（曾判定"哈希一致
不可达"，被这一步推翻）。完整清单见 `REFERENCE.md`。

**C3 ★"改文件后第一次跑"可能给出不同结果（预热效应）**｜实测：改完后**第一次**截图等于**改动前**的旧值，从**第 2 次**
起稳定一致。⚠️ **机制未查明（未验证）**，不要编解释。｜对策：看**连续**结果，不拿"改动后的第一次"当判据。

**C4 ★验证期间不要并发写工程**｜★实测：**有并发写入时 3 次全链 2 次失败**且**症状分散在不同步骤**；**停止并发写入后
连续 7 次全绿**；内存 6.5–7.1 GB 未变 ⇒ **排除内存压力**。｜落地：验证与写工程**串行**；有并行会话先确认谁在写。
｜**若要更硬**（多 agent / 多进程常态并行的工程）：可把这条纪律**机制化**为三层 —— ① **互斥窗口**（验证开始时申请
全局单例租约；stale 可接管、不留死锁；旁路必须**响亮声明**「本次无保护」）；② **任务期判据哈希**（跑链开始冻结、
结束复算，漂移 ⇒ 本次证据**作废**而不是重跑）；③ **判据变更串行通道**（改判据前要求全停 + 明示，改完重钉基线才
放行）。有工程按此三层落地过（实例指针见 `cases/`）。
｜反例：把偶发失败归因于被测对象，而**每一步单独跑都通过**时还不查环境。
｜**多批次共用工作树是多 agent 并行的必然后果**：判据哈希失配 ⇒ 本次 verdict 记 `invalidated`；判读规范 = **失败清单为空 ⇒ 代码面绿**，`invalidated` 只剥夺「本次证据作收口交付物」的资格——既不等于失败，也不许当成功交付。实测：102/102 条全过但 invalidated（2026-10，AuroraEngine）。

**C5 ★只维护一份副本**｜两份副本 + 反复单向同步会**必然**丢工作：★实测镜像同步**丢过两次**（同步会**回退直接写在
主副本上的改动**，**根因是设置**而非某一次操作）。｜判据：任何"同步脚本"都会让另一份的工作静默消失；备份只读、
不参与回归。｜恢复手段见 `REFERENCE.md`（可从 **Agent 运行时的会话日志**恢复）。

**C6 并行可跑性判定：同 label 的测试不得共享可变 fixture**｜多个模块的测试要能同时跑（并行迭代的前提，
模块化见 `architecture-for-ai` I5）；同 label/同批的测试若共享同一份**可变** fixture（同一临时目录、同一份工程数据、
同一个全局单例），并行时互相污染 —— 症状是"单独跑全绿、并行随机红"，且最难归因。
｜落地：每个测试实例一份独立临时作用域（数据根重定向 + 显式初始态，见 B12/E1/E2）；
并行前先证明无共享写面（判据：同一份盘上路径被两个测试写 ⇒ 不合格）。
｜反例：两个模块的测试都写 `tmp/fixture.json` ⇒ 并行时后者覆盖前者，红的那份指向与被改代码无关的原因。

## D. 文档与规则

**D1 文档即契约，且要被门禁扫**｜文档里的数字/通道/行为若不能被子门禁核对就是**腐坏源**：AI 会**照着腐坏的文档做**。
｜落地：文档事实进真值比对；文档登记/命名/家目录也要有门禁。｜反例：只声明不核对 ⇒ 漂了也没人知道。
｜**文档体系本身**（分层、准入、生成、交接）用 `docs-for-ai`；本条只给验证视角：「文档事实也要进真值比对」。

**D2 规则放在"动作现场"**｜AI **不会**主动读规则清单 ⇒ 规则要写在**它动手的地方**（脚本注释、那段代码正上方、
命令用法里）。｜反例：规则只活在 `RULES.md` 的一张表里。
｜**权威副本**在 `architecture-for-ai` E2（信息架构视角）；本条只给验证侧的观察"AI 不会主动读规则清单"。

**D3 改动即连带清单**｜新增产物要**同批**处理：白名单 / `.gitignore` / 真值 / 生成物 / 登记表 / 索引。
｜★事故：新增产物漏进白名单 ⇒ 被"家目录门禁"判乱放。｜判据：每个"新增文件"动作都能当场列出这 6 处是否要改。

**D4 别把没验过的写成经验**｜不确定的显式标注**「未验证」**并写清怎么才能验证。｜推理代替验证，是所有"文档说能用、
实际不生效"缺陷的共同母体。｜反例：把"我推断"写成"实测"；**"结论对、根因错"也要如实记**。

## E. 静默、画面证据与编码卫生

**E1 静默三层，缺一层就不算静默**｜①**不弹窗**（**构造期**即隐藏，非事后 API）·②**不抢焦点**（无 `focus()`/`show()` 兜底）·
③**不碰真实数据**（数据根重定向到临时副本）。⚠️ ③ 最常被忽略：窗口藏好了却把测试写进用户真实目录——一样是打扰，且**不可逆**。

**E2 测试不碰真实数据，判据不是"测试是否还绿"**｜子进程/CLI **同样**遵守重定向（只隔离主进程 ⇒ 子进程仍写真实数据）。
判据：**人按原有习惯操作，得到的是否还是设计意图**。落地：数据根走**环境变量**让子进程继承，并补一条"隔离生效"断言。

**E3 静默 ≠ 目的，证据才是**｜离屏只是**前提**；每条"改好了"都要有可复现证据（截图 + 结构化结论 + 哈希绑定）。
**双支撑**：机器断言绿只证明"行为级可用"，**读图**才能发现"实现变了、呈现已不是设计意图"。
｜反例：截图只写不读（**写 ≠ 读**）；用推理代替读图。

**E4 分层判定，别一步跳到"像素级全等"**｜产物存在/尺寸 → 有效帧 → 关键区域 ROI → 基线差率 → 读图结论，每级写明
**抓得住/抓不住**。｜反例：第一版就全等比对 ⇒ **噪声导致的假红会让人很快把断言关掉**。L0–L4 表见 `REFERENCE.md`。

**E5 ★编码卫生：临时产物区也可能被编码门禁扫 ⇒ 临时物也不能带 BOM**｜★同一类坑一轮里**踩了 4 次**：①**多**一个 BOM
（`Set-Content -Encoding utf8`/`Out-File` 会写）⇒ 门禁判红；②**少**一个 BOM ⇒ 旧版 PowerShell 按 **ANSI/GBK** 读 `.ps1`
⇒ 含中文脚本**乱码 + 语法错**；③**模板字符串里**放反引号 ⇒ 提前终止、语法错；④把**字符数当字节数**（中文 1 字 ≈ 3 字节
⇒ 体积与百分比全错）。｜怎么做：**不用 PowerShell 写 UTF-8 文档/脚本**，用 **node**（`fs.writeFileSync(p,s,'utf8')`）；
口径写明"字节/字符"；改门禁用**文件**而非 `node -e`（少一层引号转义）。

## F. 落地顺序

> **多数工程的起点不是阶段 0，而是阶段 −1。** 接手一个「已经有几十个测试脚本」的工程时，
> 那些脚本通常**还不是断言**：它们只 `console.log`，或失败时压根不以非 0 退出，或跑起来要靠手改环境变量。
> 直接跳到「0 基线」会得到一句"全部通过"，而那句话什么都没证明。

| 阶段 | 做什么 | 验收（不满足不算完成） |
|------|--------|----------------------|
| **−1 存量改造**（多数工程的真实起点） | 把已有脚本变成**能响的**断言：① 失败是否 `exit` 非 0；② 是否有 `require.main`/`import.meta` 守卫；③ 有没有一条命令把它们串起来；④ 它们连的外部地址是不是**本机真实值**（不是历史默认值） | 产出三张表：**能当门禁的 / 只是打印的 / 跑不起来（缺依赖或缺环境）**；且每一条"跑不起来"都写明缺什么 |
| 0 基线 | 跑起现有断言，记录现状与**逐段耗时表** | 一条命令 exit 0/1；有耗时表与预算 |
| 1 目标与分层 | 定周期成本类指标 + 分层与必跑集合 | 每个动作能回答"让哪段变快了多少" |
| 2 静默三层 | 不弹窗/不抢焦点/不碰真实数据（含子进程） | 隐藏态截图仍读到**有效帧**；真实数据零写入 |
| 3 取景确定性 | 固定尺寸/复位/禁过渡/清非确定性/等稳定 | **先禁过渡再改视图**；同输入**连续**两次哈希一致（或差率<阈值） |
| 4 程序化断言 | L1 有效帧 → L2 ROI →（必要时）L3 基线 | **注入坏帧/坏数据 ⇒ 对应断言必红** |
| 5 读图留痕 | 结论落盘 + 哈希绑定 | 可被下轮引用比对；不制造必然假红 |
| 6 门禁接入 | 计数进真值 + 门禁可单测 + 判别力证明 | 声明数≠真值即红；**采不到真值 = 红**；`require` 门禁零副作用 |

**−1 的两条实测补充**（QQ 桥接，2026-10）：
· 外部地址写死历史默认值是**最常见的"从未跑通"**：8 个脚本都写 `DSH_BASE_URL || http://127.0.0.1:3080`，
  而本机实际在另一个端口 ⇒ 它们每次都把"连不上"当成测试结果。**在 runner 里统一注入真实地址**，
  8 个脚本一行都不用改，也不会各自漂移成不同的兜底值。
· 历史聚合器（自己再跑一圈脚本的那种 `test-audit.mjs`）要与新 runner **二选一**：两个都留会重复执行、
  耗时翻倍，还让失败归因变模糊。移出后同一条链 36.9s → 17.5s。
