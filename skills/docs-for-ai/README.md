# docs-for-ai

> **定位（先读）**：本 skill 是**跨工程、跨技术栈的通用方法论**，用于指导 AI 开发/迭代**任意**项目，**不绑定特定工程**。
> 文中出现的工程名、数字、路径与命令都是**案例与证据**（供理解与排序），不是判据、不是要求 ——
> 换栈、换场景时按你的现场重新判断（标 🔴 / [未验证] 者尤其如此）；`cases/`、`checklists/`、`templates/`
> 只是参考实现，把某个工程的具体选择当成「用本方法就得这么做」是最常见的误读。

给**由 AI 生成、由 AI 长期维护与迭代**的工程设计文档体系。
判据只有一条：**一个零上下文的 AI，能否凭文档独立接手**（读懂为什么、知道按什么改、知道怎么验）。

## 文件

| 文件 | 作用 |
|------|------|
| `SKILL.md` | **决策层**（先读这份）：判据、分层与准入、单源与生成、三类内容分治、交接面、写作约定、文档门禁、反面清单 |
| `REFERENCE.md` | **机制层**：13 条文档判定的实现骨架、模板（元信息块/文档骨架/决策记录行/工作目录 README/接手 N 步）、成本与实测数据 |
| `checklists/新建项目-文档架构自检.md` | 从零建一套：该有哪些文档、各自只写什么、门禁怎么挂 |
| `checklists/既有项目-文档架构改造评估.md` | 只读评估：现有文档体系的病灶、优先级、以及"改完凭什么说变好了" |
| `templates/docs-gates.js` | **可整份拷走的起步门禁**（6 个 check）：登记与家门（四行元信息）· 层取值表 · 悬挂登记 · 归档横幅（递归）· 工作目录状态 · 登记表生成与一致性。自带 `--selftest`：临时工程里逐种注入，**必红项全红、负例保持绿**，条数由脚本现场统计（**不写死**） |
| `cases/文档体系六轮演进.md` | 真实工程（Electron 笔记应用 + CLI）的六轮演进：**20 余处**缺陷的修法、以及**我自己踩的坑** |

## 证据强度：统一四档词表

三份 skill 用**同一套四档**给结论标强度。**本段在三份 README 里内容相同**（改一处要同批改三处 —— 否则就是这几个 skill 自己禁止的"第二份会漂移的副本"）。

| 记号 | 名字 | 含义 | 换环境会怎样 |
|---|---|---|---|
| 🟢 | 源码级 / 平台契约 | 能从源码、类型声明或官方文档直接读到，是硬约束 | 仍成立，除非上游改契约 |
| 🟡 | 单机实测 | 在一台机器 / 一个版本上跑出来，并留有记录 | **应重测**再引用 |
| 🔴 | 参考实现的选择 | 设计取舍，**不是定律**；条件变了可能反转 | 换栈 / 换场景**应重新判断**，最该被推翻 |
| ⬜ | 未验证 | 只有现象或推断；机制未查明，或只是"我认为应该这样" | **不可作为依据**，只能当待验假设 |

**附加标记**（与四档正交）：**⚠️[未验证的处方]** = "我认为该这么做，但在来源工程里**从未落地**"。

**怎么用**：读到一条结论 → 先按上表定位它的档 → 🟢🟡 可当依据（🟡 换机要重测）；🔴 要问"我的条件是不是也满足"；⬜ 只能当假设。
**本 skill 自己的记号怎么对应到四档** → 见下一节。

## 与相邻 skill 的分工

| 你面对的问题 | 用哪个 |
|------|--------|
| 代码/数据该怎么摆：单源实现、分层、并发写、原子写、回滚 | `architecture-for-ai` |
| 怎么验：验证链分层、预算、真值口径、门禁机制、判别力证明 | `testing-for-ai` |
| 文档该怎么分层、准入、防漂移、交接 | `docs-for-ai` |

**依赖顺序（不是并列）**：结构前提（`architecture-for-ai`）→ 可机械取证（`testing-for-ai`）→ 交接面（`docs-for-ai`）。
后两者都以前者成立为前提 —— 这也是 `testing-for-ai` 该在"零测试项目"上拒绝出场的原因。
三者共用同一条元规则：**能被机械判定的，就不要靠自觉**。

## 该走哪份清单

| 你的工程状态 | 走哪份 | 从哪开始 |
|------|--------|---------|
| 还没有文档，或只有一份刚写的入口文档 | `checklists/新建项目-文档架构自检.md` | 阶段 0「先定判据」（不写文件） |
| **已经有**过期文档 / 散落草稿 / 漂移过的清单 | `checklists/既有项目-文档架构改造评估.md` | 阶段 0「取证」（只读，先立基线） |
| 有腐坏物、又打算长期做下去（**最常见**） | **两份拼起来**：既有清单的**阶段 0 取证** → 新建清单的**阶段 1–5 重建** | 顺序是"先取证 → 再重建 → 用同一把尺子验收"，**不要跳过取证** |

## 一句话版本

> 文档不是写给人看的记录，而是 **AI 与工程之间的交接面**：
> 让每一份事实只有一处权威、让易腐的东西自己生成、让历史退出活跃视野、
> 让规则出现在动手的地方、让"什么还没做完"一眼可见 ——
> 于是即便新来的 AI 不读完全部文档，也不会把工程写坏。
