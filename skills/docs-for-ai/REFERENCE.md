# REFERENCE — 机制、判定实现与模板

> `SKILL.md` 是决策层（该不该这么摆）；本文是**机制层**：怎么把它做成能跑的判定、可拷走的模板、以及实测数据。
> 所有数字与事故都来自一个真实工程（Electron 笔记应用 + CLI + MCP，AI 迭代数月，文档体系被修了六轮）。
> 行业无关：判定语言是任意脚本语言，模板是纯文本。

---

## 1. 它解决什么：三个失败模式

| 失败模式 | 症状 | 根因 |
|---------|------|------|
| **作者视角**：文档写了不少，但没人读 | 新会话仍不知道下一步做什么；文档越长，读的人越少 | 文档按"作者想说什么"组织，而不是按"接手者要做什么" |
| **时间视角**：同一事实多处表达，然后漂移 | 数字对不上、清单不一致、规则两处说法不同，**且漂移掉的常是最要命的那条** | 手写副本；没有机械校验；"同步"靠人记得 |
| **接手视角**：状态不可见 | 看不出"什么还没做完""上次验证绿没绿""这份旧稿还算不算数" | 状态只活在作者脑里或长文档里；历史与现状混放 |

**推论（本 skill 的全部结论都由它推出）**：文档体系的每一条设计，都要能回答"**它降低了上面哪个失败的哪一部分**"。
回答不了的，就是净成本。

## 2. 核心模型

### 2.1 三种归宿与判定树

任何一份新内容，先落到三类之一（**判定只看两个问题**：它会不会被改？它是否承载"当前事实"？）：

```
新内容
├─ 承载当前事实、会被持续修订 → 【活跃文档】  改 + 被门禁扫 + 进真值口径 + 有唯一权威
├─ 承载历史、不再修订         → 【归档族】    只增不改 + 不进真值扫描 + 必须带历史横幅
└─ 草稿/分析/汇报/探针/临时数据 → 【工作产物区】可随时整目录删 + 不进扫描 + 不登记 + 必须有出口
```

**放不下就说明分类没想清楚**：既想留着又想随时删，是"没想清楚"的典型，一律先放工作产物区。

### 2.2 单源三件套

**权威副本（1 处）→ 生成（不手写）→ 逐字校验（不一致即红）**。

- 权威副本可以是：文档头部的元信息、代码里的注册表、真值脚本现场算出来的值。
- 生成物**必须能被逐字重算** ⇒ 它**不能含时间/随机/当天状态**；要展示这类信息就写**指针**，值由命令现场打印。
  （实测踩过：给生成物加了"生成日期"与"上次结果值"，它立刻失去被逐字校验的能力。）
- 校验失败时的输出要给**差异行号 + 重生成命令**。
- **变体：声明式单源**（当"真值"能从**可数的实现标记**现场数出来时，比整份生成更省）：
  **手写的权威副本只放一个数**（如「（N 条判定）」这种声明）→ **真值从实现现场数出**（数实现里的 `①…⑬` 标记，**去重**）→ 两者比对，不等即红；
  逐条清单**不写进文档**，改为一条命令**现场打印**（`--judgments` 这类）。
  ⚠️ 两条前提：① **标记必须唯一**（同形标记重复会让"数一遍"得到偏大的数）；② **适用条件不得由被检查方自己决定**
  —— 否则"把那个数字改写一下"（甚至只是加粗）就能**静默停用**整条比对。这两条都是门禁设计问题，
  权威与实测见 `testing-for-ai` 的 `REFERENCE.md` §7.1「适用条件自证」。**实测出处：一次真实事故（两个 `①` 数出偏大的数；条数被加粗后守卫静默失效）。**

### 2.3 交接面五件

| 件 | 作用 | 判据 |
|----|------|------|
| **第一屏 + 接手 N 步** | 新会话从"有哪些文档"升级到"先读哪份、下一步做什么" | `接手` 一词出现在第一屏（实测：97 行 → 26 行；**行号会漂移，量它别记它**） |
| **"在飞"小节**（进行中）与 **"未发布段"**（已完成未发版）分离 | 只读一边就会误判现状 | 两条各有唯一权威，且第一屏可达 |
| **上次验证留痕** | 接手者知道基线绿不绿 | 一条命令能回答；丢了显示"无记录"，不判红 |
| **指针校验** | 防止"在飞"指向已删目录（死指针） | 门禁扫指针，目录不存在即红 |
| **接手演练（可重复）** | 唯一不依赖作者假设的验收 | 零上下文会话 + 四问 + 如实报告卡点 + 卡点必须转化 |

### 2.4 门禁分级与判别力

- **能机械判定** → 门禁（挂进一条命令，违反即红）；**不能且损害高** → 铁律（少数，显式标注靠自觉）；**不能且损害低** → 约定。
- **推论**：一条已被机械化的规则应当**退出铁律名单**；铁律多不是严谨，是门禁缺失。
- **判别力证明**：注入违规 → 必须变红（记报文）→ 撤销 → **逐字节还原**（比哈希）→ 复绿。
  撤销后要**再跑一次**看是否复绿 —— 这一步实测抓到过"门禁崩溃而不是判红"的真 bug。

## 3. 文档判定的实现骨架（13 条，逐条：防什么 / 怎么判 / 边界）

> 这张清单是本 skill 最可直接照抄的部分。每条都对应过真实缺陷。判定只读文本，**应当毫秒级**。
> **本节是这条清单的唯一权威**（别处只给分类与指针 —— 复述一次就会漂移，本 skill 第一版就栽在这上面）。
>
> **口径（数条数前先读）**：这里的"**13 条**"是**本 skill 的合并口径** —— 把源工程分挂在两个门禁上的判定合成了一张表
> （其中 11 条属文档登记门禁、2 条属真值/生成物门禁）。**源工程自己的规则文件与架构文档就为此打过架（12 vs 13）** ——
> 所以别把"13"当通用数字，它是**本文的口径**。你的工程该上几条？按"**已经有现成违规**的那条先上"来挑（见 SKILL G6）。
>
> **不想从零写**：`templates/docs-gates.js` 是**起步模板**，已实现**登记与家门（元信息块四行齐备）· 层取值表 ·
> 悬挂登记 · 归档横幅（递归）· 工作目录状态 · 登记表的生成 + 一致性校验**，共 **6 个 check**；改顶部 `CFG` 一段即可用。
> 该模板自带 `node docs-gates.js --selftest`：临时工程里**逐种注入**，**必红项必须全红、负例必须保持绿**，
> **条数与结果都由脚本现场统计打印** —— 本文刻意不写死条数（写死过一次就会漂；写入当日实测为"必红 8 / 负例 2"）。
> 判别力可**随时复跑**（跑完自动删除临时工程；探针不落盘）。
> **两条硬要求写进了判定本身**：① **采不到真值 = 红**（文件读不出来不许静默跳过）；② **检查模式与生成模式一致**（`--write` 在同样输入上也拒绝）。
> 其余判定照下面各条加，加一条就照 §2.4 做一次注入证明。
> **非 JS 工程**：模板只用了三个语言无关的原语（读前 N 行 + 正则抓 `键: 值` / 排序渲染 markdown 表 /
> `exists` + 逐字比对），用任何自带文件 API 的语言重写约 150 行即可，**判定逻辑不要改**。

### 3.1 登记与家门

- **防**：表外文档、散落文档、工程根与顶层目录乱放（"同一事实多副本"的入口）。
- **怎么判**：① 每份受管文档**必须**在文件前 25 行内有元信息块（见 §4.1），且**四行齐备**
  （缺行 = `partial`，与"没有块"分开报 —— 报错要说准，别把"缺两行"说成"没有块"）；
  ② 工程根只允许"入口文档 + 配置文件"白名单；③ 顶层目录只允许既有那批；④ 登记表里声明的文档必须都在磁盘上（悬挂登记）；
  ⑤ 元信息块里的 `层` 必须在**取值表**内（`入口/治理/契约/设计/记录/归档`，权威在 `SKILL.md` B3）。
  ⚠️ ⑤ **必须真正实现**：只把取值表用于排序（非法值排到末尾）等于没判 —— 模板的 `checkLayers()` 就是为这条补的。
- **实现骨架**：
  ```js
  const HEAD = ['SKILL.md', 'README.md', 'CHANGELOG.md'];        // 根白名单里的文档
  const ROOT_FILES = [...];  const TOP_DIRS = [...];             // 其余根文件与顶层目录
  const LAYERS = ['入口', '治理', '契约', '设计', '记录', '归档'];  // 值不在表内 ⇒ 配置错误
  // 收集：docs/*.md + HEAD；判定：有元信息块且层合法 → ok；工作产物区的目录 → 需 README（见 §3.7）
  ```
- **边界**：只判"有没有家、在不在白名单"，**判不了**"这份东西该不该存在""内容是否与别的文档重复"。

### 3.2 悬挂登记

- **防**：登记表里写了、磁盘上删了（读者去找一个不存在的东西）。
- **怎么判**：登记表的每个路径都要 `exists`；归档族用**前缀行**放行（`docs/archive/*`、`docs/changelog/*`），不需要逐份登记。

### 3.3 归档与主文件不重复

- **防**：滚动归档后，同一段历史同时躺在主文件与归档目录（两边都不进真值扫描 ⇒ 恰好落在盲区）。
- **怎么判**：遍历归档文件，若主文件里仍存在对应标题段 ⇒ 红。

### 3.4 交接死指针

- **防**：接手者按"在飞"条目去找证据，而目录已被删/改名。
- **怎么判**：取"在飞"小节（从标题到下一个二级标题），用 `\.review\/[^`\s]+` 抓反引号里的指针，逐个 `exists`；
  **跳过占位写法**（含 `<` `>` `*` 的）—— 否则会抓到规则文字里的 `.review/<目录>`（实测第一版就抓到了自己）。
- **实现骨架**：
  ```js
  for (const m of line.matchAll(/`(\.review\/[^`\s]+)`/g)) {
    const ref = m[1].replace(/[\\/]+$/, '');
    if (/[<>*]/.test(ref)) continue;          // 占位符，不是真指针
    if (!fs.existsSync(path.join(root, ref))) problems.push({ kind: 'handover', rel: line + ':' + no, ... });
  }
  ```

### 3.5 新代码未入档

- **防**：新增模块/脚本不进架构文档 ⇒ 接手者不知道它存在。
- **怎么判**：`src/*.js`、`cli/commands/*.js`、`scripts/*.js`（顶层）每个文件名**必须**在架构文档里出现过。
- **边界**：`tests/`、`scripts/smoke/`、`scripts/vision/` 等**豁免**（目录级说明 + 自描述命名，逐文件登记只增维护面）。

### 3.6 归档缺横幅

- **防**：grep 到旧稿，把它当现状。
- **怎么判**：归档目录下每个 `.md`/`.html` 的**前 8 行**必须含标记（`勿作现状引用|历史快照|历史归档|ARCHIVED`）。
  只有"开头"的横幅才起作用 ⇒ 只查前几行。

### 3.7 工作目录无状态

- **防**：误删在飞工作 / 把陈旧分析当现状。
- **怎么判**：工作产物区的**直接子目录**必须有 `README.md`；散落单文件豁免；
  **工具自建目录豁免**（如按需创建的读图记录目录，用途在别处已说明）。

### 3.8 导航不可达

- **防**：文档登了记，但第一屏（AI 的第一份必读文档）里找不到它 ⇒ 等于没有这份文档。
- **怎么判**：登记表里的每份文档，其路径或文件名必须出现在第一屏文档里（**集合级**判据，措辞不限）。
- **边界**：只查第一屏那一份；人类门面文档（README）若已降级为"指针 + 少数几份"，**不纳入**该判定。

### 3.9 契约缺字段

- **防**：契约自述"只读本文档就能写出解析器"，而它漏了字段 ⇒ 照着契约改就会漏。
- **怎么判**：用一个**显式常量**列出应有字段（人的判断），并让它**双向自查**：
  ① 标为"被校验"的字段必须能在代码里找到（否则清单过期）；② 标为"仅契约"的字段**不应**在代码校验里出现（否则分类漂移）；
  ③ 全部字段必须在契约文档里出现。
- **为什么用常量而不是正则抽源码**："哪些字段属于契约"是人的判断；但常量必须能被源码**证伪**。

### 3.10 章节断号

- **防**：有人删/挪过章节而没人复查（读者去找一个不存在的节）。
- **怎么判**：同一层级内编号连续；顶级允许从 0 或 1 起；允许无编号章节；**跳过生成物**（结构由生成器决定）；
  **跳过 fenced code block 与引用块里的行** —— 文档里的模板/示例本身含 `## …` 这类行，会被误当成标题
  （本 skill 的 `REFERENCE.md` §4 就是现成一例：那四行在 ``` 围栏里）。

### 3.11 登记表与元信息一致

- **防**：手改登记表 / 改了文档元信息却忘了重生成 —— 登记表是唯一权威，它一旦漂移，整条准入链失效。
- **怎么判**：用与生成器**同一个渲染函数**重算，与磁盘逐字比对（容忍标记注释后的空行）；不一致报差异行 + 重生成命令。
- **自适应门**：**只有工程里至少一份文档带元信息时**才判 —— 否则老工程与单测 fixture 会被无差别判红；
  而"块被删光"这种情况会由 3.1 的"文档无元信息"逐份报出，不会静默放过。

### 3.12 生成物未过期（跨文件一致性）

- **防**：改了源忘了重生成 ⇒ 文档开始骗人。
- **怎么判**：对每份生成物，调用它的渲染函数重算并与磁盘逐字比对。生成物必须**确定性**（见 2.2）。

### 3.13 体量/行数与"未来版本号"类易腐声明

- **防**：把**会自己变化的现状**写成精确数字（"当前体积 230 KB""主文件 2200 行""（v0.16.6 起）"）——
  它会被读成现状，且没有任何东西会在它过期时提醒。
- **怎么判**：
  - `N KB/MB` → **无锚即红**（锚 = 同行带版本号 / 快照 / 原记 / 当时 / 曾）。
  - `N 行`（三位数以上）→ **仅在"断言现状"时**判红；带**近似标记**（`约` / `≈` / `量级` / `N 行级`）**放行**。
    为什么：**量级是接手者需要的信息**（"这是 2 千行还是 20 万行"决定他怎么读），而精确到个位的行数是会腐坏的断言。
  - `vX.Y.Z` **高于当前发布版本** → 红（同行带"计划/拟/目标/预计"放行）。
    **前提**：工程里有"当前发布版本"这个真值（如 `package.json` / `__version__`）；没有版本体系 ⇒ 这条不适用，跳过。
- **边界**：它抓"写出来的数字"，抓不住**状态措辞**（"开发中"没有数字）—— 那属于写作约定 + 演练（SKILL F3）。

## 4. 模板（可直接拷）

### 4.1 文档头部元信息块（登记表的数据源）

```markdown
<!-- registry（本块是登记表的数据源；改完跑 `npm run docs:registry` 重新生成表）
层: 契约
作用: 数据契约：全部字段、版本演进与兼容承诺
不该写: 命令用法、架构理由
更新方式: 改 schema 必同步
-->
```

- 放在**第一个 H1 之后**（有 frontmatter 的文件同理），必须在**前 25 行**内。
- **生成物也要有**：由它的生成器产出（否则每次重生成都会抹掉它 —— 实测踩过）。
- 生成器把它们汇总成登记表，夹在成对标记之间：

```markdown
<!-- BEGIN:registry-table（由各文档头部元信息生成：npm run docs:registry；勿手改）-->

| 层 | 文档 | 作用（存在的唯一理由） | 不该写什么 | 更新方式 |
|----|------|---------------------|-----------|---------|
| 契约 | `docs/DATA-FORMAT.md` | … | … | … |
| 归档 | `docs/archive/*` | 历史快照（回溯用） | —（**勿作现状引用**） | 只增不改（必须带历史横幅） |
<!-- END:registry-table -->
```

### 4.2 一份活跃文档的骨架

```markdown
# <标题>

<!-- registry（与 §4.1 同一套四键；登记表由它生成）
层: <入口|治理|契约|设计|记录|归档>
作用: <一句话，它存在的唯一理由>
不该写: <它不写什么，指向该写的地方>
更新方式: <谁能改、什么时候改、怎么重新生成>
-->

> 读者：<谁在读它、读它来做什么>（可选的读者面说明，**不属于元信息块**，登记表不读它）

## …正文：判据 / 步骤 / 禁令（不要写成叙事）…
```

### 4.3 决策记录行（"为什么"的家）

```markdown
| **<决策名>** | <内容：决定了什么、约束是什么> | <理由：防什么损害 / 真实事故 / 实测> |
```

规则：理由列**不接受**"更规范""更优雅""更严谨"；必须是**损害**或**实测**。

### 4.4 工作目录 README（工作产物区的出口）

```markdown
# <YYYYMMDD>-<主题>

- **主题**：<这件事是什么>
- **开始日期**：YYYY-MM-DD
- **状态**：在飞 | 已收口 | 已废弃
- **说明**：<当前结论 / 下一步 / 为什么可删>

> 本目录可随时整目录删除；状态与「在飞 / 未收口」清单保持一致。
```

### 4.5 第一屏的"接手 N 步"

```markdown
## 接手 5 步（第一次进入本工程就按这个顺序走）
1. 看没做完的事 → 「在飞 / 未收口」（每条带证据指针）
2. 看最近改了什么 → 变更记录的未发布段（与上一条分工不同，缺一边会误判现状）
3. 找你这类的做法 → 架构文档的「每任务四步」表
4. 改完怎么算完 → 一条命令跑完整链；只改文档可先跑子集自检（**自检 ≠ 验收**）
5. 收尾 → 变更记录 + （新增文档则先写元信息块并重生成登记表）
```

> **真实工具链里只能有一个第一屏**：`AGENTS.md` / `CLAUDE.md` / `README.md` 并存时，
> 选**工具链会自动读**的那份当第一屏，其余降级为指针（README ≤ 20 行产品门面 + "AI 从 `AGENTS.md` 读起"）。
> 把这个选择写进决策记录。

### 4.6 「每任务四步」表（**最该先有的模板**：接手者 80% 的问题都是"我这类任务怎么做"）

四列固定：`读哪份 → 改哪里 → 跑什么 → 更新什么`。第四列是**同一次改动里必须做完的**（漏了会被门禁或人工核对抓出来）。

```markdown
| 任务 | ① 读 | ② 改 | ③ 跑 | ④ 更新 |
|------|------|------|------|--------|
| 加 / 改命令行参数 | 契约文档 + 设计文档的模块职责 | 脚本本体 + 生成器里的字段/参数常量 | `生成器` → `门禁` | 变更记录 + 契约（若对外可见） |
| 新增一个脚本 | 设计文档的模块表 | 新脚本（首行 docstring = 用途；参数即用法） | 同上 | 设计文档模块表 + 变更记录 |
| 改一个数据口径 | 契约文档（字段语义） | 脚本 + 契约散文 + **决策记录补一行"为什么改"** | 门禁 + **人工核对一小段样本**（门禁抓不住语义） | 变更记录 |
| 只改文档 | 无 | 文档 | 子集自检（**自检 ≠ 验收**） | 变更记录一行 |
| 加一条门禁 | 规则文件的门禁表 + 能力边界 | 门禁脚本 + 规则文件的门禁行 | **注入违规 → 变红（记报文）→ 撤销 → 复绿**，再跑全链 | 变更记录 + 规则文件 |
| 从备份恢复 | 事故记录 + 恢复步骤 | —— | **先导到临时位置**验证 → 再决定替换/合并 | 变更记录（何时、从哪份备份、恢复成什么） |
```

**只写你这类工程真正会发生的任务**（3–8 行即可）；每行都要是"照着做就能做完"的程度，不是"注意一下"。

### 4.7 契约文档的"部分生成"形态（手写散文 + 生成表格共存）

数据/接口契约最常见的形态是**一半手写、一半生成**。门禁**只比对 BEGIN/END 之间那一段**，其余散文自由撰写：

```markdown
## 字段表

<!-- BEGIN:fields（由 `tools/docs_gen.py` 从 FIELDS 常量生成；勿手改）-->

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| …    | …    | …    | …    |
<!-- END:fields -->

## 版本演进与兼容承诺（**手写**：这属于意图，生成不出来）
- 新增可选字段不递增格式版本；改语义/删字段/改必填性才递增，并补迁移分支。
```

- 字段清单的**来源是人的判断**：写在生成器的一个显式常量里（`FIELDS = [...]`），由它渲染表格；
  同时用**双向自查**保证它不撒谎：① 标为"被校验"的字段必须能在代码里找到；② 合约里的字段必须在表里出现。
- **手写段可以引用生成段**（"字段语义见上表"），**但不得重复列出字段名** —— 那就是第二份副本。

### 4.8 门禁登记行（规则文件里的门禁表）

```markdown
| **G8** | <名字> | <防什么损害：具体到会发生什么> | <实现脚本 / 判定条数> | <挂在哪一步> |
```

并在表后单独写**能力边界**（它抓得住什么、抓不住什么）——不要插进表格中间（markdown 表格被空行打断即结束，会让行静默消失：实测事故）。

## 5. 实测数据（用来做成本/收益判断，换工程要重新量）

| 量 | 实测值 | 说明 |
|----|--------|------|
| 13 条文档判定耗时 | **< 1 s**（该步墙钟实测约 0.6 s） | 占整条验证链约 **1%**（链总长约 49 s，大头是界面冒烟） |
| 单点错误的消息数 | **1 条**（改名 = 2 条） | 报错带处置方法 ⇒ 不是噪音源 |
| 加一份文档的同步点 | **3 处**（文档头 + 重生成表 + 变更记录） | 生成式登记表把 4 处降到 3 处 |
| 一次典型改动同步点 | 5–6 处 | 其中生成物**不用手改** |
| 接手演练的产出 | 两次演练 → **12 处真缺陷** | 全部转化为判定或约定 |
| 六轮修掉的缺陷 | **20 余处**（源工程口径；本文不复刻精确总数） | 其中 9 条判定在真实内容上抓到过东西 |
| 归档族规模 | 6 + 14 份 | 历史退出活跃视野后的常态 |

**反面数据（同样重要）**：文档语料里"散文副本"归零后，真值比对**没有对象可比** ——
这不是门禁坏了，而是 ADR「易腐事实不手写」达成了目标。
⚠️ 此时旧断言"必须抓到若干条"会**假红**，应改成断言**不变量**："凡语料里存在的声明，都不得逃过比对"。

> ⚠️ **这些数字是某个栈的量级参考，不是验收标准**（来源：一个有界面冒烟、有发布版本、有 npm 脚本链的工程）。
> 换到别的工程：**接口冒烟**那条大头没了 ⇒ 文档判定占比会升高（但绝对值仍是毫秒级）；
> **没有发布版本**的工程 ⇒ "未来版本号"判定不适用；**没有分层验证链**的工程 ⇒ "各步耗时"无意义，留痕只写时间/结论/失败项即可。
> 唯一可以直接照抄的是**相对关系**：判定要便宜、错误要少而准、同步点要少。

### 5.1 分档：什么规模上什么（避免过度设计）

| 规模 | 手写登记表 | 元信息块 + 生成式登记表 | 归档族 / 工作产物区 | 交接面 | 演练 |
|------|-----------|------------------------|-------------------|--------|------|
| **≤ 5 份文档**（脚本集、小工具） | ✅ 够用（配"表里路径必须存在" + 白名单两条判定） | ❌ 先别上（同步点只从 4 降到 3，不划算） | ✅ 要（草稿最容易泛滥） | ✅ 第一屏 + 在飞（**最低成本、最高收益**） | ✅ 每次改动批次后一次 |
| **6–15 份文档**（有契约、有决策、有验证链） | —— | ✅ 该上（漂移通常已经发生过） | ✅ 要 | ✅ 全套（含留痕与指针校验） | ✅ 每轮一次 |
| **> 15 份 / 多人多 AI 并发** | —— | ✅ 必须 | ✅ 要 + 历史检索入口 | ✅ 全套 + 并发提示 | ✅ 每轮 + 执行变体 |

**判断依据是"漂移有没有真的发生过"，不是"文档多不多"**（F5：改动要有据）。第一次真发生登记表漂移，就是上生成式的信号。

## 6. 落地顺序（新建项目 / 既有项目都适用）

| 阶段 | 做什么 | 验收（不满足不算完成） |
|------|--------|----------------------|
| **0 基线** | 数一遍：现在有几份文档、谁和谁重叠、接手四问能否答上、有没有门禁 | 写下**具体条目**（文件名/命令/数字），不产出形容词 |
| **1 分层与准入** | 给每份文档写"作用/不该写/更新方式"；定根与顶层白名单；建工作产物区 | 每份文档一句话说得清存在理由；没有"什么都写"的文档 |
| **2 单源化** | 挑**最易腐**的三样做生成 + 逐字校验（如：清单、计数、契约字段） | 手改生成物会被判红；改了源不重生成也被判红 |
| **3 交接面** | 第一屏接手 N 步 + 在飞小节 + 上次验证留痕 + 指针校验 | 一个零上下文会话能答上四问；在飞指针有门禁 |
| **4 门禁化** | 按 §3 清单挑**已有真实缺陷**的判定，逐条做 + 注入证明（起步可直接用 `templates/docs-gates.js`） | 每条判定都"红过一次"；撤销后复绿；总耗时仍毫秒级 |
| **常设** | 每轮（或每个发版周期）做一次**接手演练**，卡点必须转化 | 演练记录留档；卡点清单要么变条目，要么显式"决定不做" |

**顺序不能颠倒**：先分层再单源（否则不知道该给谁做生成）；先单源再交接（否则接手者读到的是会漂移的副本）；
门禁**最后**做，且只做"已经发生过缺陷"的那几条（先有缺陷再做门禁，避免凭空发明规则）。

**两条路怎么选、怎么拼**（新建 vs 既有）：
- 工程里**已经有**过期文档、散落草稿、或漂移过的清单 ⇒ 走 **既有项目清单**（它从"取证"开始：范围 / 回滚能力 /
  文档清单与"谁没人读"的证据 / 接手四问基线 / 接手成本基线 / 历史杂物普查）。
- 工程**还没有**文档、或只有一份刚写的入口文档 ⇒ 走 **新建项目清单**（它从"定判据"开始，不写文件）。
- **两者可以拼，且经常需要拼**：既有清单的**阶段 0（取证）**当成基线，再按**新建清单的阶段 1–5**重建结构 ——
  顺序是"**先取证 → 再重建 → 最后验收（用同一把尺子）**"。**不要跳过取证**：没有基线就没有"变好了"的证据。

**没有验证链的工程怎么办**（本 skill 不假设你一定有 `testing-for-ai` 那套链）：
- "一条命令回答上次绿没绿"退化成：**一条命令 = 你的文档判定 + 你现有的测试（哪怕只有一个）**，
  留痕只写 `时间 / 结论 / 失败项`（没有各步耗时就不写，别编）。
- "判别力证明"退化成：**手工注入一次违规**（改坏一个文件/删一个登记项），确认它判红，再撤销 —— 不需要链也能做。

## 7. 不可逆与恢复（文档体系能做什么、不能做什么）

- 文档体系**不能**替代版本控制。若工程零提交（企业策略拦 `.git/objects` 之类），必须在文档里
  **显式标注"无回滚（外部阻塞）"**，并给出唯一兜底：**改动前导出到被改目录之外**。
- 文档体系**能**做的三件事：① 把恢复步骤写进"每任务四步"（找备份 → **先导到临时位置验证** → 查 → 决）；
  ② 每次跑验证链时**打印备份新鲜度**（只提示不判红）；③ 在文档里写明"同盘的备份不算兜底"。

### 7.1 没有 CI / 没有 pre-commit 时，门禁靠什么被执行

这是 G 组（"挂进一条命令"）与 H6（"写进文档 ≠ 会发生"）之间那条没修的路。三条可行的替代，**按优先级**：

1. **写进第一屏的第 4 步**："改完怎么算完"就写着跑哪条命令 —— 让"被执行"成为**接手步骤的一部分**，而不是叮嘱。
2. **在变更记录里留痕**：每条改动末尾记一行"判定：通过/失败"。跑没跑是**可见**的，跳过也看得见。
3. **能加钩子就加**（pre-commit / CI 一行配置）；加了就写进规则文件；
   **没加也要写明"目前靠约定"** —— 不要让人误以为它自动执行了。

## 8. 已知缝隙（诚实标注，别假装覆盖了）

1. **语义正确性没有门禁**：判定只查"数字/清单/结构/覆盖"，查不了"文档说的和实现是不是一回事"。
   这类由"断言来自执行"的写作规则 + 交接演练承担，是人工残差。
2. **状态措辞抓不住**：`开发中`/`临时` 这类标注没有数字，判不出来（SKILL F3 只能靠约定 + 演练）。
3. **"该不该存在这份文档"判不了**：门禁只判"有没有家"，判不了"是否与别处重叠"（那是 SKILL B1/H1 的人工判断）。
4. **并发写入只做提示不做仲裁**：多个 AI 会话同时改文档时，判定只能告知"最近有谁在动"；
   真仲裁需要锁，而锁在会话异常退出后会死锁 —— 取舍：**提示 + 约定（先重读、别反复重写）**。
5. **演练依赖"读者在变"这一事实**：不同模型会暴露不同卡点，所以演练结论**不是收敛的** —— 它的价值在于不断发现，而非一次找全。
6. **"散文列举"与标记的一一对应无法机械化**：判定能对齐"声明的**数字** vs 实现现场的标记数"，但**对齐不了**
   同一行里那串用来"说明包含哪些"的**逐条列举**（它可能少一项或多一项，措辞还可自由改写）。
   ⇒ **正解不是给它加判定**（那要依赖措辞，脆弱），而是**改结构**：文档里**不再逐条列举**，只声明**条数 + 分类**；
   逐条清单改为**一条命令现场打印**。
   **一般化：能靠改结构消除的易腐表达，不要靠加门禁去守。**
