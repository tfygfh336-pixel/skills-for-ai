# 案例：一个真实工程的文档体系六轮演进

> 来源：一个由 AI 生成、由 AI 长期迭代的桌面工程（Electron 笔记应用 + CLI + MCP，活跃数月）。
> 本文按**轮次**记录：每轮**是什么触发了它**、**发现了什么**、**做了什么改动**、**哪些结论是工程特定的**。
> 所有缺陷都是**实测**出来的（探针 / 注入 / 零上下文接手演练），不是推理出来的；也包括**我自己的失误**。
> 读法：先看 §1 的起点与 §7 的"可迁移结论"；§2–§6 是过程与证据。

---

## 1. 起点：文档不少，但接手很难

改造前的状态（典型的"作者视角"产物）：

- 活跃文档 8 份 + 一个 300 KB 的变更记录；文档总量可观，**但接手路径要拼**：新会话得自己从 3 份文档里拼出"下一步做什么"。
- **同一份清单有三处副本**：人类门面文档抄了一份门禁清单（含实现命令）、规则文件有一份权威、生成物有一份链定义 —— 三份**没有任何东西守它们一致**。
- **易腐数字手写**：体积/行数类声明 5 处已过期（如"变更记录已 230+ KB"）。
- **历史污染活跃视野**：变更记录主文件 300 KB 中，未发布段一度占到 189 KB（占文档总量四成以上）。
- **归档没有身份**：6 份归档里 4 份没有任何"我是历史"的标记；而它们**仍会被 `grep` 到**。
- **工作产物区没有出口**：一个工作目录当天还在写（70 个文件），却没有任何"在飞/已收口"标记。
- **接手者最先想知道的那件事没人回答**："上次全链验证绿没绿" —— 工程里**没有任何落盘痕迹**。
- **不可逆**：版本控制为零（企业安全策略拦写对象目录），文档里写着"改动前导出到工程外"，但那个工程外目录**不存在**，最新备份在 7 天前且与工程同盘。

**结论**：这个工程的文档"量"不缺，缺的是**交接面**与**防漂移**。

---

## 2. 第 1–2 轮：把"落盘"和"准入"变成可查

**触发**：一次审计发现"同一事实多副本"是这个工程反复修的同一类病（文档数字、规则清单、文档清单都漂移过）。

**做了什么**：
1. 定义三类归宿：**活跃文档 / 归档族 / 工作产物区**，并写明各自规则（改不改、进不进真值扫描、能不能整目录删）。
2. **准入即门禁**：`docs/` 之外不得出现文档；根与顶层目录白名单；归档族用前缀行放行；每份文档要有家。
3. **接手面**：路线图里加「在飞 / 未收口」小节（主题 · 当前结论 · 下一步 · 证据指针），并在第一屏写明它与"未发布段"的分工。
4. **每任务四步表**：把"加命令 / 加渲染功能 / 改数据格式 / 加门禁 / 发版 / 打包 / 动侧栏运行包 / 从备份恢复 / 加断言"写成
   `读哪份 → 改哪里 → 跑什么 → 更新什么` 四列 —— 接手者**照表走**即可，不必理解全貌。

**实测收益**：接手演练的会话**自己拼出了**"给数据加字段"的完整 7 步（含"字段进 JSON ≠ 对 AI 可见"这种本地知识），
并正确说出"验收 = 一条命令跑完整链；改门禁必须先注入一次违规证明会红"。

---

## 3. 第 3–4 轮：把"门禁清单"补成一张能照抄的表

**触发**：零上下文接手演练（**只读、不许跑重命令**）报告了 6 处具体缺口。**这 6 处没有一处是我的审计想到的**：

| 演练者报出的缺口 | 真相 | 修法 |
|-----------------|------|------|
| 数据契约里**没有**某个字段，而命令会写它、校验器会校验它、生成的命令参考里有说明 | 契约不完整，且自述"只读本文档就能写出解析器" | 契约补字段 + **门禁：契约必须覆盖代码校验涉及的字段**（含"清单自身过期"双向自查） |
| 契约文档章节编号 `2.3 → 2.5` 断号 | 有人删/挪过章节没复查 | 重排编号 + **门禁：受管文档章节编号连续** |
| 人类门面文档把已发布功能标成"v0.15/v0.16 开发中" | 状态标注无人管，`release` 只同步版本号 | 改写措辞 + **写作约定：状态词必须带锚**（这条**没有门禁**，是人工残差） |
| 文档里出现 `v0.16.6`、`v0.16.2`，而发布版本是 `0.16.1` | **内部迭代编号与发布版本混用**，演练者原话："我无法判断这是笔误还是另一套命名空间" | 定口径：`vX.Y.Z` **只表示发布版本** + **门禁：高于发布版本的编号即红**（带"计划"字样放行） |
| 数据目录里躺着一个 26 KB 的无主脚本（无门禁、无说明） | 数据目录被当作"用户数据"跳过扫描，于是成了无人区 | 删除 + 契约写明"数据目录只应有这几项" + **提示级**列出未声明项（不判红） |
| "上次全链绿没绿"无法确认 | 无留痕 | 验证链结束时写结果文件，**跑之前打印一行** |

**教训（最重要的一条）**：**探针只能发现"我想到要探的模式"；演练不依赖作者的假设。**
这两轮之后我把"演练"制度化成了常设动作（§7.6）。

## 4. 第 5–6 轮：反向审计 —— "这套体系是不是冗余？"

**触发**：用户直接问"这套体系是否冗余"。这是一次**反向**审计（前几轮都在加），先量化三件事：

| 量 | 实测 | 结论 |
|----|------|------|
| 一次错误触发几条消息（真实工程注入） | 加未登记文档 1 条 / 删已登记文档 1 条 / 死指针 1 条 / 契约缺字段 1 条 / 改名 2 条 | **机制不冗余**：精准且可行动（此前在"假工程"上测得的 18 条是 fixture 不完整造成的假象） |
| 同一事实被写了几处 | 门禁清单 **3 份**、验证链步骤 **5 处**、"导出到工程外"规则陈述 ≈ **4 处**、工作产物区规则 **5 处** | **记录层真冗余**：3 处该剪 |
| 一次改动的同步点 | 加文档 4 处 / 加字段 5 处 / 加命令 6 处 / 改门禁 5 处 | 偏高，其中"加文档 4 处"里有 1 处可彻底消掉 |

**剪了什么**：
1. 人类门面文档的**门禁表 → 指针**（门禁清单 3 份 → 2 份：权威 + 生成物）。
2. 路线图**不再按版本记流水**（改成"能力状态视图"，版本流水唯一权威 = 变更记录），并删掉它与"已实现"段的 **4 条逐条重复**。
3. `待办` **并入**「在飞」清单，用状态列区分（未开始 / 在飞 / 外部阻塞 / 已收口）—— "没做完的事"三处 → 两处。
4. 写作约定加一条**副本上限**：*一条规则/一份清单/一组数字，最多 1 处权威 + 1 处动作现场，第 3 处必须是指针*。
5. **登记表从手写改为生成**：每份文档在自己头部声明元信息，命令据此生成登记表，门禁逐字比对 ——
   加文档的同步点 **4 → 3**，且不再手改"别处的表格"。

**副作用（值得记）**：登记表刚改成生成式时，**生成物（命令参考、基线文件）的元信息块被重生成抹掉了** ——
因为它们的内容由代码产出。修法：让**生成器自己产出**那个块。这类"新机制与既有生成物打架"的坑，
只有**真跑一遍**才会暴露。

## 5. 我自己犯的错（都留在这里，因为它们比结论更有教育意义）

1. **编码事故**：用 shell 的文本工具（`Get-Content`/`Set-Content`）读写 UTF-8 文档 ⇒ 旧版 PowerShell 按 GBK 解码再以 UTF-8 写回，
   **整份文档双重编码损坏**（400+ KB 全乱码、被加 BOM）。靠门禁的"BOM 检查"发现，从备份字节级恢复。
   **教训**：文档工作里最危险的不是逻辑，是**工具链的编码**；用能显式指定编码的 API，不要用会往返转码的 shell 工具。
   **边界**：那次门禁抓到的是 BOM；我另造了一个**无 BOM 的双重编码**探针 —— 它**通过了**。诚实记下：门禁抓"损坏的结果"，抓不住"违规的动作"。
2. **假阳性**：新加的"交接死指针"判定第一次上线就抓到了**它自己的规则文字**（`.review/<目录>` 这种占位写法被当成真指针）。
   修法：跳过含 `<` `>` `*` 的占位符，并补单测。
3. **真 bug（由"撤销后复核"抓到）**：我改门禁时误用了一个未定义变量，结果门禁**崩溃**而不是判红 ——
   而"注入后确实变红了没有"这一步**看不出差别**（崩溃也非零退出）。**只有撤销后复跑、确认复绿，才暴露它。**
4. **测试期望本身就是错的**：有一条断言写的是"必须抓到若干条声明"。当"易腐事实不手写"真正落地、文档里的散文副本归零后，
   这条断言**假红**了 —— 把它改成断言**不变量**（"凡语料里存在的声明，都不得逃过比对"）才正确。
   **教训**：门禁的测试要断言**机制**，不要断言"语料里恰好有东西"。
5. **一次注入脚本留下的残留**：批量注入验证后漏删一个文件，被门禁精准报出（1 条消息）—— 这条**正面证明**了判定的信噪比。

## 6. 六轮之后的形态（可对照自检）

- **文档判定 13 条**：登记与家门 / 白名单 / 悬挂登记 / 归档与主文件不重复 / 交接死指针 / 新代码未入档 /
  归档缺横幅 / 工作目录无状态 / 导航不可达 / 契约缺字段 / 章节断号 / 登记表与元信息一致 / 生成物未过期（+易腐数字与未来版本号在真值门禁里）。
- **生成物 3 类**：命令参考、验证基线（含"文档体系快照"）、登记表。
- **决策记录 20 条**，其中 **7 条**是文档体系自身的决策（"为什么这么定"有家）。
- **接手面**：第一屏的"接手 5 步"（从第 97 行提到第 26 行）+ 在飞清单 + 上次验证留痕 + 死指针校验 + 演练协议。
- **成本**：13 条文档判定合计 **< 1 s**，占整条验证链约 **5%**。

## 7. 可迁移结论（哪些与工程无关）

1. **判据只有一条**：零上下文的新 AI 能否独立接手。**文档数量不是指标**。
2. **三类归宿 + 准入即门禁**：任何内容先落三类之一；"有没有家"必须能一条命令判。
3. **单源三件套**：权威副本 → 生成 → 逐字校验。生成物**不得含时间/当天状态**（否则永远无法逐字校验）。
4. **让文档自描述**：元信息写在文档自己的头部，汇总表由它生成；加文档的动作 = 写头 + 重生成。
5. **副本上限**：1 处权威 + 1 处动作现场；第 3 处必须是指针。判断方法就是 `grep` 一下命中几处。
6. **演练是唯一的完整性检验**：它对"构思时的假设"免疫；卡点必须转化，否则演练等于没做。
7. **门禁只锁可机械判定的事，且每条先证明会红**；撤销后**必须复绿** —— 那一步能抓到别的步骤抓不到的 bug。
8. **便宜与精准是门禁能活下来的前提**：毫秒级、单点错误 1–2 条消息、报错即教程。

## 8. 工程特定的部分（换栈要重新判断）

- 具体的**目录名**（活跃文档 / 归档 / 工作产物区）与**门禁条数**（13 条）都是这个工程长出来的，不是普适值；
  小项目通常 3–5 条判定就够。
- **判定实现语言**（Node 脚本）与"一条命令跑完整链"的形式，取决于工程的工具链；
  非 JS 工程照搬"生成 + 逐字校验 + 注入证明"的思路即可，不必照搬代码。
- **成本数字**（< 1 s、占 5%）依赖"文档判定只读文本"这一事实；若你的判定要跑编译或起服务，成本模型完全不同。
- 本文的**演练提示词**（只读 / 禁止重命令 / 要求如实报告卡点）是为"文档类缺口"设计的；
  若要验证**执行能力**，应改用"在临时副本上真改一处并跑门禁"的执行变体。
