# docs-for-ai — 为"被 AI 长期接手"设计的文档体系

> **定位（先读）**：本 skill 是**跨工程、跨技术栈的通用方法论**，用于指导 AI 开发/迭代**任意**项目，**不绑定特定工程**。
> 文中出现的工程名、数字、路径与命令都是**案例与证据**（供理解与排序），不是判据、不是要求 ——
> 换栈、换场景时按你的现场重新判断（标 🔴 / [未验证] 者尤其如此）；`cases/`、`checklists/`、`templates/`
> 只是参考实现，把某个工程的具体选择当成「用本方法就得这么做」是最常见的误读。

**只回答一件事：文档该怎么分层、怎么准入、怎么防漂移、怎么交接，才能让一个没有先前上下文的 AI 独立接着把工程做下去。**

> 本文是**决策层**（读完再动手）：机制、判定实现骨架、模板与实测证据见 `REFERENCE.md`；
> 自检与改造评估见 `checklists/`；真实工程的六轮演进（含我自己的失误）见 `cases/文档体系六轮演进.md`。
> 每条结论都来自一个真实工程（Electron 笔记应用 + CLI + MCP，由 AI 迭代了数月）：那里文档体系被反复修了六轮，
> 每一轮都由**实测**驱动，而不是由"看起来更规范"驱动。

**术语** —— **活跃视野**＝一份新会话为了正确动手**必须**读的那些内容；**权威副本**＝某条事实/规则/清单唯一被允许"完整写出"的地方；
**动作现场**＝执行某动作时执行者必然会看到的位置（第一屏、报错文本、命令输出、函数头）；**接手成本**＝从零上下文到"知道下一步该做什么"所需的阅读量与跳转次数；
**易腐事实**＝会随迭代自己变化的东西（计数、体积、清单、字段、状态标注）。
**证据强度（怎么读本文）**：正文里带"（实测…）"的条目都对应 `REFERENCE.md` §5 的证据与 `cases/` 的记录；
`REFERENCE.md` §8 另列**已知缝隙**（判定抓不到什么）—— 只读本文时，请把"已知缝隙"当作**必须一起读**的部分。

> **如果只来得及做 5 件事，做这 5 件**（A–G 有几十条，全做等于不做）：
> ① **第一屏给出有序的「接手五步」**（E1）—— 新会话不会通读文档，只读开头；
> ② **每份文档头部写清「唯一理由 / 不该写什么 / 更新方式」**（B1/C3）—— 写不出"不该写什么"就说明它和别的重叠；
> ③ **易腐事实一律生成、不手写**（B4/C2）—— 计数、清单、字段表手抄一份就是埋一个漂移源；
> ④ **归档必须带「我是历史」横幅**（D2）—— 归档仍会被 grep 到，没标记就会被当成现状；
> ⑤ **「没做完的事」与「最近改了什么」分开、各自一处权威**（E2）—— 只读一边必然误判现状。
> 存量工程请从 **B4 的「先分层，再数份数」** 和 **D5 的两步退役** 开始，别先建生成器。


**与相邻 skill 的分工**（读错 skill 会得到一份用不上的方案）：
**导航表与"12 组重叠规则的权威分配"见 `README.md`** —— 本 skill 内**不复制**
（复制一份就是本 skill 自己禁止的"第二份会漂移的副本"）。

两者已各有一条与本 skill 相邻的条目（`architecture-for-ai` E2「规则放在动作现场」、`testing-for-ai` D 组「文档与规则」）——
那两条是**验证/结构视角**；本 skill 给的是**信息架构视角**（分几层、谁是权威、怎么生成、怎么交接），两者不冲突，取更严的那条执行。

**模块层（多模块工程）的分工**：模块的**边界与注册表单一来源**在 `architecture-for-ai` I 组（I1/I4）；
模块级**测试/label/断言计数**在 `testing-for-ai`（A6/B17）；本 skill 只负责**模块文档的最小集与对账**
（A5/B6/C5）—— 即"每个模块配什么文档、文档里的表与指针怎么与注册表机械对账"。

## A. 判据与度量

**A1 唯一判据：一个零上下文的 AI 能否凭文档独立接手**｜不是"文档是否齐全"、不是"是否规范"、也不是"人读起来舒不舒服"。
｜落地：把这条判据拆成可回答的四问 —— ① **现在处于什么状态、有没有没做完的工作**？② 我这类任务该**按什么步骤**做？
③ **写文件有什么禁令**？④ 凭什么判断"**做完了**"？四问答不全 ⇒ 文档体系没建好，与文档数量无关。
｜反面：用"我写了 8 份文档"证明体系好 —— 而新会话读完后仍然不知道下一步做什么。

**A2 度量接手成本（**诊断工具**，不是验收标准）**｜三个可当场量的指标：① 从**第一屏**到"下一步做什么"要读几份、跳几次；
② 常见任务（加字段 / 加命令 / 发版 / 改文档）各自需要读几份文档；③ 一条命令能否回答"**上次验证绿没绿**"。
｜**它们只用于定位问题**：数值不降说明改动没打到点上。但**验收只认 A1 的四问** ——
"跳数从 3 压到 2"这种形式改动最容易伪造出好看的数字，而它可能一点没帮到接手者（这正是 F5 要防的）。
｜反面：把诊断指标当 KPI ⇒ 优化出"更少的跳数、更差的理解"。

**A3 默认不落盘**｜落盘前先问一句：**3 个月后还会有人读它吗**？不会 ⇒ 写在对话里，或放进可整目录删除的工作产物区。
｜落地：把"落盘"变成需要理由的动作，而不是默认动作；写不清楚属于哪一类的，一律进工作产物区。
｜反面：把"分析过程"当资产留存 ⇒ 活跃视野被草稿淹没，真正的契约文档被埋掉（实测：一个工程的工作产物区攒到 71 个文件，其中大半已无人能判断死活）。

**A4 文档体系是**给接手者**的，不是给作者的**｜作者写文档时最想写"我做了什么"；接手者要的是"我现在该怎么做"。
｜落地：同一件事，写成**判据/步骤/禁令**，而不是写成叙事；叙事留给变更记录与决策记录。
｜反面：契约文档里夹着一段"当时我是怎么试出来的" ⇒ 接手者分不清哪句是现状、哪句是过程。

**A5 文档份数 ∝ 读者数（过度设计防线）**｜不是"文档越全越好"：给每个模块都配齐教程/指南/参考/解释四类是**失败形态** ——
没有读者的文档不产生接手价值，只产生漂移面与准入成本。｜落地：写任何一份文档前先答两个问题 ——
**谁在读、多久读一次**；答不出读者的不写（或写进工作产物区）。给"每个模块"配文档时默认**一级一份**（见 B6），
升级到多份要先过这两问。｜反面（先例工程的真实诱惑）：N 个模块 × 4 份 = 4N 份文档，每份都要准入、登记、
防漂移、被门禁扫 —— 维护成本超过全部读者获得的价值；且没人读的文档**照样会漂移**，漂移后误导的正是接手者。

## B. 分层与准入

**B1 每份文档只有一个存在理由**｜每份文档必须能一句话回答"**它存在的唯一理由**"，并在头部声明：
`层 / 作用 / 不该写什么 / 更新方式`。写不出"不该写什么" ⇒ 说明它与别的文档重叠。
｜落地：这四行就写在**文档自己的头部**（见 C3），并用它生成登记表。
｜反面：三份文档都能回答"整体架构" ⇒ 三份都会漂移，且读者永远不知道信哪份。

**B2 准入即门禁：没有登记的文档视为非法**｜"先登记再写"靠自觉必然失守（实测：一条人读的准入规则，两次被绕过）。
｜落地：把"文档有没有家"变成一条命令：`docs/` 之外不得出现文档；工程根只允收入口文档与配置文件；
顶层目录只允许既有那批；归档族由前缀行放行；**每份受管文档必须有头部元信息块**。
｜反面：只在文档里写"新增文件要登记" ⇒ 新增文件照样乱放，且没人发现。

**B3 建目录的唯一标准：规则是否不同**｜层（入口/治理/契约/设计/记录/归档）是**角色**，不是规则：
角色不同但规则相同的文档**平铺在同一目录**即可。只有"只增不改""可随时整目录删""不进真值扫描"这类**规则差异**才配拥有独立目录。
｜**层的取值表（唯一权威，就在这一行）**：`入口` / `治理` / `契约` / `设计` / `记录` / `归档`。
新增一个层 = **同时改这一行**（登记表的第一列由它校验；值不在表内即是配置错误，不是文档错误）。
｜反面：按"契约/设计/记录"建三个子目录 ⇒ 加一个文件要判两次类，收益为零，还多出一层路径要在门禁里维护。

**B4 文档清单只有一处权威，且它是生成的**｜清单类内容（有哪些文档、门禁几条、命令多少、契约有哪些字段）
**禁止手写第二份**：唯一权威 + 生成 + 逐字校验。
｜落地：文档头部元信息 → 生成登记表；代码里的命令注册表 → 生成命令参考；真值脚本 → 生成基线文件。
｜**分档（别一上来就上生成器）**：
- **文档 ≤ 5 份**：登记表**手写**即可，配两条便宜判定（"表里的路径必须存在" + 根/顶层白名单）就够了 ——
  4 行元信息块 + 生成器 + 逐字校验 + "生成物自己的元信息块"这一串成本，换来的只是**同步点从 4 处降到 3 处**，不划算。
- **文档 ≥ 6–8 份，或第一次真的发生登记表漂移之后**：再上生成式（元信息块 + 生成器 + 一致性判定）。
  理由是证据：漂移**已经发生过**（F5 要求改动有据），而不是"生成更规范"。
｜反面（实测）：门禁清单一度有 **三份**（README / 规则文件 / 生成物），README 那份是手工复制 —— 它必然漂移，只是时间问题。
｜⚠️ **上面那个分档有个前提：它是给「新建体系」写的。接手存量工程时，份数阈值会把你带错。**
实测（QQ 桥接，2026-10）：接手时已有 **26 份 md**，照字面早该"上生成器"了 —— 但真实问题不是"要不要生成"，
而是**这 26 份里哪些还活着**。先上生成器等于把过期稿一起机器化，同步点从 4 处降到 3 处的同时，
把一份错的事实固化成了"权威"。
⇒ **先分层，再数份数**。存量收编的顺序是：① 逐份判定死活（仍承载当前事实？）→ ② 抢救"为什么"
（唯一可能还在草稿里的决策依据，进决策记录 —— 见 D5 的两步退役）→ ③ 定归宿（活跃 / 归档带横幅 / 工作产物区）
→ ④ **此时才统计活跃份数** → ⑤ 再按上面的阈值决定要不要上生成器。
｜判据：如果你说不出"当前活跃的是哪几份、其余各自为什么不算活跃"，就还没到谈生成器的时候。

**B5 "为什么"必须有家，且与"发生了什么"分开**｜决策（为什么这样定）进**决策记录**；事故（为什么禁止这么做）进**事故记录**；
变更（什么时候改的）进**变更记录**。三者混在一处 ⇒ 接手者读不出"哪条是约束、哪条是历史"。
｜落地：决策记录用固定三列（**决策 / 内容 / 理由**），理由列写"防什么损害"而不是"更优雅"；事故记录只追加。
｜反面：把"为什么"全留在变更流水里 ⇒ 想读懂一处设计要先翻几百 KB 历史（实测：接手演练的 AI 明确报告"我无法判断这是笔误还是另一套命名空间"，根因就是决策没家）。

**B6 模块文档最小集：一级一份 README，固定骨架**｜每个"独立迭代单元"（模块/包/组件；粒度判据见
`architecture-for-ai` I1）配**一份** README、不长于一屏，固定六段骨架：① 一句话定位（含边界：**什么不做**）；
② 依赖与被依赖（表格）；③ 单独构建与测试命令；④ 公开 API 一览（类/函数级，不进细节）；
⑤ 守护的判据（门禁编号 + 测试文件 + 判别力证明指针）；⑥ 不该写（本模块的反模式清单）。
｜**家目录与命名**：README 落在模块自己的目录里，不建 `docs/modules/` 第二层 —— 建目录的唯一标准是规则不同（B3），
模块文档与其它文档规则相同；文档名不带模块名（家目录已说明归属，带名字等于把路径写两遍）。
｜**两级裁剪**：一级 = 上述骨架；只有出现"跨模块读者"（接入方、要对比多个模块的新接手者）才升二级，
且升级前先过 A5 的两问。｜反面：给每个模块复制四份 Diátaxis 文档 ⇒ 4N 份没人读的文档（A5）；
README 写到仓库级 `docs/` 下 ⇒ 模块目录里没有"我该怎么做"的动作现场（C1/E1），家目录规则被稀释。

## C. 单源、生成与副本上限

**C1 一条事实最多两处：1 处权威 + 1 处动作现场副本**｜能机械化的规则不要写成约定；但**规则必须出现在动手的地方**，
否则"规定过"与"实际发生"长期不一致。第二处副本只允许是**摘要 + 指针**，不是逐条复制。
｜**判据（人工，不可机械）**：逐处问这句话 —— "**它为什么在这里？**（权威 / 动作现场 / 指针）"。
答不上来的那一处就是多余副本，改成指针。一次改动里出现第三处**完整表达**即是违规。
｜为什么不用"grep 命中数"当判据：动作现场副本天然 ≥3 处（命令帮助、报错文本、函数头注释），
它们本来就该各写一遍；用命中数当标准只会**逼人把规则写得更含糊以躲开 grep**（把可测性当成正确性）。
命中数只能当**气味**（>3 处该看一眼），不能当判据。

**C2 易腐事实一律生成，并逐字校验**｜计数、体积、清单、契约字段、命令参考、验证链步骤 —— 全部由源**现场算**；
生成物头部写"**请勿手改 + 怎么重新生成**"；校验方式是**用同一个渲染函数重算并与磁盘逐字比对**，不一致即红。
｜落地：生成物本身也必须能被逐字校验 ⇒ 它**不能含时间戳/随机值/当天状态**（要写就写指针，值由命令现场打印）。
｜**后续完整先例**：一个原生 C++ 引擎工程把这条做到了全量 —— 门禁清单由代码侧注册表渲染、文档登记表由各文件头部元信息块汇总、版本/计数/命令表全部生成 + 逐字校验（新增条目只改一处，"忘了同步"这类漂移从根上消除）。
｜反面：把"上次验证结果""生成日期"写进生成物 ⇒ 它每天都不一样，于是**永远无法被逐字校验**（实测踩过：加入当天日期后，该文件立刻失去校验能力）。

**C3 让文档自描述，而不是维护一张别人的表**｜每份文档在自己的头部声明元信息，用一处生成器把它们汇总成登记表。
加一份文档的动作 = **写它的头 + 跑一次生成**，而不是"去改另一个文件里的表格"。
｜收益（实测）：新增文档的同步点从 4 处降到 3 处；登记表的解析脆弱面消失（手写表格曾被空行打断、被占位符误判）。
｜反面：登记表手写 ⇒ 它既是唯一权威、又是最大单点故障（实测它在同一工程里出过两次解析事故）。

**C4 契约必须覆盖代码真值**｜"字段怎么存"的文档必须与代码里的校验**对得上**：把校验涉及的字段名逐个在多份文档里核对，
缺一个就是"照着文档改会漏"。章节编号也要连续 —— 断号是"有人删/挪过章节而没人复查"的可见痕迹。
｜落地：字段清单用一个**显式常量**列出（人的判断），并让它**自查**：常量里的字段必须能在代码里找到（否则清单过期）；
每个字段必须在契约文档里出现（否则判红）。
｜反面（实测）：一个由命令写入、被校验器校验的字段，**契约文档里根本没有** ⇒ 第三方照着契约写解析器必然漏字段。

**C5 模块登记表对账：README 的依赖表 ⇔ 注册表**｜模块 README 里的依赖表**不是手写事实** ——
它与构建系统导出的注册表（唯一事实；导出方式见 `architecture-for-ai` I4）逐条对账，不等即红；
第⑤段的判据指针（门禁编号/测试文件/证明）同样必须机械可检，**指针失效即红**（与 E3 死指针同族）。
｜落地：依赖表由注册表渲染、或由对账门禁逐条校验；判据指针交给"路径必须存在"型门禁扫。
｜反面：README 依赖表手写 ⇒ 加一条链接边忘了同步，接手者按错的表判断影响面（"改它要动谁"全错）；
判据指针写"见相关测试" ⇒ 无法机械校验，测试被移走后腐烂没人知道。

## D. 三类内容分治：活跃 / 归档 / 工作产物

**D1 只有三种归宿，且规则不同**｜**活跃文档**（改、被门禁扫、进真值口径）／**归档族**（只增不改、不进扫描、**必须带历史横幅**）／
**工作产物区**（可随时整目录删除、不进扫描、不登记）。
｜判据：一份新内容属于哪类，只看两条 —— 它会不会被改？它是否承载"当前事实"？
｜反面：把历史留在活跃目录 ⇒ 门禁要不断为"历史里的旧值"开例外，最终没人信门禁。

**D2 归档必须自带"我是历史"的标记**｜归档**仍会被 grep 到**：没有横幅，接手者会把旧稿当成现状（实测：6 份归档里 4 份没有任何标记）。
｜落地：`.md` 用引用块、`.html` 用注释，写在文件**开头**；门禁只查前若干行（横幅必须在开头才起作用）。
｜反面："归档"被理解成"藏起来" ⇒ 它没藏住，却失去了被识别的机会。

**D3 工作产物区必须有出口**｜它是唯一杂物区，但**没有出口就会变成垃圾场**：每个工作目录必须在自己的 `README.md` 里声明
**主题 / 开始日期 / 状态（在飞 / 已收口 / 已废弃）**，与"没做完的事"清单对齐；根下只允许**工作目录**与**机器产物**。
｜**谁权威**：**"在飞"清单是权威，工作目录 README 是动作现场的副本**（C1 允许的第二处）—— 二者不一致时以清单为准；
README **只写状态与"能不能删"，不重复写"下一步"**（那是清单的字段，重复就是第二份会漂移的副本）。
｜判据：一个新人能否只读目录名 + 一个 README 就判断"这个目录能不能删"。
｜反面（实测）：一个工作目录当天还在被写（70 个文件）却没有任何状态标记 ⇒ 接手者要么误删在飞工作，要么把陈旧分析当现状。

**D4 历史要能窄查询，且不随年龄增长**｜变更历史是只增资产，必须有"按关键词/版本段"的检索入口，索引**从正文现算**（不落副本）；
查不到时要**指路**（"主文件没有 ≠ 没发生过"）—— 否则接手者会以为历史丢了。
｜落地：历史按窗口滚动（主文件只留最近 N 段，更老的整段移入归档目录），并让检索**同时覆盖归档**。
｜**分档**：一年也长不到需要检索入口的体量（小项目、低频迭代）**不要做**这条 —— 写进"决定不做"清单并给理由即可。
｜反面（实测）：归档之后检索只搜主文件 ⇒ 老版本的历史查不到，用起来像"历史的丢了"（这条被用户直接报成"机制坏了"）。

**D5 活跃文档的退役是**两步**，不是一步**｜草稿/过期文档**不能直接扔掉或直接归档** ——
**第一步先抢救"为什么"**：把这些草稿里唯一可能存在的决策依据、口径来源、踩过的坑抽进决策记录/契约；
**第二步再定归宿**：结论已被别处承载 → 原文进归档（带横幅）或删；结论还没进契约 → 原文进工作产物区并列入"在飞"（带指针）。
｜**顺序不能反**：先动结构后抢救 = 不可逆的信息损失（B5 的"为什么必须有家"）。
｜落地：逐份做一张**待遇表**（仍承载当前事实？有没有"为什么"？被引用过吗？归宿是哪类？），**合并同主题的草稿目录**（6 份草稿 → ≤2 个工作目录），不要一份一个目录。
｜反面：把 6 份草稿一次性移进归档 ⇒ 归档里多了一堆没人能判断死活的旧稿，而它们原本携带的口径依据永久丢失。

## E. 交接面：让"下一步"看得见

**E1 第一屏必须给出"接手 N 步"**｜新会话不会通读文档。第一屏要有**有序的**五步：看没做完的 → 看最近改的 → 找你这类的做法 →
改完怎么算完 → 收尾。｜判据：把"接手"这个词在第几行出现量一下（实测：改前在第 97 行，改后进到第一屏前段 —— **行号会随文件增长漂移，判据是"量它"，不是"记它"**）。
｜**真实工具链里的落地约定**：仓库里常同时存在 `AGENTS.md` / `CLAUDE.md` / `README.md` —— **第一屏只能有一个**。
选**你的工具链会自动读**的那一份（AI 工具会自动加载的那份优先）；其余几份**降级为指针**：
`README.md` ≤ 20 行的产品门面 + "AI 从 `AGENTS.md` 读起"；`CLAUDE.md` 若必须存在，就写成一行指针（"见 `AGENTS.md`"）。
**把这个选择写进决策记录**（否则下一个人会再建一份）。
｜反面：把导航表当成接手路径 ⇒ 接手者知道"有哪些文档"，但不知道"先读哪份、下一步做什么"。

**E2 "没做完的事"与"最近改了什么"必须分开，且都要在第一屏可达**｜前者 = 进行中的工作（带证据指针与下一步）；
后者 = 已完成未发布的变更（由变更记录的未发布段承载）。**只读一边就会误判现状**（实测：演练的 AI 因此把已收口的工作当成最新在飞）。
｜落地：两条各有一处权威，条目格式固定（`主题 · 当前结论 · 下一步 · 证据指针`），并在第一屏写明两者的区别。
｜反面：两件事混成一个清单 ⇒ 每条都要靠脑补判断它"是完成还是在做"。

**E3 交接面的指针必须被校验**｜"在飞"条目指向的证据目录可能已被删/改名 ⇒ **死指针**让接手者白找一场。
｜落地：门禁扫该小节的指针，目录不存在即红；状态列的词表固定（未开始 / 在飞 / 外部阻塞 / 已收口），加粗不算区别。
｜反面：指针腐烂无人管 ⇒ 接手者相信了一个不存在的现场。

**E4 上次验证的结果必须留痕**｜接手者最先想知道的一件事是"**基线绿不绿**"。没有留痕 ⇒ 要么盲跑一遍全链，要么在不知道基线的情况下动手。
｜落地：验证链结束时写一份极小的结果文件（时间/结论/失败门禁/各步耗时/版本），并在跑之前**打印一行**；
文件丢了就显示"无记录"，**不判红**（它是工作产物，不是契约）。
｜反面：只留日志不落盘 ⇒ 每个新会话都要重付一次全链成本（实测：一次全链数十秒，且带界面工程的更久）。

**E5 把"接手演练"做成可重复的验收动作**｜"任何新 AI 都能接手"是对**未来读者**的断言，**无法穷举检查** —— 只能反复做实验。
｜落地：给一个**零上下文**的会话两种变体：**只读理解**（不许改文件、不许跑重命令）与**执行变体**（在**临时副本**上真改一处并跑门禁）；
要求它回答 A1 的四问并**如实报告卡点**；记录留档（工作产物区）；**每条卡点必须转化为条目/判定，或显式写下"决定不做"及理由**。
｜反面：把演练当"演示" ⇒ 它会变成找优点的表演，而报告的价值恰恰在于暴露缺口（实测：两次演练直接产出 12 处真缺陷）。

## F. 写作约定（决定"门禁要抓的东西会不会被写出来"）

**F1 每行要么可执行、要么可验证、要么是"为什么"**｜三者都不是的行（"本功能很重要""建议注意"）不写 —— 它只增加接手者的阅读成本。
**F2 不写易腐数字**｜要当前值就**指路当场取**；必须写历史数值时同行带锚（版本号 / 快照 / 原记 / 当时 / 曾）。
**F3 状态类措辞必须带锚**｜`开发中` / `待办` / `临时` / `暂不支持` 要么带版本或日期，要么不写 —— 这类标注**没有门禁能抓**
（实测：一个已发布功能被标成"开发中"，躺过两个版本无人发现）。｜它是人工残差，只能靠写作约定 + 演练抓。
｜**与"在飞清单的状态词表"不冲突**（两处不是一回事）：**清单里的状态列用固定词表**（未开始 / 在飞 / 外部阻塞 / 已收口，
它靠"每次改动同步"保鲜）；**正文里的状态措辞必须带锚**（正文没人会定期回看，所以必须自带时间信息）。
**F4 报错即教程**｜门禁判红时必须**告诉人怎么改**：哪个文件、跑哪条命令、有几条出路。接手者遇到红的第一反应是读报错。
**F5 别用"更严谨/更规范"当改动理由**｜需要**真实事故或实测**作依据。没有证据的分层、门禁、新文档都是净成本
（本 skill 自己的六轮里，最有价值的三轮都是由"实测出的具体缺陷"驱动的）。
｜**权威副本**在 `architecture-for-ai` H4；本条只是它在文档改动上的同一条要求。

## G. 文档门禁：把"体面"变成"可查"

**G1 先分级，再决定形式**｜**能机械判定** → 门禁（脚本，挂进一条命令，违反即红）；**不能且损害高** → 铁律（少数，显式标注"靠自觉"）；
**不能且损害低** → 约定。｜推论：**一条已被机械化的规则应当退出铁律名单**；铁律条数多不是严谨的信号，是门禁缺失的信号。
｜反面：把主观质量（文案好坏、命名优雅）做成硬门禁 ⇒ 要么长期假红被无视，要么被迫改成永远通过。
｜**权威副本**：「什么是可机械判定的、什么只能进铁律/约定」的一般原则见 `architecture-for-ai` F3；本条给文档门禁的分级落点。

**G2 每条门禁都要写"防什么损害"和"能力边界"**｜不写边界，使用者会以为它万能（实测：编码门禁能抓"带 BOM/乱码"这类**结果**，
抓不住"用错工具但结果暂时正确"这类**动作**；数据门禁能抓结果非法，抓不住"绕过流程"）。｜落地：门禁表里每行都带"能力边界"一列。

**G3 新门禁必须证明判别力**｜**先注入一次违规、确认它变红，再撤销**；没红过的不算门禁。撤销后要复绿。
｜附加收益（实测）：**"撤销后复核"这一步抓出过我自己引入的真 bug**（门禁崩溃而不是判红），只看"变红了没有"是抓不到的。
｜**权威副本**在 `testing-for-ai` B4（完整做法与实测）；本条只给文档门禁侧的要点。

**G4 采不到真值 = 红**｜取不到真值必须失败并打印"无法取得真值，门禁不能自称已校验"；**"跳过"必须与"通过"可区分**。
｜并且**两条路径要一致**：检查模式拒绝写入时，生成模式也必须拒绝（实测：检查会拒绝、生成却照样写入一个 `null`）。

**G5 文档门禁要便宜、要精准、要能自愈地指路**｜它们只是读文本，应当**毫秒级**（实测：13 条判定合计不到 1 秒 ——
该步墙钟约 0.6 s，占整条验证链约 **1%**）；一次错误**只应报出一两条消息**（实测：单点错误 → 1 条；一次改名 → 2 条，各自可行动）。
｜反面：为同一根因喷一屏消息 ⇒ 使用者学会无视它。

**G6 判定的清单只有一处权威：`REFERENCE.md` §3**｜本节**不复述**那张清单 —— 复述一次就是制造第二份会漂移的副本
（本 skill 的第一版就在这里犯了它自己禁止的错：三处都列了清单，条数还不一致）。
这里只给**分类**，用来挑"先上哪几条"：
① **准入类**（有没有家、在不在白名单、有没有元信息）；② **一致性类**（登记表↔元信息、生成物↔源、契约↔代码字段）；
③ **结构类**（章节编号、归档横幅、工作目录状态、导航可达）；④ **交接类**（死指针）；
⑤ **易腐声明类**（体量/行数、未来版本号）。
｜**先上哪几条（顺序）**：先把**你已经有现成违规**的那条挂上（现成的乱放文件、现成的过期数字），
再上"一致性类"（它防的是"文档开始骗人"），最后才是"结构类"。

## H. 反面清单（看到这些提议，先怀疑）

- **H1 不为"更规范"建目录、加文档**：目录按**规则差异**建（B3）；新文档要先回答"它与哪份重叠"。
- **H2 不手写任何可派生的清单**（B4/C2）：能被生成的清单，手写一份就是埋一个漂移源。
- **H3 不让同一件事有两处完整表达**（C1）：包括"文档与代码之间"。
- **H4 不把主观质量做成门禁**（G1）：审美、命名好坏、"是否优雅"最多做人工清单。
- **H5 不靠"大家注意点"**：工作产物区要有出口（D3），并发写入要有提示，历史要有查询入口 —— 机制缺失不能靠叮嘱补。
- **H6 不用文档替代机制**："写进文档"≠"会发生"。规则要么进动作现场（E1/C1），要么进验证链（G 组），否则等于没写。
- **H7 不把"我没找到"当成"不存在"**：检索查不到时要**指路**（D4）——归档、别的分区、历史版本都可能是答案所在。

## 边界

- **不解决代码/数据的结构本身**（单源实现、分层、并发写、原子写、回滚）：那是 `architecture-for-ai`；本 skill 只处理
  "这些约束该写在哪、怎么让接手者一定看到"。
- **不解决验证体系**（分层、预算、真值与门禁机制、判别力证明的完整做法）：那是 `testing-for-ai`；
  本 skill 只在"文档类门禁"这一小块给出可直接照抄的判定目录（G6），其余引用它。
- **不解决主观质量**（文案、美感、研究结论）：它们缺的不是文档，是可判定的目标。
- **不适用于一次性脚本、寿命短于一个月的项目**：分层、准入、生成、门禁的成本高于收益。
- **不承诺"文档齐全"**：本 skill 的产出是**接手成本下降**与**漂移可被机械发现**，不是文档数量。
  若一个项目只有 3 份文档但四问都答得上，它比 8 份文档答不上四问的项目健康。
