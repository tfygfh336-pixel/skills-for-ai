# architecture-for-ai — 为"被 AI 长期改"而设计的代码与数据组织

> **定位（先读）**：本 skill 是**跨工程、跨技术栈的通用方法论**，用于指导 AI 开发/迭代**任意**项目，**不绑定特定工程**。
> 文中出现的工程名、数字、路径与命令都是**案例与证据**（供理解与排序），不是判据、不是要求 ——
> 换栈、换场景时按你的现场重新判断（标 🔴 / [未验证] 者尤其如此）；`cases/`、`checklists/`、`templates/`
> 只是参考实现，把某个工程的具体选择当成「用本方法就得这么做」是最常见的误读。

**只回答一件事：结构怎么摆，AI 才能在没有完整上下文、会漏连带、又可能与人并发的情况下长期把它改对。**
输出的是**结构前提**（可机械取证的前提），不是验证方法论。用法：正文给"该不该这么摆"；落地细节、权衡、反例、实测证据在 `REFERENCE.md`；自检在 `checklists/`；真实取舍在 `cases/`。
**证据强度（怎么读本文）**：正文**不逐条标注**强度 —— 凡带 ⚠️**[未验证的处方]** 的，是"我认为对、但在来源工程里**没落地过**"的条目；
其余条目都对应 `cases/` 与 `REFERENCE.md` 里的记录（后者含 `[实测]/[推断]/[未验证]` 标注与"权衡不是定律"表）。
**只读本文时：未标注的当"已验证的结构判断"，带 ⚠️ 的当"假设"。**

术语：**单源**=一个事实/一条逻辑只在一处表达，他处只转发或引用；**薄壳**=只做翻译转发（界面/参数解析/路由）不含业务判断；
**现场**=执行某动作时执行者必然会看到的位置；**可机械取证**=一条命令即给出对错。

> **如果只来得及做 5 件事，做这 5 件**（A–I 有几十条，全做等于不做）：
> ① **先上版本控制**（G1）—— 没有它，之后每次改动都是单向门，别的都免谈；
> ② **同一事实只准一处完整表达**（A3/C1）—— 包括文档与代码之间；
> ③ **写盘走唯一闸门**（D1/D3 原子写）—— 绕过它的脚本迟早毁一次数据；
> ④ **失败必须响亮**（F1）—— 禁止静默回落、静默跳过、静默降级；
> ⑤ **依赖方向单向、无环**（A2）—— 底层出现上层 import 就是分层的终点。
> 这 5 条做完再谈分层细化、模块化（I 组）、并发版本闸门（D2）——**顺序反了会花大力气去做净成本的事**。

## A 单一真源与分层

- **A1 单一逻辑源 + 薄壳。** 原则：业务逻辑只实现一次，界面/CLI/API/机器人都是转发壳。
  落地：把逻辑收进一个可被多方 `require`/`import` 的模块层，壳只做参数→调用→输出。
  判据（任一即可动手）：`grep` 同一个判定表达式出现 ≥2 次；壳里出现 `if (格式/版本/合法性)`。
  反面：界面保存的数据脚本不认（两套序列化）；改一个规则要改三处，漏一处就分叉。
- **A2 单向依赖，禁回边。** 原则：依赖方向只有一个（壳 → 逻辑 → 数据），底层永不知道上层存在。
  落地：写出允许的层序；"底层需要上层信息"用**注入**（传参/回调）解决，不用反向 import。
  判据：依赖图里没有环；底层模块的 import 列表里不含上层名字。
  ⚠️ **[未验证的处方 → 已有先例]**：把这条判据做成**一条可机械检查的规则**（脚本扫 import 方向）
  在来源工程里**从未实现** —— 性质成立、检查没建（别以为它已经在跑）。**后续先例**：一个原生 C++
  引擎工程把这条做成了运行中的门禁 —— ① 依赖矩阵 = **允许集**（声明式、单源）；② import/include
  扫描 = **实际集**（现场算）；③ 两者对账 + 挂进验证链，并抓到过真实越界（一个「壳 → 底层」的
  非法边）。⇒ 该处方可落地，成本与一条普通守卫同量级。
  反面：数据层为了发通知去调界面函数 ⇒ 无法无头运行、无法单独测试、换壳即崩。
- **A3 同一事实禁止两处表达。** 原则：包括**文档与代码之间**——数字、清单、约束只写一处，别人引用它。
  落地：易腐事实（工具数、用例数、字段清单、规则条数）产出**单源**（生成物或常量模块），文档不手抄。
  判据：同一事实能在 `grep` 里被两处各自"完整写出"⇒ 已经会漂移。
  反面：README 说 7 条规则、正文写 6 条；两边都对不了，且漂移掉的常是最要命的那条。
  单源化的**做法**（生成 + 逐字校验 + 副本上限）权威见 `docs-for-ai` C2 —— 本条只给"只准一处"这个结构判据。

## B 可机械取证的结构前提

> 本组只负责让"可验证"在结构上成为可能；缺任何一条，验证体系都会退化成人工操作。
> **B1 的总判据不是"测试是否还绿"，而是"人按原有习惯操作得到的是否还是设计意图"。**

- **B1 一切"算不算对"要能一条命令判定。** 落地：为每个声明的不变量写一个"跑完给退出码"的入口，
  失败文本含**对象 + 期望 + 实际**。反面：判据是"我看了觉得没问题"。
- **B2 进程内可调用的入口。** 原则：核心入口要能从同一进程里调用，不经子进程、不靠管道 stdio。
  落地：把入口拆成纯函数 `invoke(argv) -> {code, stdout, stderr}`（`process.exit` 留给最外层壳，
  退出码是全局态，进出都要隔离）。反面：每条断言 0.7 s 冷启动、上百条断言跑两分钟 ⇒ 没人愿意跑 ⇒ 事实上的无验证。
- **B3 无头路径。** 原则：有界面的系统也要有一条不依赖人眼和鼠标的验收路径。落地：显式固定窗口尺寸
  （别把框架**默认值**当固定值）、离屏/隐藏但**仍然出帧**、等"渲染稳定"而不是固定 sleep。
  反面：验证时窗口弹在桌面抢焦点；隐藏后截到黑屏，于是"全绿"其实什么都没测。
- **B4 纯逻辑下沉。** 原则：不需要 I/O、不需要时钟、不需要网络就能测的部分，要真的被拿出来。
  落地：判定/转换/校验/排序/剪枝放纯模块；I/O 与时钟从参数注入。
  反面：一个函数里 parse + 读盘 + 写盘 + 打印，想测它必须先造文件系统。
- **B5 确定性产物。** 原则：同输入两次产出**逐字节相同**。
  落地顺序：**先消除非确定来源**（时间戳、随机 id、并发顺序、默认值、动画中间态、字体与 dpr）——
  把易变字段移出产物或做成参数；**全部消除后仍不可复现，才考虑放宽判据**（比阈值、比结构化字段）。
  反面：默认拿"相似度 > 95%"开局，真实回归会藏在噪声里；两次哈希不同却归因于"机器抖动"。

## C 为"上下文有限"设计接口

- **C1 窄接口。** 原则：程序必须能只回答**一个窄问题**，不必先把全集读完。落地：为高频问题各给一个专用入口
  （"某 id 的入边是谁""某文件属于哪一层"），而不是"读全量再自己筛"。反面：只有全量导出，问小事也付全量代价。
- **C2 粒度分层。** 原则：>=3 档（骨架 / 摘要 / 单条 / 按子树），每档明确**丢了什么**。
  反面：只有"全量"和"一条"两档 ⇒ 中间问题只能靠全量，成本随规模爆炸。
- **C3 高频动作的读取成本有上界，且不随项目年龄增长。** 落地：先生成索引/清单再把查询打到索引上；
  读一个东西不要扫全目录；给每个高频入口一个字节量级上界并写下来。
  反面：越用越慢的历史文件（变更日志、快照目录）被每次操作全读一遍。
  ⚠️ **[未验证的处方]**："给每个高频入口一个**字节量级上界并写下来**（可被测试）"在来源工程里**从未落地**
  （没有任何 size 断言）。前半句（成本会随项目年龄增长）有实测；后半句（把上界写下来并测它）是**未验证的建议**。
- **C4 变更历史要能窄查询。** 原则：历史是**只增**资产，必须有"按关键词/段/条目"的检索入口。
  落地：索引从正文现算（不落一份会漂移的副本）；查不到时输出要**指路**（"主文件没有，不等于没发生过"）。
  反面：几百 KB 的历史被整份塞进上下文，只为了问一句"这个功能哪一版加的"。
  历史与归档的**治理规则**（归档横幅、退出活跃视野、检索同时覆盖归档）权威在 `docs-for-ai` D4；本条只给读取成本判据。

## D 为"人机并发"设计数据层

- **D1 唯一写盘闸门。** 原则：写盘出口只有一个函数，其他写路径一律禁止。
  落地：该函数负责 校验 → 版本检查 → 原子写；新增写路径必须复用它（评审时搜裸写文件调用）。
  反面：绕过闸门的手改脚本"临时用一下" ⇒ 校验与原子性同时失效。
- **D2 并发写入即版本闸门。** 原则：读时带回**内容指纹**；写回时盘上必须仍是那一版，否则**拒绝写入并报出两侧版本**。
  落地：指纹用内容哈希（不用 mtime/size——同秒两次写分不开、原地改字段 size 不变，会让闸门**静默失效**）；
  界面保存与命令行写入**共用同一个闸门** —— ⚠️ "共用"指**同一份比较与报错实现**：只共用底层原语
  （原子写、哈希函数）而各自重写一遍比较逻辑，**不算共用**（来源工程里就残留了这样一处，属 A1/A3 禁止的"同一逻辑两处表达"）。
  反面：内存里是子集时整树写回，删掉别人的条目；AI 刚写的被界面一次保存覆盖。
- **D3 原子写。** 原则：写盘 = 同目录临时文件 → fsync → rename；中断只留临时文件，不留半截正式文件。
  反面：断电/异常中断后正式文件半截 JSON，读出即崩，且原内容已被破坏。
- **D4 可派生的不手写。** 原则：能由单源算出来的东西一律**生成**，并加"生成物是否过期"的逐字比对。
  落地：生成物头部写"请勿手改 + 怎么重新生成"；比对失败即红。
  反面：命令清单手抄一份，新增命令时忘了同步 ⇒ 文档开始骗人。

## E 为"AI 会漏连带"设计登记面

- **E1 新增产物必须在架构层有登记面。** 原则：新增文件/目录要么落在**白名单/忽略清单**里，要么被登记为
  真值/生成物；否则它会被规则判非法，或被扫描器、收集器误纳入。
  落地：维护"根目录允许什么、顶层目录允许什么、哪些是工作产物区（可整目录删除、不进扫描）"，
  且把这三条**写进报错文本**里（报错即指路）。
  反面：新产物在工程根被扫描器当输入 → 报一个与被改内容无关的红，误导出"我改坏了什么"的结论。
- **E2 规则与说明放在动作现场。** 原则：这是**信息架构**问题，不是文档纪律问题。
  规则该出现在"执行这个动作时会看到的地方"：跑命令时的输出、函数头注释、文件头、报错文本、新会话第一屏；
  集中式的规则权威副本只放**指针**与该动作当场需要的条目。
  判据：把规则字数 × 出现位置数当作成本量；远处的规则等价于没有规则。
  反面：规则只写在没人会读的长文档里 ⇒ "规定过"与"实际发生"长期不一致且没人察觉。

## F 为"AI 会犯低级错"设计容错

- **F1 失败必须响亮。** 原则：禁止静默回落、静默跳过、静默降级。
  落地：不确定就报错并给出下一步；跳过要显式打印"跳过了什么、为什么"；"无法判定"必须与"通过"可区分。
  反面：坏状态被自动降级成默认值 ⇒ 人看到的"全绿"其实是"没测"。
- **F2 编码卫生。** 原则：哪怕临时产物区也可能被扫描、被入库、被下一步读取，编码必须显式 UTF-8 无 BOM。
  落地：写文件用能明确指定编码的工具链；**不要用会写 BOM 的工具链写 UTF-8**；
  `Get-Content`/`Set-Content` 这类往返在非 UTF-8 默认代码页下会同时引入 BOM 与乱码。
  反面：一个"只是临时"的文件带 BOM，下游 diff/哈希/解析全乱，且没人知道是谁引入的。
  编码卫生的**权威副本**在 `testing-for-ai` E5（含"一轮踩了 4 次"的实测）；本条只给"临时产物也不例外"这条结构判断。
- **F3 不要把"不可自动判定"的东西做成硬门禁。** 原则：门禁只锁**可机械判定**的事；审美、命名好坏、
  "是否优雅"这类主观项，最多做人工确认清单。
  反面：主观项进门禁 ⇒ 要么长期假红被无视，要么被迫改成永远通过，两种结果都让门禁失去意义。

## G 回滚与不可逆

- **G1 必须有版本控制。** 原则：没有它，每次改动都是**单向门**，任何一次覆盖即不可逆。
  落地：能上版本控制就上；不能上时要把它当作**已声明的风险**，而不是默认没事。
  反面：靠"同一份内容的第二个副本"当版本控制 ⇒ 见 H5 与 `cases/`（必然丢工作）。
- **G2 没有版本控制时：每步先备份 + 记前后哈希，并如实标注这是弱等价。**
  落地：改动前导出可整体回滚的备份到**被改目录之外**；记录改动前后哈希以便证明"改了什么"；
  在文档里写清"这是弱等价、不是等价"——它无法给出分支、无法二分定位、无法原子回滚整批。
  反面：口头说"有备份"但备份与原件同目录、同一次批量写盘、或备份本身就是被覆盖的对象。

## H 反面清单（看到这些提议，先怀疑）

- **H1 不因为"AI 好写"就堆第二份实现。** 写得快不是单源可以放弃的理由；第二份实现会立刻开始漂移。
- **H2 不用"兼容层"实现核心能力。** 兼容层是过渡脚手架，不是承载判定/转换/校验的地方；
  核心能力放进兼容层 ⇒ 它永远拆不掉，且所有壳都依赖它。
- **H3 不给最高频的动作加新成本。** 高频动作每加一步，都要乘以次数；代价不会被"更严谨"抵消。
  要用开关/旁路（opt-in）表达新能力，且**不加开关时输出与从前逐字节相同**。
- **H4 不把"看起来更严谨"当改动理由。** 需要**真实事故或实测**作为依据；没有证据的抽象、分层、
  门禁、日志都属于净成本（`cases/` 里有一次真实反例：以"更严谨"为名的改动让判据退化）。
- **H5 不依赖"没人会碰"。** 不可逆或多副本的地方要**显式复位/隔离**（单源目录、只读副本、明确停写），
  而不是"大家注意点"。多副本 + 单向同步 = **必然**丢工作，不是概率问题。
  多副本与同步的**权威副本**在 `testing-for-ai` C5（含"丢过两次"的实测）；本条只给隔离/复位这个结构动作。
  ⚠️ **谈"多副本风险"之前先判拓扑**（实测踩空一次，2026-10）：看起来"两份完全相同的副本"，
     可能压根不是副本 —— 目录联接（Windows Junction / `mklink /J`）、软链接、硬链接、挂载点，
     都会让两个路径指向**同一个实体**。此时"两份内容一致"是必然的、不存在漂移，
     而真正的风险变成"**联接被删掉 / 被换成真副本 / 被指到别处**"。
     · 判据（一条命令）：Windows `(Get-Item $p).LinkType` / `dir` 显示 `<JUNCTION>`；POSIX `readlink`、`stat` 的
       硬链接数、`findmnt`；跨机看是否同一 inode/卷。
     · 判错的代价很实际：会按"选一份为源、另一份改成生成物"的处方去改一个**不需要改**的东西，
       并在文档里写下一句错的因果（"只改源 = 线上没变"——而实际上改源立刻生效）。
     · 正确处置：**联接是"唯一源"的最强形态，保留它**；把守护从"同步"改成"拓扑+内容一致性门禁"
       （逐文件哈希 + 断言目标仍指向本源），并留一个"联接坏了之后的修复脚本"。

## I 模块化框架（多模块工程的边界、对账与并行）

> 本组回答：工程按功能长出多个模块时，**什么该是一个模块、模块间的依赖怎么不再双维护、
> 模块能不能被单独构建与测试、模块元数据放在哪、多个改造者怎么按模块并行**。
> 与 A 组的关系：A 组管"一个工程内部"的单源与分层；I 组管"模块作为独立迭代单元"的框架契约。
> 本组的判据全部可机械取证；模块级**测试/label/计数**见 `testing-for-ai`（A6/B17/B18/C6），
> 模块级**文档最小集与对账**见 `docs-for-ai`（B6/C5/A5），并行**可跑性判据**见 `testing-for-ai` C6。

- **I1 模块边界：功能内聚 + 依赖单向 + 可独立编译验证，三者缺一不成模块。** 原则：模块是**独立迭代单元**，
  不是目录收纳盒。落地：先画允许的依赖方向（无环），再按"改一件事只进一个模块"切分；
  切完当场验证"能单独构建+跑它的测试"。判据（任一不满足就该重新切）：模块内部改动不需要碰别的模块；
  依赖图无环；**单独构建该模块及其测试是一条命令**。
  反面：按文件类型分模块（`utils` / `common` 黑洞——什么都能进，改了谁都要重编）；
  按迭代速度分模块（"热点模块"——热度是时间函数，边界会每周变）；
  "物理上分了目录"但任何一个模块都编不出独立产物（只是目录，不是模块）。
  ⚠️ **[未验证的处方]**：模块数上限/理想粒度无通用数值 —— 先例工程是 17 个模块、约 350 个第一方文件
  （≈20 文件/模块），但这依赖技术栈与团队规模，**不是判据**；判据是上面那三条，不是文件数。
  ⚠️ **「可独立编译」只适用于编译期模块，别拿它否掉部署期单元。** 一个工程里可能同时存在两类边界：
  · **编译期模块**：靠依赖图证明（include/import 无环、能单独构建）—— I1 的三条针对这一类；
  · **部署期单元**：靠**运行时边界**证明（独立进程、独立端口、独立安装/挂载的插件、独立部署物）。
    它们往往**零代码 import**，改一个不需要重编另一个，判据是「能独立启动 + 能独立验证」，
    而不是「能独立编译」。
  ⇒ 按 I1 的字面判据，一个用 stdio/HTTP/消息队列通信、零 import 的三进程工程会得出"它们都不算模块"
  的荒谬结论 —— 而它们恰恰是最干净的模块。**先问「这条边界由编译期还是运行时保证」，再选判据。**
  ⚠️ **[未验证的处方]**：模块数上限/理想粒度同 I1；另注：部署期单元的拆分理由与编译期不同 ——
  前者常按"故障隔离 / 独立发布 / 独立扩缩"切，后者按"依赖内聚"切，别互相套用。
- **I2 依赖声明对账：代码用的边 ⊆ 构建图声明的边，且两个集合都要有守卫。** 原则：include/import 扫描给出
  **代码实际用了什么**，构建系统声明**链接了什么**，两处各说各话时，"编译能过"会成为 undeclared dependency 的掩护
  （靠传递包含活着）。落地：代码扫描边 ⊆ 构建图边（构建图取**真链接**，注释里的 target 名不算 —— 注释免疫）；
  方向上另有**允许矩阵**（声明式，约束"允许的边"这个法，不是"实际的边"这个事实）；
  **登记完整性**：每个模块目录都必须出现在矩阵里，漏登记即红（否则新模块被静默跳过检查）。
  反面：矩阵手抄两份（CMake 一份、文档一份）⇒ 必然漂移；注释里写个 target 名就被当成链接（洞： declarations 寄生在注释里）；
  新模块目录不在检查范围 ⇒ 它带着循环依赖进来都没人红。
  **先例**：有工程把这三层做成了运行中的门禁（允许矩阵 + include 扫描 + 链接闭包对账，抓到过真实越界边）；
  换栈时按同一三层重新实现，配方见 `REFERENCE.md`。
- **I3 独立编译：一条命令构建该模块及其测试；关掉它对全仓零影响。** 原则："能单独编"必须是真命令
  （构建该模块 target + 它的测试 target），不是"全构的子集顺带编了它"。落地：per-module 测试可执行 +
  统一 label；**关闭开关**时，依赖方在 configure 期**响亮失败并点名**（缺了哪个模块），而不是静默跳过或运行期崩溃。
  判据：从干净树起，一条命令得到该模块的测试退出码；关掉它再 configure，报错文本含模块名与"谁需要它"。
  反面：关模块后 configure 照过、链接期才报一串未定义符号（失败离原因太远）；
  "能单独编"但测试仍在全仓单测二进制里（改一个模块要链全部测试文件）。
- **I4 框架登记五件：模块元数据由构建图生成，禁手写第二份。** 原则：目录/target/开关/依赖/测试 label/文档指针
  这六项元数据，唯一来源是**构建图本身**（configure 期遍历 target 属性导出注册表），文档与测试只**消费**它。
  落地：模块注册函数（各栈形态不同：CMake 函数、Bazel rules + package_group、Meson subdir 摘要）=
  唯一登记入口；configure 结束导出机器可读注册表；文档里的依赖表、测试计数**与注册表对账**（不等即红）。
  判据：注册表是生成物（头部写"请勿手改 + 怎么重新生成"）；grep 同一模块的依赖列表命中第二份手写副本 ⇒ 已漂移。
  反面：元数据三处手抄（CMakeLists / 架构文档 / 测试清单各一份）—— 三份都会漂，且没人知道信哪份；
  注册表手填"猜测值"（如测试用例数）⇒ 双维护复发，猜错的那天没有任何门禁会红。
- **I5 并行前提：租约粒度 = 模块，提交面 = 模块目录，文档段所有权明确。** 原则：多个改造者（人或 agent）
  并行改一个工程，冲突面必须**预先切开**，不能靠"大家注意点"。落地：租约挂在**模块 key** 上（不是文件、不是 agent）；
  每个模块的提交面显式声明（源码目录 + 它的测试 + 它的文档段）；跨模块改动（如注册表消费方）显式登记为串行面。
  判据：两个改造者同时改不同模块时，互不 `git add` 对方文件、全链仍绿 ⇒ 并行是被证明的事实而非口号。
  反面：口头约定"你改 gameplay 我改 renderer"—— 共享一个 `tests/CMakeLists.txt` 或一个门禁文件时照样撞车；
  租约按文件粒度发（同一文件被两人先后 claim，先写者的工作被静默覆盖）。
  **租约与通道的工程化落地**（互斥窗口 / 任务期判据哈希 / 判据变更串行通道）见 `testing-for-ai` C4；
  本条只给"粒度=模块、提交面=目录"这个结构判据。

## 边界

- 不解决**零测试项目**：本 skill 的 A–I 是"让验证成为可能"的结构前提，不是"从零到有测试"的路线图。
- 不解决**主观质量主导的项目**（文案、视觉风格、研究结论）：它们缺的不是结构，是可判定的目标。
- 不解决**一次性脚本、寿命很短的脚本**：为它们做的分层、登记面、版本闸门成本高于收益。
- **不替代"怎么设计验证体系"**：本 skill 只产出可被机械取证的结构前提（B 组）与模块化框架契约（I 组），
  真值口径、门禁分级、判别力证明见 `testing-for-ai`；文档分层、准入、防漂移、交接见 `docs-for-ai`。
  模块级**测试/label/断言计数/并行可跑性**见 `testing-for-ai`（A6/B17/B18/C6）；模块级**文档最小集与对账**见 `docs-for-ai`（B6/C5/A5）。
- **邻居与"12 组重叠规则"的权威分配**：见 `README.md` 的「与相邻 skill 的分工」表。
- 本 skill 的取舍来自特定工程（桌面应用 + 命令行 + AI 读写同一批数据），**换栈要重新判断**，详见 `REFERENCE.md`。
