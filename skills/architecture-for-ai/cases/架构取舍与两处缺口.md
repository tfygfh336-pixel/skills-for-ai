# 案例：某 Electron 桌面笔记应用的架构取舍与两处缺口

**阅读约定**：本文刻意脱敏——不出现工程名、仓库路径、盘符、门禁编号、脚本名、命令名。
所有数字都是**实测记录**，且是 **2026-09 的快照** —— 易腐数字（行数、模块数、条目数、耗时）**只当量级用**，
现状以工程自身为准。"取舍"与"缺口"部分照实写，包括没做成的事。

**背景**：一个本地桌面笔记/知识整理应用（Electron 外壳 + 浏览器渲染层 + 一个命令行入口），
数据以 JSON 文件形式存在本地目录里。**两类使用者**：人用图形界面改，AI 用命令行改，
两者对同一批数据读写。这个"人机共用一份数据"的前提，决定了后面几乎所有取舍。

---

## 1 为什么选"单一逻辑源 + 薄壳"，放弃了什么

**当时的形态**：界面侧有自己的校验与序列化，命令行侧又有一套。两边的规则看起来一致，
但**表达方式不同**（一个在浏览器里从对象出发，一个从文件与参数出发）。

**选择**：把校验、转换、序列化、关系计算收进一个**双端可加载的共享模块层**；
命令行的最外一层只负责"接参数 → 调共享层 → 输出 → 置退出码"，界面也只负责展示与交互编排。
**界面不复制任何业务逻辑**，它的写操作经进程间通道交给共享层，再由共享层过校验闸门后落盘。

**放弃的东西（都是真的代价）**：
1. **放弃了各端各自的最优写法。** 共享层必须同时能在浏览器与独立进程里加载，
   于是不能用任一端独有的 API；需要环境能力时必须注入。共享层里的代码**看起来更啰嗦**。
2. **放弃了"界面自己快速修数据"的便利。** 界面上任何写都必须绕一圈到共享层，
   即时的、纯前端的"改一下就好"被禁止。代价是延迟与实现复杂度上升。
3. **放弃了单一入口的简单性。** 有两类使用者 ⇒ 必须同时维护两个入口的契约；
   这也直接引出后面第 4 节的并发问题（**这是这个选择的必然账单，不是意外**）。

**换来的**：规则只写一处，两个入口行为一致；同时也意外地为第 2 节的收益铺了路——
因为判定逻辑不再依赖浏览器环境，它就可以被直接调用。

## 2 进程内可调用的入口：实测收益与代价

**问题**：集成断言原先只能靠"起一个子进程跑命令行"，每条断言都要付一次进程冷启动。
实测 **~0.73 s/条**，共 140 余条 ⇒ 整段约 **102.1 s**。成本高到没人愿意在每次改动后跑。

**做法**：把命令行入口的最外层拆开，中间层做成**可在同一进程内调用的函数**（返回退出码与输出文本），
最外层只剩"接进程参数 → 调用 → 落地输出"。两条硬约束写进了实现：
① **不得调用会立即结束进程的 API**（宿主可能是测试进程、编辑器主进程或常驻服务，被连带杀死）；
② **退出码是全局状态，进出都要隔离**（校验类命令会自行置非 0 表达失败，
所以退出码必须被**读回**，不能只看调用有没有抛错）。

**实测收益**：同一段集成断言 **102.1 s → 4.8 s**（约 21 倍；同期断言条数由 140 增到 144）。
另一轮记录到的数字是 **4.2 s**（约 24 倍）—— 差异来源未查明，**以 4.8 s 为准**（见文末"不确定"）。

**代价（三条，都是真的）**：
1. **入口必须做成可从外部调用。** 这要求把"参数解析 + 执行 + 输出"从"进程生命周期"里剥离，
   原先混在一起的错误处理路径必须重排（否则退出码会漏读）。
2. **退出码与输出文本变成了对外契约。** 一旦有调用方（常驻服务、编辑器主进程、测试）依赖输出文本，
   内部重构就可能破坏它。为此必须先写**契约快照**（退出码 + 输出文本逐字节），再改内部，
   改完用逐字节比对证明等价——**顺序反了就会"断言变快了，但断言测的东西也变了"**。
3. **同步入口需要一条可机械把守的不变量。** 为了支持直线式同步断言序列，
   另提供了一个同步入口，它依赖"命令体在首个异步点之前同步执行"这一语言特性。
   这条不变量由一条静态检查守死，违反时**立刻抛错、不静默降级**——
   没有这条把守，某次改动后同步入口会静默半途返回，而断言照样"全绿"。

**一个顺带的判断**：这次改造的价值不只是"快"，而是**把"愿不愿意验证"从成本问题变成了非问题**。
它没有改变任何判定内容（逐字节比对证明对外行为未变），这正是"薄壳"设计在结构上给的红利。

## 3 归一化取景后截图逐字节可复现

**问题**：为了让"界面是否画对"能被机器判定，需要截图产物**可复现**。
实测：同一台机器、同一输入，连跑 **4 次**，图像尺寸恒定（1424×835），
但 **4 次哈希全不同**（字节差约 1.2%）。

**根因**：状态栏写了**本地时间串**（"已保存 12:30:05"）且**落在截图范围内**。
而流程末尾恰好会触发一次保存 ⇒ 时间串每次都不同 ⇒ 画面每次都不同。
根因不在"截图技术"，而在**一个把非确定信息放进可观测画面**的产品行为。

**改造（四处，各自对应一个非确定来源）**：
1. **固定窗口尺寸**并**显式传入**（此前只传了"不显示"，尺寸走的是框架**默认值**——默认值不是固定值，
   它会随框架版本漂移。这是一次被记录下来的误判："别再把默认值当固定值"）；
2. **新增采集前准备**：展开全树、禁过渡动画、**清空状态栏文本**、等待**若干帧**再采集
   （此前只有一个固定睡眠，那不是"等稳定"，忙时必偶发红）；
3. **落盘一份采集记录**：分辨率 / 字节数 / 哈希 / 像素统计，供后续比对；
4. **像素统计收敛到单源**（此前两处各写一份，其中一处还依赖**通道顺序**这个未承诺的实现细节）。

**实测结果**：改造后连跑两次，尺寸相同、像素统计完全相同、**字节差 0**（哈希一致）。
⇒ 原计划里"相似度阈值"的判据**直接不需要了**。这也印证了一条顺序：**先消除非确定来源，再谈放宽判据**。

**附带发现的一个真实缺陷**：像素统计原先按一种通道顺序读位图，而框架文档明确写着该格式
"**平台相关**"。也就是说"统计出差异"完全可能来自通道身份，而不是画面内容。
做法是把统计量改成**与通道顺序无关**的形式；并用一个"通道互换"的合成输入验证：
旧口径确实敏感，新口径完全相同。**判据依赖未承诺的实现细节，本身就是缺陷源。**

## 4 并发版本闸门与原子写

**问题**：人用界面改、AI 用命令行改，**两者会撞**。已经实测出两条丢数据的路径：
① 界面内存里是子集时整树写回，会把其他笔记删掉（**曾 7 篇变 5 篇**）；
② AI 在界面打开期间写入的笔记，被界面随后的一次保存覆盖。

**设计**：读取数据时**一并返回内容指纹**；写回时如果调用方声明了"我读到的是哪一版"，
盘上必须仍是那一版，否则**拒绝写入并报出两侧版本号**。关键点是：
**界面保存与命令行写入共用同一个闸门**——只要有一个入口不检查，闸门就等于不存在。

**为什么指纹必须是内容哈希（而不是修改时间/文件大小）**：修改时间的粒度粗到"同一秒内两次写分不开"；
文件大小在"原地改一个字段"时**完全不变**。两者都会让闸门**静默失效**——
看起来有保护，实际没有。这是最坏的失效方式。

**为什么选择"拒绝"而不是"自动合并"**：在这个场景里，**静默丢数据是最重的损害类别**，
而"自动合并"在当时无法证明不丢数据。所以把冲突推给人处理（多一次人工介入）换取"不丢"。
**代价写在明处**：冲突时使用者会被打断一次。

**一个由这次设计暴露出的隐蔽漏洞**：有些字段**只存在于磁盘上、页面从没见过它**。
页面保存时用空值写回就会把它抹掉。正确做法是"页面没带这个字段时从磁盘取回"，
但这不能靠猜——**必须用指纹闸门区分"我把它清空了"与"我没见过它"**。
这个过程还暴露了一个真实教训：最初只在某一个字段上打了"磁盘优先"的补丁，
**节点树没有**同样保护；统一闸门补的就是这个不一致。

**原子写**：写盘一律 同目录临时文件 → 落盘 → 重命名 覆盖正式文件；失败时清理临时文件、正式文件保持原样。
理由很直接：**中断留下半截 JSON，会让数据不可读，而且原内容已被破坏**——这是不可逆点，
值得为它多付一次重命名与落盘等待。

## 5 两处未解决的缺口（照实写，这是本文的价值所在）

### 缺口一：没有版本控制 ⇒ 无回滚（外部阻塞）

**事实**：这份工程**至今零提交**。仓库初始化成功，但写入版本库内部对象时被**企业侧的安全软件拦截**。
需要企业为该目录加排除规则才能获得版本回滚能力。**在此之前，唯一兜底手段是把数据整体导出到工程目录之外的备份**。

**这不是"没做"，而是"做不了"，且它造成了实际损失**：
- 一次**目录级事故**把整个工程（源码 + 文档 + 笔记数据）**一次性清空**。
- 恢复手段是**从会话轨迹里逐帧提取写入调用、重放重建**代码，缺失的模块按架构约定重写，
  知识体系按教材结构重建。
- **恢复是不完全的**：某个知识库原有 44 个条目，重建后有 36 个条目，
  部分条目的**详情文字与图片无法恢复**。产出的安装包与截图可以重新生成，但人工内容不能。

**诚实标注**：当前状态被文档明确写成"本地版本控制至今无任何提交，
在此之前把数据导出到工程外目录是**唯一**的兜底手段"。
这正是 G1/G2 要求的做法：**能力缺失要被显式声明为风险**，而不是默认没事。
"每步先备份 + 记前后哈希"在这里只是**弱等价**：它不能分支、不能二分定位、
不能原子回滚一整批改动、也不能区分"我改的"和"别人改的"。

### 缺口二：主进程仍是千行级的多职责单文件 —— 而且缺口不止在主进程

**事实**：渲染层已被拆成十多个模块（视图、详情框、媒体、审计面板、命令面板、
关联笔记页、动作与保存闸门、接线层、交互层……），**多数**模块的职责能一句话说清。
但**主进程侧仍是约 880 行的多职责单文件**：窗口创建、进程间通道处理、菜单、冒烟驱动、导出全在一处；
而侧栏初始化后来被单独拆出一个**同样约 880 行**的文件 ⇒ 今天主进程侧有**两个**千行级文件，不是一个。

**而且缺口不止在主进程**：挑出来的那些渲染模块里，有一个视图模块自己长到了**千行以上**
（统一视图变换 + 视口接线 + 面板锚定 + 主题模式 + 拖动树 + 展开收起），**比主进程那个还大**。
⇒ 准确的说法不是"一边拆好了、一边没拆"，而是"**按文件拆开了、按职责没拆开**"：
把函数搬进新文件不等于把职责分开，而 AI 判断"该改哪里"靠的正是职责边界。

**为什么这是缺口（不是"风格问题"）**：
1. **职责边界不清导致 AI 的行为不均。** 边界清楚的模块，改动有"该改哪个文件"的确定答案；
   千行级多职责文件的改动永远是"在里面找位置"，于是**同一类任务的成功率在两处明显不同**。
2. **它破坏了 A2 的可检查性。** 单向依赖没法在这样一个文件里被搜索验证——它同时是壳、是编排者、也是业务判断的所在地。
3. **它是改造的盲区。** 自动化断言主要覆盖共享层与命令行，主进程侧的多职责代码**天然难以被无头覆盖**，
   于是它成了"最容易改坏、又最难发现"的区域。

**为什么至今没拆（如实说）**：它不在"损害最重的类别"里——它不会静默丢数据、不会让人得出错误结论；
而拆分一个有窗口生命周期与进程间通道的常驻文件，**风险集中在"改坏启动路径"**，
在当时缺回滚能力的前提下（见缺口一），收益/风险比不划算。**这是一次被明确记录下来的"暂时不动"，
不是遗忘。**

## 6 一次真实事故：两份副本 + 反复单向同步 ⇒ 必然丢工作

**结构**：同一份工程存在两份副本（一个工作区副本 + 一个盘上的副本），
**两边已经双向发散**：有人在盘上那份实现了"发版时把旧版本段滚动归档"的功能（盘上有若干归档文件），
而工作区副本没有这个功能。

**触发**：随后一次**单向**同步（从工作区推向盘上那份，且**不加清理目标目录的开关**）。

**后果（精确地说）**：
- 盘上那些**较新的文件被换成了旧版**（实现该功能的代码没了、登记这些归档产物的登记表行也没了）；
- 而同步工具**不清理目标**，于是归档产物本身**幸存**下来；
- 最终状态是"**产出它们的代码没了、登记它们的行也没了，但产物还在**"，
  于是一条"文档/产物是否被登记"的检查报出十几处"表外文档"。
  **报错地点与真实原因相距极远**——这是这类事故最贵的地方：它浪费的是别人的排查时间。

**丢过两次**：同类损失发生过两次。两次的恢复手段都是**从会话日志里逐帧重放**那一侧的写入
（因为并行一方的写操作还留在会话日志里）。恢复成本的量级由"日志里有多少帧"决定，而不是由"丢了多少"决定。

**结论（支撑 G1/G2 与 H5）**：
1. **多副本 + 单向同步不是"有风险"，而是"必然"丢工作**：因为两边会独立演化，
   而同步工具的方向与清理策略不会告诉任何人它刚刚覆盖了什么。
2. **"备份"必须是被改目录之外的、单向只读的**；同目录的第二份副本不是备份。
3. 事件发生后正确动作是**先停写、先定权威**，再决定恢复方向——
   本次正是这样处置的（在决定权威之前停止了一切跨副本写入）。
4. **判据不是"有没有副本"，而是"能不能回到上一版"**。两份副本给出的回滚能力是**零**。

## 附：本文未覆盖 / 不确定

1. **进程内改造的耗时有两个记录值（4.8 s 与 4.2 s）**，来自不同测量轮次，差异来源未查明（**以 4.8 s 为准**）。
2. **"自动合并冲突"未验证**——本文只证明了"拒绝写入"这一种策略在本场景可行，不代表自动合并不行。
3. **缺口二的拆分没有做过可行性验证**（没有拆过、没有估算过工作量），
   所以"风险集中在启动路径"是**判断**，不是实测结论。
4. **所有数字来自单机、单写者为主的场景**；多人并发、多分支、网络文件系统下的行为**未验证**。
