# REFERENCE — 机制层：落地做法、权衡、失败模式、实测证据

本文件是 `SKILL.md` 的展开。决策层给"该不该这么做"，本文件给"具体怎么落、代价是什么、会怎么坏、凭什么这么说"。

**证据标注约定**：`[实测]` = 在真实工程里被观察到并留有记录的现象；`[推断]` = 从机制推导、未单独复现；
`[未验证]` = 我无法确认的。**本文件里的取舍都来自特定的"桌面应用 + 命令行 + AI 读写同一批数据"型工程，
换栈（Web 服务、嵌入式、数据管道、库）必须重新判断**——见文末《哪些是权衡、不是定律》。

## A 单一真源与分层

### A1 单一逻辑源 + 薄壳
- **怎么落**：把逻辑收进一个被多方共用的模块层（同一份代码同时能被独立进程与界面进程使用，
  例如 UMD/ESM 双端可加载，或抽成独立包）。壳只做"参数 → 调用 → 输出"。
  壳的判据很简单：**删掉壳，逻辑仍然完整可用**；壳里有 `if` 判断业务规则就是漏了。
- **真正的收益不是"优雅"**，是**变更成本可预测**：加一条规则只改一处，且所有入口同时获得它。
- **权衡**：共享层不能依赖任何一端的环境（不能用 Node 专属 API，也不能用 DOM 专属 API）。
  这层限制是价格，不是缺陷。若共享层需要环境能力，用**注入**（传参）而不是 import。
- **失败模式**：① 壳里"就这一次"复制了一段判定 → 半年后两处判定不同，症状是"界面能存、脚本不认"；
  ② 为了共享而共享，把纯展示逻辑也塞进共享层，于是共享层开始依赖样式与 DOM。
- **实测**：某工程把校验/转换/序列化收进共享模块后，新增命令无需在界面侧再写一遍，
  "界面保存的数据命令行不认"这类问题消失；代价是共享层必须保持"无环境依赖"。

### A2 单向依赖，禁回边
- **怎么落**：先写下允许的层序（例如 壳 → 逻辑 → 数据），再写一条**可机械检查**的规则：
  底层目录的 import 里不得出现上层目录名。
- **权衡**：单向依赖会让"底层触发上层动作"变麻烦，必须改成"底层产出事件/返回值，上层决定动作"。
  这是正确的负担转移：底层不需要知道通知渠道，才能被复用与无头测试。
- **失败模式**：一旦出现回边，单测底层就必须拉起整个应用；无头路径随之不可得（B3 被连带破坏）。
- **实测**：数据写入层保持"不知道界面存在"后，同一份写入逻辑能同时被命令行、被主进程、被测试直接调用。

### A3 同一事实禁止两处表达（含文档与代码之间）
- **怎么落**：把易腐事实分三类处理——① 能算出来的：生成（见 D4）；② 必须手写的：选**唯一权威副本**，
  其他文档只放**指针 + 执行该动作当场需要的条目**；③ 历史：归档且不进活跃视野。
- **权衡**：单源要求"引用方不完整"（文档不再自足）。这是刻意的：**不完整但不漂移**优于**自足但两份**。
- **失败模式**：规则清单在两份文件里各写一份，数字不同；更糟的是**漂移掉的恰恰是最关键的那条**，
  于是"读到的规则"与"实际执行的规则"不是同一套——而团队以为是一套。
- **实测**：一次自洽性检查在真实工程里抓出三处真缺陷（标题声明条数与表格行数不符；一个表格被引用块打断，
  三行门禁静默掉出表格、渲染成纯文本；摘要文件漏掉一条最关键规则）。**这些都是"抄了一份"的必然后果**。

## B 可机械取证的结构前提

### B1 一条命令判定
- **怎么落**：每个不变量配一个入口，输出"对象 + 期望 + 实际"，以退出码表达成败。
  报告型入口（批量校验）也用非 0 退出码表达失败，且**与输出格式无关**。
- **判据（最重要的一条）**：判定"改动是否可接受"的依据不是"测试是否还绿"，
  而是"**人按原有习惯操作得到的是否还是设计意图**"。所以改完要能回答：
  默认路径（不传新开关）的行为是否**逐字未变**？新行为是否只在 opt-in 时出现？
- **失败模式**：把"测试还绿"当验收 ⇒ 优化了没人走的路径、弄坏了每天走的路，却全绿。
- **实测**：某次以"更严谨"为名的改动，让默认输出变了，判据退化；纠正方式不是回滚抽象，
  而是把新能力改成 opt-in，**不加开关时输出与从前逐字节相同**。

### B2 进程内可调用的入口
- **怎么落**：把命令行入口做成 `invoke(argv) -> {code, stdout, stderr}` 的纯函数（可再加同步版供直线式断言）；
  最外包一层壳负责 `stdout/stderr` 落地与 `process.exitCode`。两条硬约束：
  ① **不调用 `process.exit`**（会连带杀死宿主进程：测试进程、编辑器主进程、机器人服务）；
  ② 进出**隔离 `process.exitCode`**（它是全局态，且校验类命令会自行置非 0 表达失败，
  所以退出码必须**读回**，不能只看"抛没抛错"）。
- **同步版的不变量**：若提供同步入口，必须有可机械把守的约束（命令体不得出现 `await`/`.then()`/
  异步文件 API），违反时**立刻抛错、不静默降级**。没有这条把守，同步入口会在某次改动后静默半途返回。
- **实测收益**：集成断言从"每条起一个子进程"改为进程内调用后，同一段断言从 **102.1 s 降到 4.8 s**
  （约 21×；断言条数同时由 140 增到 144，故"每条约 0.73 s 冷启动"这个基线成本不变）。
  另有一轮记录到 **4.2 s**（约 24×）—— 差异来源未查明，**引用时以 4.8 s / 约 20 倍为准**（见文末《未验证/不确定》）。
- **代价与前提**：入口必须做成可从外部调用，于是**退出码与 stdout/stderr 变成对外契约**，
  一旦有人依赖文本输出，重构就会破坏它。因此改造顺序是：**先写对外契约快照**（退出码 + 输出逐字节），
  再改内部；改完用逐字节比对证明"行为等价"。用子进程路径跑对照断言，是证明进程内路径没有偷偷改变语义的唯一办法。
- **失败模式**：没有契约快照就改 → 断言变快了，但**断言测的东西也变了**，且没人发现。

### B3 无头路径
- **怎么落**：① **固定窗口/画布尺寸**：显式传尺寸，不要把框架默认值当固定值（默认值会随框架版本漂移）；
  ② 离屏运行（不弹桌面、不抢焦点）；③ 隐藏状态下**仍然出帧**——需要显式开启绘制与关闭后台节流，
  否则定时器降频、动画帧暂停，截图拿到旧帧或黑屏；④ 等"渲染稳定"用**若干帧 + 关键状态清空**，
  而不是固定 `sleep`。
- **权衡**：离屏带来的新失败类别是"藏住了但不出帧"。必须用一条像素统计断言守住它（非空、非纯色）。
- **失败模式**：① 验证时窗口弹在用户桌面；② 隐藏窗口被节流 ⇒ 断言读到旧帧却不报错；
  ③ 用固定 sleep 代替"等稳定" ⇒ 忙时必偶发红、闲时全绿，于是大家学会"重跑一次"。
- **实测**：一次"隐藏窗口但截到黑屏"的次生回归被新增的像素统计断言抓到；
  `backgroundThrottling` 与"未显示也绘制"两项是抓它之后才补上的必需配置。

### B4 纯逻辑下沉
- **怎么落**：判定、转换、校验、排序、剪枝、路径处理都是纯函数；I/O、时钟、随机、环境从**参数注入**。
  自检方法：**这个模块能不能在一个不存在的目录里被调用？** 能，就下沉成功了。
- **权衡**：纯函数化会让调用方多传几个参数（看起来啰嗦），换取的是"无需准备环境即可测试"。
- **失败模式**：把"读盘 + 判定 + 写回"写在一个函数里，导致：判定规则无法单独验证、
  错误信息无法定位到"是数据坏了还是写入坏了"、且任何测试都要造真实文件系统。
- **实测**：把引用关系计算、链接剪枝、内容解析等下沉为纯模块后，单测数量与覆盖同时上升，
  且这些模块能被界面与命令行**共用**（因为不依赖 I/O），A1 的收益在 B4 上二次兑现。

### B5 确定性产物
- **怎么落（按顺序）**：
  1. 找非确定来源：本地时间串、随机 id、并发完成顺序、框架**默认值**、动画中间态、字体/缩放/设备像素比；
  2. **消除**它们：把易变字段移出产物、或做成显式参数；状态类文本（如"已保存 12:30:05"）
     要么不参与产物，要么在采集前清空；
  3. 采集前显式等待稳定（B3 的顺序语义：先行为、后画面）；
  4. **全部消除后仍不可复现，才放宽判据**（比对结构化字段、或比阈值），并在文档里写明放宽的理由与残余风险。
- **为什么顺序不能反**：先放宽判据 = 把真实回归藏进噪声。放宽是**失败的承认**，不是设计的开局。
- **实测**：某工程截图改造前同输入连跑 4 次，尺寸恒为 1424×835 但 **4 次哈希全不同**（字节差 ~1.2%）；
  根因是**状态栏写了本地时间串且落在截图范围内**。改造后连跑两次**字节差 0**（sha256 一致、像素统计完全相同），
  于是原计划的"相似度阈值"判据**直接不需要了**。
- **一个易错细节**：像素统计若依赖通道顺序（RGB/BGR），而框架文档明说该格式"平台相关"，
  那么"测出来的差异"可能来自通道身份而不是画面。做法是让统计量与通道顺序**无关**（加权亮度/三通道均值）。
  这类"依赖一个没有承诺的实现细节"的判据，本身就是一个缺陷源。

## C 为"上下文有限"设计接口

### C1 窄接口
- **怎么落**：把"高频小问题"各自变成一个命令/函数（某 id 的入边、某文件属于哪层、某符号被谁引用），
  返回值只含该问题所需字段；不要"先读全量再让调用方筛"。
- **权衡**：窄接口会变多（接口表变长）。控制方式是**粒度分层**（C2），而不是把窄接口合并成大接口。
- **失败模式**：只有全量导出 ⇒ 每个小问题都付全量代价；一旦规模超过上下文上限，
  使用者会开始"抽样读"——于是判断建立在残缺信息上，且没有任何信号提示这件事。
- **实测**：某工程为不同粒度各设了一档输出（骨架 / 摘要 / 单条 / 按子树）。
  实测同一棵树：全量 ~212 KB、摘要 ~44 KB、骨架 ~30 KB、骨架 + 子树 ~21 KB。
  ⇒ **同一个问题用不同粒度问，代价差 10 倍**；缺档位时人只能选全量。

### C2 粒度分层
- **怎么落**：至少三档，并**明确每档丢了什么**（把"丢了什么"写进文档与命令帮助里）。
  建议档位：仅结构（无正文）/ 带导航字段（标签、链接）/ 全量 / 指定子树。
- **权衡**：档位越多，语义重叠越容易出错（"摘要"和"骨架"到底谁包含谁）。必须写清包含关系，
  并用测试锁住"某一档确实不含某字段"。
- **失败模式**：两档之间缺少一档 ⇒ 中间需求靠全量；或两档语义重叠且互相覆盖，使用者无法预测会拿到什么。
- **实测**：某工程发现"带导航字段档"保留了标签与链接、"列表档"是扁平结构，
  于是"**只要结构不要正文又要嵌套**"这个中间需求无档可用，补一档后同一棵树的输出从 ~44 KB 降到 ~30 KB。

### C3 读取成本上界
- **怎么落**：① 生成索引，让查询打索引而不是扫目录；② 给高频入口定"字节量级上界"并**写下来**（可被测试）；
  ③ 只增文件（变更日志、归档、快照）必须靠"检索入口"访问，不能靠"整份读"。
- **权衡**：索引是一份派生数据（D4），必须能被重新生成，否则它自己成为新的单源风险。
- **失败模式**：① 成本随项目年龄线性增长 ⇒ AI 的有效上下文逐年下降，表现为"越到后期越容易改错/改漏"，
  而没人把它归因到结构上；② 用 mtime/size 之类的指纹做"版本"，看似便宜，实则**静默失效**（见 D2）。
- **实测**：某工程给历史条目提供了"按段/按关键词检索"的窄查询，索引从正文**现算**、不落副本，
  理由是"落一份生成物就要维护它不过期，而它只是检索加速"。

### C4 变更历史窄查询
- **怎么落**：只增历史 + 一个"关键词/段号"检索入口；查不到时输出**指路**
  （"主文件里没有，不等于没发生过，更老的段在归档目录里"）。归档规则与活跃区不同：只增不改、不进数字扫描。
- **权衡**：归档会让"完整历史"分裂在多处，因此检索入口必须同时覆盖归档，否则"查不到"会被误读成"没发生"。
- **失败模式**：整份历史进上下文（实测某工程的历史文件达 ~280 KB / 数千行，且每次改动都要被读）——
  它同时污染上下文与信噪比。
- **实测**：把已发布版本段滚动归档后，主文件从 2920 行降到 2788 行（**只省 5.1 KB**）。
  诚实结论：**膨胀主要来自未发布段的积压，不是历史**；归档解决的是"检索与视野"，不是"体积"。
  这正是"先测量再改动"的价值——若不测，会以为归档解决了体积问题。

## D 为"人机并发"设计数据层

### D1 唯一写盘闸门
- **怎么落**：只有一个写函数，且它内部顺序固定：**校验 → 版本检查 → 原子写**。
  评审规则：搜索裸写文件调用，任何非闸门的写路径都是缺陷（迁移脚本也不例外，或明确标注例外）。
- **权衡**：所有写路径都被这一处串起来 ⇒ 它成为热点与风险点，必须被测试重点覆盖（含坏数据、并发、中断）。
- **失败模式**：① "临时脚本直接改文件"绕过校验与原子性；后来被当成常规做法；
  ② 闸门只覆盖"结果非法"（校验），不覆盖"绕过流程"——手改能写出**合法但错误**的数据。
- **实测**：某工程明确"数据改动一律走同一个入口，不直接手改数据文件"，理由是校验闸门兜不住"绕过去"。

### D2 并发写入即版本闸门（本组最重要）
- **怎么落**：读操作**一并返回内容指纹**（如内容哈希前若干位）；写操作接受"我读到的是哪一版"；
  写前比对盘上指纹，不同则**拒绝写入并报出两侧版本号**。
  **界面保存与命令行写入共用同一个闸门**——只要有一个入口不检查，闸门就等于不存在。
- **为什么不能用 mtime/size 当版本**：mtime 粒度粗到"同秒两次写分不开"；size 在"原地改一个字段"时完全不变。
  两者都会让闸门**静默失效**——这是最坏的失效方式（看起来有保护，实际没有）。
- **权衡**：拒绝写入会把"冲突"推给人处理（增加一次人工介入），换取的是**不丢数据**。
  在"静默丢数据是最高损害类别"的场景里，这个交换是划算的；反过来，若数据可重算，闸门就是多余成本。
- **失败模式**：整树写回。实测两条路径：① 内存里只有子集时整树写回，把其他条目删掉（**7 篇 → 5 篇**）；
  ② AI/命令行在界面打开期间写入的内容，被界面一次保存覆盖。
  还有一种隐蔽形态：某字段只在磁盘上、页面从没见过它，保存时用空值写回 ⇒ 该字段被抹掉；
  正确做法是"页面没带这个字段时从磁盘取回"，但**不能靠猜**——要靠指纹闸门区分"我清空了它"和"我没见过它"。
- **实测**：先在单一字段上打了"磁盘优先"的补丁，后来发现**节点树没有**同样的保护，才补上统一闸门。

### D3 原子写
- **怎么落**：同目录临时文件 → 写入 → fsync → rename 覆盖正式文件；失败时清理临时文件、**正式文件保持原样**。
- **权衡**：比直接写多一次 rename 与一次落盘等待；换来"中断不留半截文件"。
  注意临时文件必须**同目录**（跨盘 rename 不原子）。
- **失败模式**：断电/异常中断导致正式文件半截，解析即崩，且**原内容已被破坏**——原子写防的就是这个不可逆点。
- **实测**：写盘闸门的行为被单测锁住（目标文件逐字节不变、临时文件被清理）。

### D4 可派生的不手写
- **怎么落**：生成物（命令清单、真值计数、格式说明）+ 一条"是否过期"的逐字比对。
  生成物头部写"请勿手改 + 重新生成命令"。生成物的**输入**必须是单源（注册表/常量/源码扫描），不是人脑。
- **权衡**：生成物是"第二份表达"，但它由机器维护且被比对守住，所以不会漂移；
  代价是构建/校验多一步，且生成器本身成为要维护的代码。
- **失败模式**：① 生成物被人手改 ⇒ 下次生成覆盖掉手改内容（且没人知道他改过）；
  ② 生成器从错误的源生成（例如从文档生成文档）⇒ 把漂移固化。
- **实测**：某工程把"命令清单"与"验证计数"做成生成物并用门禁校验是否过期；
  但明确**不**把"检索索引"做成生成物（它只服务检索、落盘就要维护不过期），**取舍是按"是否有独立价值"定的**。

## E 为"AI 会漏连带"设计登记面

### E1 新增产物的登记面
- **怎么落**：三个清单 + 一处报错指路：① 根目录白名单（只允许入口文档与工程配置文件）；
  ② 顶层目录白名单；③ 工作产物区（**唯一**杂物区：可整目录删除、进忽略清单、不进数字扫描、不算文档）。
  报错信息必须直接写出这三条去向（"放工作产物区" / "登记到文档表" / "改已有的那份"）。
- **权衡**：白名单要人维护，新增合法文件时要同批登记——这是"多一次登记"换"扫描器不会误判"。
- **失败模式（实测）**：在工作产物区放了一个测试文件，因为测试收集器的默认包含规则覆盖了它，
  整个测试套件变红。后果不是"坏了"，而是**让人得出错误结论**（以为改动破坏了什么），
  真实原因只是"两个口径不一致"（工作产物区的口径 vs 收集器的口径）。
  修法是让两者一致（收集器显式排除该区 + 把它加进根白名单）。
- **实测（同一工程）**：新增一个截图产物落在工程根，被"根目录白名单"判为乱放，于是**同批**把它加入白名单与忽略清单。
  这条规则的价值在于：新增产物时**会被提醒**，而不是几个月后在别处爆红。

### E2 规则放在动作现场（信息架构）
- **怎么落**：
  1. 先列"高频动作清单"（新建文件、加一个入口、改数据格式、发版……），每个动作问一句：
     "执行者在这一刻**必然会看到**什么？"（命令输出、报错文本、文件头、函数注释、新会话第一屏）。
  2. 把该动作当场需要的条目放在那里；集中式权威副本只放**指针**与全量。
  3. 成本的量度：**规则字数 × 出现位置数**。远处出现的规则近似等于不存在。
  4. 关系型约束（"改 A 必须连带改 B"）要写成**可机械检查**的形式（见 E1），否则它只是一个愿望。
- **权衡**：把规则分散到现场会让"全局一致性"变难 ⇒ 必须同时保留一份权威副本 + 一个自洽性检查
  （声明条数 == 表格行数、引用编号闭合、被点名的实现存在、其他文档转述的条数一致）。
- **失败模式（实测）**：规则清单曾在多个文件里各写一份并漂移（某文件列 7 条、另一份列 6 条），
  且**漂移掉的恰恰是最要命的那条**；又曾出现"某条规定禁止用某工具读写文档，但**全程没有任何东西会报警**，
  而规则作者本人违反了它"——这条规则当时只是一句话，没有现场、没有检查。
- **一个反直觉结论**：把规则放在"新会话第一屏"比放在长文档里有效得多，因为**新来的执行者不读完整文档**。

## F 为"AI 会犯低级错"设计容错

### F1 失败必须响亮
- **怎么落**：错误路径必须走"打印 + 非 0 退出码"；跳过/降级必须显式打印"跳过了什么、为什么"；
  "无法判定"要有**独立于"通过"**的表示（第三个状态），不能与通过同色。
- **权衡**：响亮失败会让"偶发红"变多（例如环境缺失时不再静默跳过）——这是要的，
  因为它把"假绿"换成了"明确的红"。
- **失败模式**：① 坏状态自动降级为默认值（解析失败给空对象）；② 采集不到数据就跳过该断言（"没测"看起来像"过了"）。
- **实测**：某工程明确规定"采不到目标区域 = 红，不跳过"；并且把"坏状态报错、不降级"写进实现
  （例如运行时包解析失败时报错，而不是退回另一个来源继续跑）。

### F2 编码卫生
- **怎么落**：所有文本产物显式 UTF-8 **无 BOM**、统一换行；写文件用能明确指定编码的工具链；
  **禁止用会写 BOM 或使用非 UTF-8 默认代码页的工具做"读 → 改 → 写"往返**。
- **权衡**：没有；这是纯收益项。代价只是"不能用最顺手的那个命令"。
- **失败模式（实测）**：用某种"读原始文本再写回"的 shell 往返修改一份 UTF-8 文档，
  在默认代码页非 UTF-8 的环境下**同时引入 BOM 与乱码**（中文全坏），只能从会话轨迹里提取权威版本重建。
  注意它的隐蔽性：命令**没有报错**，文件看起来"写成功了"。
- **另一个隐蔽点**：临时产物区也可能被扫描/入库/被下一步读取 ⇒ "临时的"不是"可以不管编码"的理由；
  用命令行工具测字符长度时也可能量错对象（多行输出被折成数组，量到的是**行数**而不是字符数）。

### F3 不要把不可自动判定的东西做成硬门禁
- **怎么落**：门禁只锁可机械判定的（结构、计数、存在性、逐字比对、哈希、退出码）。
  主观项（命名好坏、是否优雅、文案质量）做成**人工确认清单**，只提示不判红。
- **权衡**：把主观项排除在门禁外，意味着它靠人把关；但把主观项放进门禁的两种结局都更差（长期假红 / 被迫永远通过）。
- **失败模式（实测）**：曾想给一个"看起来该测"的区域加断言，但该区域在采集前被**刻意清空**过，
  于是断言会**永远判红**。这类"看起来该测、其实不能测"的项，必须在代码注释里写明原因，否则会被后人加回来。
- **相关**：某项"是否有判别力"也需要证据。某工程发现测量工具的读数依赖一个**平台相关**的实现细节，
  于是把判据改成与实现细节无关的形式——**判据依赖未承诺的实现细节 = 判据自身是缺陷源**。

## G 回滚与不可逆

### G1 必须有版本控制
- **怎么落**：能上就上；不能上时把它当作**已声明的风险**写进文档，并明确"当前没有回滚能力"。
- **权衡**：版本控制本身有成本（忽略清单要维护、大二进制会膨胀），但"没有它"的代价是**每次改动都是单向门**。
- **失败模式**：① 靠"另一份副本"替代版本控制 ⇒ 见 H5；② 有版本控制但从不提交（本机提交被安全软件拦截等），
  于是"有 git"只是一种错觉——**判断标准是"能不能回滚"，不是"有没有 .git"**。
- **实测**：某工程版本控制在环境层被拦截、**至今零提交**；文档明确写"在此之前，导出到工程外目录是唯一的兜底手段"。
  这是"能力缺失被如实标注"的正面例子：它把风险变成了一个显式的、可被讨论的约束。

### G2 无版本控制时的弱等价
- **怎么落**：① 改动前把可整体回滚的备份导出到**被改目录之外**（同一目录的"备份"会与被改对象一起丢）；
  ② 记录改动前后哈希（证明"改了什么"，并为"是否等价"提供证据）；③ 在文档里写明**这是弱等价、不是等价**。
  弱等价缺什么：不能分支、不能二分定位、不能原子回滚整批、不能区分"我改的"与"别人改的"。
- **权衡**：每步备份 + 记哈希会拖慢改动节奏；但在无版本控制下，这是把"不可逆"降级为"可恢复"的最低成本手段。
- **失败模式**：① 备份与被改对象同目录（一次目录级事故全丢）；② 备份是手工的、没有哈希 ⇒ 恢复后无法证明恢复的是哪一版。
- **实测**：一次目录级事故把整个工程（源码 + 文档 + 数据）一次性清空，恢复手段是**从会话轨迹里提取写入调用逐帧重放**，
  重建后仍有部分数据无法恢复（节点数从 44 降到 36，详情文字与图片丢失）。
  ⇒ 教训不是"要小心"，而是"**没有回滚能力时的损失是不可逆且部分不可恢复的**"。

## H 反面清单的机制说明

- **H1 第二份实现**：两份实现的漂移不是"可能"，是**时间问题**——因为它们的修改者、修改时机、修改动机都不同。
  判据：只要存在"改 A 时不需要改 B"的错觉，B 已经开始漂移。
- **H2 兼容层承载核心能力**：兼容层的存在理由是"过渡"，一旦核心能力住在里面，
  所有调用方都依赖它，"过渡"变成"永久"，且它通常缺少核心能力应有的测试与约束。
- **H3 高频动作的新成本**：代价 = 单次成本 × 次数。最贵的改动不是"加了一层"，
  而是"给每天做 200 次的动作加了一步"。**新能力默认 opt-in，且不加开关时行为逐字不变**。
- **H4 "看起来更严谨"**：没有实测/事故支撑的抽象、分层、日志、门禁都是净成本。
  可操作的规则：**新增规则必须有一条真实事故或实测作为依据**；否则先记录假设，不动结构。
- **H5 依赖"没人会碰"**：多副本、软链、手工同步属于**结构性隐患**：
  ① 两边会独立演化（双向发散）；② 单向同步（不清理目标）会把**较新的文件换成旧版**，
  而同步工具不删的多余文件会**幸存**⇒ 出现"产出它们的代码没了、登记它们的行也没了，但产物还在"的诡异状态；
  ③ 恢复源往往存在于**会话日志**里，恢复成本极高。
  正确做法是**显式复位/隔离**：只保留一个可写单源，其他副本只读或删除；或者明确"停写"直到定权威。

## 结构自检该问哪些问题

按顺序问；前四问决定"这份东西能不能被长期改"，后四问决定"改了会不会丢/会不会漏"。

1. **同一件事有第二处表达吗？**（搜判定表达式、搜同一份清单、搜文档里的数字）——有 ⇒ A1/A3/D4。
2. **依赖方向是单向的吗？能不能指出一条回边？**——有回边 ⇒ A2（并检查它是否已破坏无头能力）。
3. **"算不算对"能不能一条命令判定？判定依据是"测试还绿"还是"人按原习惯操作得到的仍是设计意图"？**——B1。
4. **核心逻辑能不能在一个不存在的目录里被调用？**（不需要 I/O、时钟、网络）——B4；再问产物两次是否逐字节相同——B5。
5. **"该读哪一部分"有没有专门入口？成本有上界吗？会不会随年龄增长？**——C1/C2/C3。
6. **写盘出口有几个？读回来的版本指纹在哪？冲突时是拒绝还是覆盖？**——D1/D2/D3。
7. **新增一个文件/目录，会被谁判非法？报错信息有没有写"该放哪"？**——E1；
   再问"执行这个动作的人此刻会看到这条规则吗"——E2。
8. **这一步如果中断/写错/被并发覆盖，能回到上一版吗？**——G1/G2；不能则确认它被**显式标注**为单向门。

## 哪些是权衡、不是定律

以下全部是**特定工程条件下**的取舍。换栈时逐条重新判断，不要当规律背：

| 取舍 | 在什么条件下成立 | 换栈后可能反转 |
|---|---|---|
| 逻辑单源 + 薄壳，壳里零业务判断 | 同一逻辑被两个以上入口/进程使用 | 只有一个入口、且预计永不增加：单源仍有价值但不迫切 |
| 强制单向依赖、禁回边 | 需要无头测试与可替换的壳 | 极紧耦合的性能敏感路径（如内联到渲染循环）可能反向收益 |
| 版本闸门**拒绝写入** | 静默丢数据的损害远大于"多一次人工介入" | 数据可重算 / 写入方是唯一写者：闸门是多余成本 |
| 原子写（tmp→fsync→rename） | 中断不可接受、文件是权威单源 | 纯缓存/可再生产物：直接写即可 |
| 内容哈希当版本指纹 | 内容大小与频率都不极端 | 超大文件（哈希成本高）或内容顺序不稳定：需换方案 |
| 产物逐字节可复现 | 产物要参与判定/回归比对 | 产物体积巨大或本质随机（采样/渲染噪声）：放宽并**写明理由** |
| 生成物 + 过期比对 | 事实易腐且能从单源算出 | 生成器比手写更易错时：手写 + 单源权威副本更好 |
| 根目录白名单 + 工作产物区 | 有扫描器/收集器/门禁会遍历目录 | 无任何自动遍历：白名单只剩"人找东西方便"的价值 |
| 规则放动作现场 + 权威副本 + 自洽检查 | 由"新来的执行者"而非作者长期维护 | 单人短期项目：现场化仍是收益，自洽检查可能过度 |
| 离屏/无头验收路径 | 有界面且需要无人验收 | 纯后端服务：无头是默认，成本转移为"如何造真实负载" |
| 每步备份 + 前后哈希（无版本控制时） | 版本控制在环境层不可得 | 能上版本控制时它就是次优解，应尽快替换 |

## 未验证 / 不确定

1. **进程内改造的速度数字有两个记录值（4.8 s 与 4.2 s）。** **4.8 s（约 21×）**是工程侧的权威记录
   （同期断言由 140 增到 144）；4.2 s（约 24×）来自另一轮测量、差异来源未查明（机器负载／断言条数／测量口径）。
   两者我**都没有**独立复现。**引用时用"降到个位数秒、约 20 倍"。**
2. **"无头路径的收益"没有独立量化。** 只能说它是"无人验收"的必要条件；具体省下多少人工未测。
3. **C3 的"成本上界"阈值没有通用数字。** 本文件的量级（几十 KB 档、上百 KB 全量）来自特定工程的数据规模，
   不构成推荐值。**唯一可迁移的是"要有一个上界并被写下来"这件事本身。**
4. **D2 的冲突处理只覆盖"拒绝写入"。** "自动合并"（三方合并/字段级合并）在本文件里**没有验证过**，
   不要据此认为自动合并不可行——只是未测。
5. **E1 的白名单/工作产物区方案在"多人 + 多分支"场景下未验证**（本文件所有证据都来自单机、单写者为主的场景）。
6. **F2 的编码问题有环境依赖。** "默认代码页非 UTF-8 的 shell 会损坏中文"是实测；
   在默认 UTF-8 的环境里同一条命令不必然复现——**但"显式指定编码"的结论不因此改变**，
   因为它防的是"环境换了之后才发作"的隐患。
7. **B2 的"同步入口不变量"依赖语言特性**（"async 函数体在首个 await 前同步执行"）。
   换语言/换转译目标后这条把守方式需要重做。
8. **本文件没有覆盖：并发读一致性、分布式写入、网络分区、多租户权限。** 这些属于另一类问题。
