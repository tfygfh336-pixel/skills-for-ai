# skills-for-ai

给**由 AI 长期开发、长期迭代**的工程用的三个方法论 skill。

它们不解决「怎么让代码跑起来」，解决的是**跑起来之后、要一直改下去**这一段的代价：
AI 每次改动要花多少上下文去读懂、花多少时间验证对错、漏掉连带修改的概率有多大、
下一个会话能不能接上、一次改动能不能退回去。

三者都是**跨工程、跨技术栈的通用方法论**，不绑定特定工程。文中出现的工程名、数字、路径与命令都是**案例与证据**
（供理解与排序），不是判据、不是要求 —— 换栈、换场景时按现场重新判断；`cases/`、`checklists/`、`templates/`
是参考实现，**把某个工程的具体选择当成「用本方法就得这么做」是最常见的误读**。

## architecture-for-ai — 为「被 AI 长期改」而设计的代码与数据组织

> **只回答一件事：结构怎么摆，AI 才能在没有完整上下文、会漏连带、又可能与人并发的情况下长期把它改对。**

AI 改代码的失败方式和人不一样：它读不完整个仓库，只能靠搜到的一小片去推断全局；它会漏掉没看到的连带修改；
它可能和人、和另一个 agent 同时改同一份数据。结构的意义就是把这几件事挡在动手之前 ——
让同一件事只有一处完整表达、依赖方向单向、写盘只有一个闸门、失败必须响亮、没有版本控制时每次改动都是单向门。

针对的典型病灶：同一事实两处表达（A 组）· 测试/验收慢脆、是非无命令可判（B 组）· 上下文放不下、
不知道该读哪一块、高频查询越用越慢（C 组）· 人机并发改同一份数据、覆盖丢失、写半截（D 组）·
反复犯同一个错、漏连带修改（E 组）· 失败被静默吞掉、编码被写坏、给无法自动判定的东西硬加门禁（F 组）·
无版本控制的单向门（G 组）· 以「更严谨 / 更兼容 / AI 更好写」为由的加层加实现（H 组）· 模块化与按模块并行（I 组）。

## testing-for-ai — 可验证工程（AI 迭代版）

> 判定标准用**周期成本类**指标；每条「改好了」都由可复现证据支撑；**每个门禁先证明它会红。**

AI 改完最常见的自证是「跑过了」—— 而那条命令可能压根没验证任何东西。这套做法要回答的是：
这次改动凭什么算对、验证链的钱花在哪一段、某一步是不是在悄悄变慢、结论只有 exit code 时画面到底对不对。
它给的是**可机械取证**的能力：一个入口一条命令、失败非 0 退出、「跳过」与「通过」可区分、采不到真值就算红。

用：AI 生成且由 AI 长期迭代、有验证链的工程；结论只有 exit code 没人看过画面；验证越跑越慢；
带界面的工程验证时会弹到用户桌面；工程按模块/包组织，要建 per-module 测试入口与并行可跑性。
不用：好坏无法机械判定的主观质量；纯人肉验收且不改 headless；一次性脚本或寿命 < 1 个月；目标只是「省 token / 降费」。

本 skill **吸收并取代**了原 `silent-verify-loop`（后者已删除），吸收关系与新增内容见其 `README.md`。

## docs-for-ai — 为「被 AI 长期接手」设计的文档体系

> **只回答一件事：文档该怎么分层、怎么准入、怎么防漂移、怎么交接，
> 才能让一个没有先前上下文的 AI 独立接着把工程做下去。**

**判据只有一条（仅限文档体系）：一个零上下文的 AI，能否凭文档独立接手** —— 读懂为什么、知道按什么改、知道怎么验。
目标不是「多写文档」：写多了反而把活跃视野淹没，真正该看的规则沉在长文里没人翻到。
所以它管的是「哪份只写什么」「同一事实只有一处权威」「易腐的计数清单一律生成不手抄」
「历史必须带横幅退出活跃视野」「规则要出现在动手的那个位置」。

每条结论都来自一个真实工程（Electron 笔记应用 + CLI + MCP，由 AI 迭代数月），那里文档体系被反复修了六轮，
**每一轮都由实测驱动，而不是由「看起来更规范」驱动**。

## 这三件事的共同对手

三个 skill 打的是同一类失败：**AI 在没有完整上下文的情况下长期改动一份工程，而代价被悄悄转移到了下一轮。**

- 结构上的两处表达，会让下一次改动只改一处、于是分叉 —— 代价转移给下一个读到旧那份的会话；
- 验证上的假绿，会让错误通过一次，代价转移给后来排查的人；
- 文档上的手抄清单，会让计数漂移，代价转移给照着旧数字动手的那个 agent。

它们各自给出的答案也不同：结构给**可机械取证的前提**，验证给**会红的门禁**，文档给**唯一的权威副本与交接面**。
一条元规则贯穿三者：**能被机械判定的，就不要靠自觉。**

## 也给已有的工程用：接手改造

这三份不是只能用在从零开始的项目上 —— 恰恰相反，**真实起点通常是一个已经跑了很久、由 AI 反复迭代过的工程**：
目录长歪了、测试脚本一堆但都只是 `console.log`、文档和代码各说一套、上一个会话留下的状态没人知道。
这时候要的不是「推倒重来」，而是先量出病灶在哪，再按代价从高到低改。

- `architecture-for-ai/checklists/既有项目-改造评估.md` —— **只读评估**：该不该动、先动哪里、动完凭什么说变好了。
  从「取证」开始：回滚能力是否真的成立、基线哈希、写者清单、高频动作成本，然后才是结构病灶。
- `testing-for-ai` 的 **阶段 −1「存量改造」** —— 多数工程的真实起点。先把已有脚本变成**能响的断言**
  （失败是否 `exit` 非 0、有没有 `require.main` 守卫、有没有一条命令串起来、连的外部地址是不是本机真实值），
  产出「能当门禁的 / 只是打印的 / 跑不起来」三张表，再谈基线。
- `docs-for-ai/checklists/既有项目-文档架构改造评估.md` —— 同样是只读评估，多一步：让一个零上下文会话只读工程回答四个问题
  （现在什么状态/按什么步骤做/写文件的禁令/凭什么算做完），**如实记下它答不上来的部分**，作为改造前的基线。

改造的共同纪律也一样：**先取证，再动手**；任何「重写 / 合并 / 替换」动作之前先确认锚点唯一命中，
搜到 0 条或 >1 条就停手，不要「猜一个最像的」。没有基线就没有「变好了」的证据。

## 内容组织

每个 skill 都按同一套结构放内容，把重的东西放在资源文件里而不是正文里：
`SKILL.md` 会被逐字加载进上下文，所以它必须短；同目录的其它文件是纯资源、不自动加载，用得着才读。

- `SKILL.md` —— 决策层，先读这份，回答「该不该这么摆 / 该不该这么做」
- `REFERENCE.md` —— 机制层，落地细节、权衡、失败模式与实测证据
- `cases/` —— 真实工程里踩过的坑与取舍（`architecture-for-ai` 附一处已脱敏的结构缺口；`docs-for-ai` 附六轮演进含作者自己的失误）
- `checklists/` —— 可独立执行的清单，`architecture-for-ai` 与 `docs-for-ai` 各有一份「新建」与一份「既有项目改造」
- `templates/` —— 可整份拷走的脚本与示例（`docs-for-ai` 的起步门禁自带 `--selftest`，逐种注入验证必红项全红、负例保持绿）

## 证据强度

三份 skill 用**同一套四档**给结论标强度：🟢 源码级/平台契约、🟡 单机实测（换机要重测）、
🔴 参考实现的选择（换栈要重新判断，最该被推翻）、⬜ 未验证（只能当假设）。

**该表的权威副本在各 skill 的 `README.md`**，那里还写明「本 skill 没有哪一档」——
比如 `architecture-for-ai` 明说自己没有 🟢 档（结论都来自一个真实工程的观察，不是源码契约），
`docs-for-ai` 的实测全部来自同一个工程，`testing-for-ai` 的 🟡 全部是单机、某一时段的观测。
**引用一条结论前先读那一行。**
