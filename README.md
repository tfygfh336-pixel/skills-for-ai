# skills-for-ai

给**由 AI 长期开发、长期迭代**的工程用的三个方法论 skill。

三者都是**跨工程、跨技术栈的通用方法论**，**不绑定特定工程**。文中出现的工程名、数字、路径与命令都是**案例与证据**
（供理解与排序），不是判据、不是要求 —— 换栈、换场景时按现场重新判断；`cases/`、`checklists/`、`templates/`
只是参考实现，**把某个工程的具体选择当成「用本方法就得这么做」是最常见的误读**。

## 三个 skill 各自解决什么问题

以下定位取自各 skill 自己的 `SKILL.md`，以原文为准；本文件只做索引，**不复述正文条目与表格**（复述一份就是这些 skill 自己禁止的「会漂移的副本」）。

### [`architecture-for-ai`](skills/architecture-for-ai/) — 为「被 AI 长期改」而设计的代码与数据组织

> **只回答一件事：结构怎么摆，AI 才能在没有完整上下文、会漏连带、又可能与人并发的情况下长期把它改对。**

输出的是**结构前提**（可机械取证的前提），不是验证方法论。

范围（只写「结构选择」）：分层与依赖方向 · 单一逻辑源与薄壳 · 接口粒度与读取成本上界 ·
数据层并发保护与原子写 · 可机械取证的结构前提 · 回滚能力 · 给 AI 的动作现场做信息架构。

针对的失败模式：同一事实两处表达（A 组）· 测试/验收慢脆、是非无命令可判（B 组）· 上下文放不下、不知道该读哪一块、
高频查询越用越慢（C 组）· 人机并发改同一份数据、覆盖丢失、写半截（D 组）· 反复犯同一个错、漏连带修改（E 组）·
失败被静默吞掉、编码被写坏、给无法自动判定的东西硬加门禁（F 组）· 无版本控制的单向门（G 组）·
以「更严谨 / 更兼容 / AI 更好写」为由的加层加实现（H 组）· 模块化与按模块并行（I 组）。

不适用：验证体系、门禁与真值口径、判别力证明（用 `testing-for-ai`）；文档治理流程（用 `docs-for-ai`）；
零测试且寿命很短的一次性脚本；主观质量主导（文案 / 视觉 / 研究结论）的项目。

### [`testing-for-ai`](skills/testing-for-ai/) — 可验证工程（AI 迭代版）

> 「让 AI 迭代的工程**可验证**」这一套做法。
> 判定标准用**周期成本类**指标；每条「改好了」都由可复现证据支撑；**每个门禁先证明它会红。**

不只是「静默那一半」：先量出验证链卡在哪一段，再定分层与必跑集合、一个入口跑完整链并打印逐段耗时、
建立真值与门禁、让门禁自己有单测和判别力证明、给界面工程补上离屏截图与读图证据。

用：AI 生成且由 AI 长期迭代、有验证链的工程；给新项目接入自动验证/回归闭环；结论只有 exit code、没人看过画面；
验证越跑越慢；带界面的工程验证时会弹到用户桌面；工程按模块/包组织，要建 per-module 测试入口与并行可跑性。

不用：好坏无法机械判定的主观质量；纯人肉验收且不改 headless；一次性脚本或寿命 < 1 个月；
目标只是「省 token / 降费」——那不是本 skill 的目标。

本 skill **吸收并取代**了原 `silent-verify-loop`（后者已删除），吸收关系与新增内容见其 `README.md`。

### [`docs-for-ai`](skills/docs-for-ai/) — 为「被 AI 长期接手」设计的文档体系

> **只回答一件事：文档该怎么分层、怎么准入、怎么防漂移、怎么交接，
> 才能让一个没有先前上下文的 AI 独立接着把工程做下去。**

**判据只有一条（仅限文档体系）：一个零上下文的 AI，能否凭文档独立接手** —— 读懂为什么、知道按什么改、知道怎么验。
目标不是「多写文档」。

每条结论都来自一个真实工程（Electron 笔记应用 + CLI + MCP，由 AI 迭代数月），那里文档体系被反复修了六轮，
**每一轮都由实测驱动，而不是由「看起来更规范」驱动**。

不适用：代码与数据的结构本身（用 `architecture-for-ai`）；验证体系与真值口径（用 `testing-for-ai`）；
主观质量主导的写作；一次性或寿命 < 1 个月的项目；只想「产出更多文档」而不打算让 AI 接手维护。

## 它们之间的关系：依赖顺序，不是并列

> **结构前提（`architecture-for-ai`）→ 可机械取证（`testing-for-ai`）→ 交接面（`docs-for-ai`）。**

后两者都以前者成立为前提 —— 这也是 `testing-for-ai` 该在「零测试项目」上拒绝出场的原因。
三者共用同一条元规则：**能被机械判定的，就不要靠自觉。**

跨 skill 的指针**不构成依赖**：每个 skill **自足**，单独拷走就能用，不依赖任何工程、绝对路径或脚本。
重叠规则（共 12 组）的权威分配表在**三份 README 里内容相同**，是**导航视图**而非新的事实权威；
本仓库根 README 不复制它，**有分歧时以各 skill 条目里的指针为准**。

## 证据强度：统一四档词表

三份 skill 用**同一套四档**给结论标强度。**该表是各 skill `README.md` 的权威副本**（内容在三处相同，改一处要同批改三处）；
这里不复制，避免出现第四份会漂移的副本 —— 请直接读
[`architecture-for-ai`](skills/architecture-for-ai/README.md#证据强度统一四档词表) 的那一节。

一句话：🟢 源码级/平台契约、🟡 单机实测（换机要重测）、🔴 参考实现的选择（换栈要重新判断，最该被推翻）、⬜ 未验证（只能当假设）。
**每个 skill 都把「本 skill 没有哪一档」写在各自 README 里** —— 引用前先读那一行。

## 用法

把需要的目录拷到 skill 加载目录即可：

```bash
cp -r skills/architecture-for-ai ~/.dsh/skills/
```

每个 skill 自足：`SKILL.md` 是**决策层**（先读），`REFERENCE.md` 是**机制层**（落地、权衡、失败模式、实测数据），
`cases/` / `checklists/` / `templates/` 是参考实现与可整份拷走的脚本。
frontmatter 决定**要不要加载**，正文按需加载、必须短；同目录其它文件是纯资源、不自动加载。
